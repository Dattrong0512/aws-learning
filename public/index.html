AWS Availability Zone

Availability Zone (AZ) là các data center vật lý nằm trong một Region (khu vực địa lý) của AWS.

Cấu trúc:

Region (ví dụ: ap-southeast-1 – Singapore)
├── AZ: ap-southeast-1a  (data center A)
├── AZ: ap-southeast-1b  (data center B)
└── AZ: ap-southeast-1c  (data center C)

Tại sao cần nhiều AZ?

Các AZ cách nhau vài km — nếu một AZ bị mất điện hoặc thiên tai, các AZ còn lại vẫn hoạt động bình thường → đây là nền tảng của High Availability (tính sẵn sàng cao).

Ví dụ thực tế:

Bạn deploy app trên 3 AZ ở Singapore. Ngày hôm đó 1a mất điện đột ngột → app vẫn chạy trên 1b và 1c, người dùng không bị gián đoạn.

Root Account & IAM Users

Root Account là gì?

Root Account là tài khoản được tạo ra đầu tiên khi bạn đăng ký AWS. Nó có toàn quyền tuyệt đối — không bị giới hạn bởi bất kỳ policy nào.

Không nên dùng Root Account cho công việc hàng ngày — chỉ dùng để setup ban đầu hoặc các tác vụ đặc biệt (như thay đổi billing). Thay vào đó, tạo IAM User để sử dụng.

Một Root Account → Nhiều IAM Users

Root Account (1 tài khoản duy nhất)
├── IAM User: trong_dev
├── IAM User: an_devops
├── IAM User: hoa_manager
└── IAM User: minh_tester

Mỗi IAM User có thể có quyền khác nhau tuỳ theo Policy được gán.

Cách đăng nhập với IAM User

IAM User không đăng nhập qua trang thường của AWS. Họ phải dùng Sign-in URL riêng của Root Account:

https://<account-id>.signin.aws.amazon.com/console

Ví dụ:

https://123456789012.signin.aws.amazon.com/console

Hoặc bạn có thể đặt alias cho dễ nhớ:

https://my-company.signin.aws.amazon.com/console

Khi vào trang Sign-in URL, IAM User nhập 3 thông tin:

TrườngVí dụ
Account ID / Alias123456789012 hoặc my-company
IAM User nametrong_dev
Password • •••••••

IAM: Users & Groups

IAM = Identity and Access Management → Hệ thống quản lý danh tính và phân quyền trong AWS.

Nó trả lời 2 câu hỏi cốt lõi:

Bạn là ai? → User, Group, Role
Bạn được phép làm gì? → Policy

User

Một tài khoản đại diện cho một người cụ thể trong AWS.

Ví dụ: user dattrong, user annguyen

Group

Nhóm gom nhiều User lại để quản lý quyền tập trung. Thay vì cấp quyền từng người, bạn cấp một lần cho cả group → tất cả thành viên tự động có quyền đó.

├── User: An

Một user cũng có thể không thuộc group nào (gán policy trực tiếp).

IAM Policies – Cấu trúc đầy đủ

Cấu trúc tổng quan

Một IAM Policy là file JSON gồm 3 phần chính:

TrườngBắt buộc?Ý nghĩa
VersionCóPhiên bản ngôn ngữ policy — luôn dùng "2012-10-17"
IdKhôngTên định danh cho policy (tuỳ chọn)
StatementCóDanh sách các quy tắc phân quyền

Mỗi Statement gồm 6 trường

TrườngBắt buộc?Ý nghĩa
SidKhôngTên định danh cho statement (tuỳ chọn)
EffectCóAllow (cho phép) hoặc Deny (từ chối)
PrincipalTuỳAccount / User / Role được áp dụng policy này
ActionCóDanh sách hành động được phép hoặc bị cấm
ResourceCóTài nguyên mà Action được áp dụng lên
ConditionKhôngĐiều kiện để policy có hiệu lực (tuỳ chọn)

Ví dụ thực tế

{
  "Version": "2012-10-17",
  "Id": "S3-Account-Permissions",
  "Statement": [
    {
      "Sid": "1",
      "Effect": "Allow",
      "Principal": {
        "AWS": ["arn:aws:iam::123456789012:root"]
      },
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": ["arn:aws:s3:::mybucket/*"]
    }
  ]
}

Đọc policy trên theo ngôn ngữ thường:

Cho phép (Allow) tài khoản root 123456789012 được đọc (GetObject) và tải lên (PutObject) các file trong S3 bucket tên mybucket.

Giải thích từng trường trong ví dụ

Principal — Ai được áp dụng policy?

arn:aws:iam::123456789012:root  →  tài khoản root của account 123456789012

Có thể là user, role, hoặc cả một AWS account.

Action — Làm gì?

s3:GetObject   →  đọc / tải file từ S3
s3:PutObject   →  upload file lên S3

Dùng * để áp dụng tất cả action: "s3:*"

Resource — Trên tài nguyên nào?

arn:aws:s3:::mybucket/*  →  tất cả object bên trong bucket "mybucket"

Dùng "*" nếu muốn áp dụng cho mọi resource.

Condition (không có trong ví dụ trên, nhưng hay dùng):

"Condition": {
  "IpAddress": {
    "aws:SourceIp": "203.0.113.0/24"
  }
}

→ Chỉ cho phép nếu request đến từ dải IP 203.0.113.0/24.

Tóm lại: Statement = Ai (Principal) được làm gì (Action) trên tài nguyên nào (Resource), với điều kiện gì (Condition), và kết quả là Allow hay Deny (Effect).
IAM: Permission (Policy)

Policy = file JSON gắn vào User hoặc Group, xác định rõ quyền được phép hoặc bị cấm.

Mỗi policy trả lời 3 câu hỏi:

Effect   → Cho phép hay từ chối?  (Allow / Deny)
Action   → Được làm hành động gì?
Resource → Trên tài nguyên nào?

Ví dụ policy thực tế — chỉ cho quyền xem (read-only):

{
  "Effect": "Allow",
  "Action": "ec2:Describe*",
  "Resource": "*"
}

→ User được xem thông tin EC2 (DescribeInstances, DescribeVolumes…), nhưng không được tạo/xóa.

Bảng tóm tắt 3 quyền phổ biến trong ví dụ:

ActionÝ nghĩa
ec2:Describe*Xem thông tin EC2
elasticloadbalancing:Describe*Xem thông tin Load Balancer
cloudwatch:ListMetrics, GetMetricStatisticsXem metrics / logs CloudWatch

Quyền user này CÓ:

✅ Xem EC2
✅ Xem Load Balancer
✅ Xem CloudWatch metrics

Quyền user này KHÔNG CÓ (vì thiếu action tương ứng):

❌ Tạo EC2             (cần: ec2:RunInstances)
❌ Xóa EC2             (cần: ec2:TerminateInstances)
❌ Tạo Load Balancer   (cần: elasticloadbalancing:CreateLoadBalancer)
Nguyên tắc vàng: AWS áp dụng Least Privilege — chỉ cấp đúng quyền cần thiết, không hơn. Giảm thiểu rủi ro bảo mật.

AWS Account

IAM = hệ thống bảo vệ AWS của bạn — kiểm soát ai được vào, và được làm gì sau khi vào.

AWS Console – Simultaneous Sessions

Khái niệm

Simultaneous Sessions = nhiều phiên đăng nhập AWS Console diễn ra cùng lúc, từ nhiều browser/tab/user khác nhau.

AWS Console không giới hạn số phiên đồng thời — nhiều IAM User có thể cùng đăng nhập và làm việc song song trong cùng một tài khoản AWS.

Ví dụ thực tế

Cùng một lúc:
├── Trong (IAM User: trong_dev)     → đang xem EC2 trên Chrome
├── An    (IAM User: an_devops)     → đang cấu hình VPC trên Firefox
└── Hoa   (IAM User: hoa_manager)  → đang xem Billing trên Safari

Tất cả 3 người cùng login vào 1 AWS account nhưng mỗi người chỉ thấy và làm được những gì Policy của mình cho phép.

Dùng nhiều tab/session cùng lúc

Bạn cũng có thể tự mở nhiều session cùng lúc cho bản thân:

SessionCách mởDùng để
Tab thườngCtrl+TConsole chính
Incognito / PrivateCtrl+Shift+NLogin bằng account/role khác
Browser khácChrome / FirefoxThêm 1 account nữa
Trick thực tế: Dev thường mở Chrome cho account Development và Firefox cho account Production để tránh nhầm lẫn.

Lưu ý quan trọng

Nhiều người cùng thao tác trên cùng một tài nguyên có thể gây xung đột — ví dụ 2 người cùng sửa 1 Security Group một lúc, người sau sẽ ghi đè người trước.

→ Trong thực tế, các team dùng Infrastructure as Code (Terraform, CloudFormation) để tránh tình trạng này.

IAM – Password Policy

Mật khẩu mạnh = bảo mật cao hơn cho tài khoản AWS của bạn.

Root Account có thể thiết lập Password Policy áp dụng cho tất cả IAM Users trong account.

Các thiết lập có thể cấu hình

Thiết lậpÝ nghĩa
Minimum password lengthĐộ dài tối thiểu, ví dụ: ít nhất 8 ký tự
Require uppercase lettersBắt buộc có chữ HOA (A-Z)
Require lowercase lettersBắt buộc có chữ thường (a-z)
Require numbersBắt buộc có số (0-9)
Require non-alphanumeric charactersBắt buộc có ký tự đặc biệt (!@#$%^&*…)
Allow IAM users to change their own passwordCho phép user tự đổi mật khẩu
Password expirationBắt buộc đổi mật khẩu sau N ngày
Prevent password reuseKhông cho dùng lại mật khẩu cũ

Ví dụ thực tế

Password Policy của một công ty:

Độ dài tối thiểu : 12 ký tự
Phải có          : Chữ hoa + chữ thường + số + ký tự đặc biệt
Hết hạn sau      : 90 ngày
Không được dùng lại: 5 mật khẩu gần nhất
User tự đổi mật khẩu: ✅ cho phép

Mật khẩu hợp lệ theo policy trên:

✅ MyP@ssw0rd2024!   (đủ hoa, thường, số, ký tự đặc biệt, >= 12 ký tự)
❌ password123       (không có chữ hoa, không có ký tự đặc biệt)
❌ ABC123            (quá ngắn)
Password Policy chỉ áp dụng cho IAM Users đăng nhập bằng Console. Không ảnh hưởng đến Access Key (dùng cho CLI/API).

IAM Roles cho dịch vụ AWS

Một số dịch vụ AWS cần thực hiện hành động thay mặt bạn (ví dụ: EC2 cần đọc file từ S3). Thay vì nhét access key vào trong server (rất nguy hiểm), ta gán IAM Role cho dịch vụ đó.

Vì sao dùng Role thay vì Access Key?

❌ Cách cũ: lưu Access Key trong code/server  →  dễ bị lộ, khó xoay key
✅ Cách đúng: gán IAM Role cho dịch vụ        →  AWS tự cấp credential tạm thời, an toàn

Ví dụ: gán Role cho EC2 Instance → ứng dụng trên EC2 có thể gọi AWS (đọc S3, ghi log...) mà không cần lưu key nào cả.

Các Role thường gặp

RoleDùng cho
EC2 Instance RolesCấp quyền cho ứng dụng chạy trên máy ảo EC2
Lambda Function RolesCấp quyền cho hàm Lambda truy cập dịch vụ khác
Roles for CloudFormationCho phép CloudFormation tạo/quản lý tài nguyên thay bạn
Tóm lại: Role giống một "chiếc mũ quyền hạn" mà dịch vụ AWS đeo vào để được phép làm việc — credential do AWS tự cấp tạm thời, không bao giờ lộ ra ngoài.

🖥️ EC2

Amazon EC2 – Tổng quan

EC2 = Elastic Compute Cloud → đây là Infrastructure as a Service (IaaS) và là một trong những dịch vụ phổ biến nhất của AWS.

Hiểu EC2 là nền tảng để hiểu cách Cloud hoạt động.

EC2 gồm những khả năng chính nào?

Khả năngDịch vụÝ nghĩa
Thuê máy ảoEC2Renting virtual machines – thuê server ảo để chạy ứng dụng
Lưu dữ liệu trên ổ ảoEBSStoring data on virtual drives – ổ cứng ảo gắn vào EC2
Phân phối tảiELBDistributing load – chia đều request ra nhiều máy
Tự động co giãnASGAuto Scaling Group – tự tăng/giảm số máy theo tải

Hình dung cách các thành phần ghép lại

      Người dùng
         │
         ▼
    ELB (chia tải)
   /     │      \
EC2     EC2     EC2     ← các máy ảo (nằm trong ASG, tự co giãn)
 │       │       │
EBS     EBS     EBS     ← mỗi máy có ổ đĩa ảo riêng
Tóm lại: EC2 (máy ảo) + EBS (ổ đĩa) + ELB (cân bằng tải) + ASG (tự co giãn) = bộ tứ nền tảng để chạy ứng dụng trên AWS.
EC2 User Data

EC2 User Data là một script dùng để bootstrap instance — tức là tự động chạy các lệnh ngay khi máy khởi động lần đầu.

Bootstrapping = chạy các lệnh tự động khi máy bắt đầu chạy.

Security Group = tường lửa của EC2 — là nền tảng của network security trong AWS, kiểm soát traffic nào được vào (inbound) / ra (outbound) instance.

💸 Rẻ tới 90% — instance RẺ NHẤT trên AWS

Nhớ: Spot = cost-efficient nhất nhưng không đáng tin → chỉ cho workload chịu lỗi tốt.

Elastic IP

Mặc định, public IP của EC2 sẽ THAY ĐỔI mỗi lần stop/start instance. Elastic IP là một public IPv4 cố định mà bạn sở hữu — gắn vào instance nào tuỳ ý, IP không đổi cho tới khi bạn xoá.

Công dụng chính: che (mask) sự cố của một instance — chỉ cần remap Elastic IP sang instance khác trong account là dịch vụ phục hồi gần như tức thì.

Đặc điểm quan trọng

Đặc điểmChi tiết
Bản chấtPublic IPv4 cố định, bạn sở hữu cho tới khi xoá
FailoverRemap nhanh sang instance khác khi instance/phần mềm gặp sự cố
Giới hạnMặc định 5 Elastic IP / account (có thể xin AWS tăng)

⚠️ Lời khuyên: HẠN CHẾ dùng Elastic IP

❌ Thường phản ánh thiết kế kiến trúc kém (poor architectural decisions)
✅ Thay vào đó: dùng random public IP + đăng ký 1 DNS name trỏ tới nó
✅ Hoặc dùng Load Balancer (không cần public IP cho instance)
Tóm lại: Elastic IP = IP công cộng cố định để failover nhanh, nhưng dùng nhiều = mùi thiết kế tệ. Ưu tiên DNS name hoặc Load Balancer.
EC2 Placement Groups

Đôi khi bạn muốn kiểm soát cách AWS đặt (place) các EC2 instance lên phần cứng vật lý → dùng Placement Group. Khi tạo, bạn chọn 1 trong 3 chiến lược:

StrategyÝ chínhUse case
ClusterGom instance vào 1 nhóm low-latency trong cùng 1 AZBig data cần chạy nhanh, app cần latency cực thấp
SpreadTrải instance ra phần cứng khác nhau (max 7 / AZ)App critical cần cách ly tối đa khỏi lỗi
PartitionTrải instance ra nhiều partition (mỗi partition = bộ rack riêng)Hadoop, Cassandra, Kafka — hàng trăm instance
🧠 Nhớ nhanh: Cluster = nhanh (gom lại) · Spread = an toàn (tách ra, ít máy) · Partition = vừa scale lớn vừa cách ly theo rack.
Cluster — low latency, cùng 1 AZ

Gom tất cả instance vào cùng 1 AZ, nối với nhau bằng mạng tốc độ cao.

🚀 Pros: mạng cực tốt — 10 Gbps giữa các instance
         (bật Enhanced Networking — khuyến nghị)
💥 Cons: AZ chết → TẤT CẢ instance chết cùng lúc (no HA)
✅ Use case: Big Data job cần xong nhanh
            App cần latency cực thấp & throughput mạng cao
Cluster đánh đổi độ sẵn sàng để lấy hiệu năng mạng tối đa.
Spread — tách phần cứng, max 7/AZ

Mỗi instance nằm trên một phần cứng vật lý khác nhau, có thể trải qua nhiều AZ.

✅ Pros: span nhiều AZ
         giảm rủi ro lỗi đồng thời (mỗi máy 1 hardware riêng)
⚠️ Cons: giới hạn 7 instance / AZ / placement group
✅ Use case: app cần High Availability tối đa
            app critical mà mỗi instance phải cách ly khỏi lỗi của nhau
Spread = an toàn nhất nhưng số máy ít (7/AZ).
Partition — scale lớn, cách ly theo rack

Trải instance ra nhiều partition; mỗi partition dùng bộ rack riêng nên lỗi 1 partition không lan sang partition khác.

📦 Tối đa 7 partition / AZ — span được nhiều AZ trong cùng region
📈 Tới hàng trăm (100s) EC2 instance / group
🔌 Instance khác partition KHÔNG share rack
💥 Lỗi 1 partition ảnh hưởng nhiều EC2 trong đó, nhưng KHÔNG ảnh hưởng partition khác
🏷️ EC2 đọc được thông tin partition qua metadata
✅ Use case: HDFS, HBase, Cassandra, Kafka
Partition = lựa chọn cho distributed/big data quy mô lớn cần vừa scale vừa chống lỗi theo rack.

EC2 Hibernate

Bình thường EC2 có Stop và Terminate. Hibernate là cách thứ ba: giữ nguyên trạng thái RAM khi tắt máy, để lần start sau boot cực nhanh (OS không bị stop/restart).

Nhắc lại: Stop vs Terminate

Hành độngĐiều gì xảy ra
StopData trên disk (EBS) được giữ nguyên cho lần start sau
TerminateEBS volume (root) nếu set "delete on termination" sẽ bị xoá → mất data
Vấn đề: mỗi lần start lại, OS boot → app khởi động → cache warm up → tốn thời gian.

Hibernate giải quyết gì?

🧠 Giữ nguyên trạng thái in-memory (RAM)
⚡ Boot nhanh hơn nhiều (OS KHÔNG bị stop/restart)
💾 Under the hood: RAM state được ghi vào 1 file trong root EBS volume
🔒 Root EBS volume BẮT BUỘC phải được mã hoá (encrypted)

Vòng đời khi Hibernate

Running ──Hibernate──▶ Stopping (ghi RAM → file trên root EBS)
                          │ Shutdown
                          ▼
                       Stopped (RAM đã lưu trong EBS)
                          │ Start
                          ▼
                       Running (nạp lại RAM → chạy tiếp như cũ)

Use cases

✅ Long-running processing (xử lý chạy dài)
✅ Saving the RAM state (cần giữ nguyên trạng thái bộ nhớ)
✅ Services mất nhiều thời gian khởi tạo (initialize)

EBS Volume – Tổng quan

EBS (Elastic Block Store) Volume là một network drive có thể attach vào EC2 instance khi nó đang chạy, giúp dữ liệu persist kể cả sau khi instance bị terminate. Ví von: như một "network USB stick".

Khái niệm cốt lõi
  • Là network drive gắn vào instance khi đang chạy.
  • Cho phép instance lưu dữ liệu bền vững (persist), kể cả sau khi terminate.
  • Ở mức CCP: chỉ mount được vào 1 instance tại 1 thời điểm.
  • Bound vào 1 Availability Zone (AZ) cụ thể.
Đặc điểm chi tiết
  • Network drive (không phải ổ vật lý) → dùng network để giao tiếp ⇒ có thể có chút latency.
  • Có thể detach khỏi 1 EC2 và attach sang instance khác rất nhanh.
  • Locked vào 1 AZ: EBS ở us-east-1a không thể attach sang us-east-1b. Muốn chuyển AZ phải snapshot trước.
  • Có provisioned capacity (size tính bằng GB và IOPS):
    • Bị tính phí cho toàn bộ provisioned capacity.
    • Có thể tăng dung lượng theo thời gian.
EBS – Delete on Termination attribute
  • Điều khiển hành vi của EBS khi EC2 instance bị terminate.
  • Mặc định: root EBS volume bị xóa (attribute = enabled).
  • Mặc định: các EBS volume khác được attach thì KHÔNG bị xóa (attribute = disabled).
  • Có thể điều chỉnh qua AWS Console / AWS CLI.
  • Use case: giữ lại root volume khi instance bị terminate.
EBS Snapshots
Cơ bản
  • Snapshot = backup của EBS volume tại một thời điểm.
  • Không bắt buộc detach volume để snapshot, nhưng được khuyến nghị.
  • Có thể copy snapshot qua AZ hoặc Region khác.
Snapshots Features
  • EBS Snapshot Archive: chuyển snapshot sang "archive tier" rẻ hơn 75%; khôi phục mất 24–72 giờ.
  • Recycle Bin for EBS Snapshots: đặt rule giữ lại snapshot đã xóa để khôi phục sau khi lỡ xóa; retention từ 1 ngày đến 1 năm.
  • Fast Snapshot Restore (FSR): ép full initialization snapshot để không có latency ở lần dùng đầu.
AMI (Amazon Machine Image)
Overview
  • AMI = Amazon Machine Image.
  • Là một customization của EC2 instance: thêm software, configuration, OS, monitoring...
  • Boot / config nhanh hơn vì software đã được pre-packaged.
  • Được build cho một region cụ thể (có thể copy qua region khác).
  • Launch EC2 instance từ:
    • Public AMI: do AWS cung cấp.
    • Your own AMI: tự tạo & maintain.
    • AWS Marketplace AMI: do người khác tạo (và có thể bán).
AMI Process (from an EC2 instance)
  1. Start một EC2 instance và customize nó.
  2. Stop instance (để đảm bảo data integrity).
  3. Build AMI — bước này cũng tạo EBS snapshots.
  4. Launch instances từ AMI đó (kể cả ở AZ/region khác).
EC2 Instance Store
  • EBS volume là network drive với hiệu năng tốt nhưng "limited".
  • Cần high-performance hardware disk → dùng EC2 Instance Store.
  • I/O performance tốt hơn.
  • Ephemeral: mất storage nếu instance bị stop.
  • Tốt cho buffer / cache / scratch data / temporary content.
  • Rủi ro mất dữ liệu nếu hardware fail.
  • Backup & replication là trách nhiệm của bạn.
EBS Volume Types

EBS Volume có 6 loại, đặc trưng bởi Size | Throughput | IOPS. Chỉ gp2/gp3 và io1/io2 Block Express dùng được làm boot volume.

Tổng quan 6 loại
  • gp2 / gp3 (SSD): general purpose, cân bằng giá & hiệu năng cho nhiều workload.
  • io1 / io2 Block Express (SSD): hiệu năng cao nhất, cho workload mission-critical low-latency / high-throughput.
  • st1 (HDD): chi phí thấp, cho workload truy cập thường xuyên, throughput-intensive.
  • sc1 (HDD): chi phí thấp nhất, cho workload ít truy cập.
General Purpose SSD (gp2 / gp3)
  • Cost-effective, low-latency.
  • Use case: system boot volumes, virtual desktops, dev & test environments.
  • Size: 1 GiB – 16 TiB.
  • gp3:
    • Mặc định đã có 3.000 IOPS và 125 MiB/s throughput, dù volume lớn hay nhỏ.
    • Nếu cần hiệu năng cao hơn, bạn có thể tăng IOPS và throughput riêng biệt:
      • IOPS tối đa: 16.000
      • Throughput tối đa: 1.000 MiB/s
  • Kích thước volume không ảnh hưởng trực tiếp đến IOPS.
  • gp2:
    • Hiệu năng phụ thuộc vào kích thước volume.
    • Công thức: IOPS = 3 × Dung lượng (GiB)
      Ví dụ:
      SizeIOPS
      100 GiB300 IOPS
      500 GiB1.500 IOPS
      1.000 GiB3.000 IOPS
    • Các volume nhỏ có thể burst (tăng tốc tạm thời) lên 3.000 IOPS.
    • IOPS tối đa là 16.000.
      Muốn đạt 16.000 IOPS: 16.000 ÷ 3 ≈ 5.334 GiB => Cần volume khoảng 5.334 GiB.
Provisioned IOPS (PIOPS) SSD (io1 / io2)
  • Cho critical business apps cần sustained IOPS, hoặc apps cần > 16,000 IOPS.
  • Tốt cho database workloads (nhạy với storage performance & consistency).
  • io1 (4 GiB – 16 TiB): max PIOPS 64,000 (Nitro EC2) & 32,000 (loại khác); tăng IOPS độc lập với size.
  • io2 Block Express (4 GiB – 64 TiB): sub-millisecond latency; max PIOPS 256,000 với tỉ lệ IOPS:GiB = 1,000:1.
  • Hỗ trợ EBS Multi-attach.
Hard Disk Drives (st1 / sc1)
  • Không dùng được làm boot volume.
  • Size: 125 GiB – 16 TiB.
  • Throughput Optimized HDD (st1): Big Data, Data Warehouses, Log Processing; max throughput 500 MiB/s – max IOPS 500.
  • Cold HDD (sc1): dữ liệu ít truy cập, ưu tiên chi phí thấp nhất; max throughput 250 MiB/s – max IOPS 250.

EBS Multi-Attach – io1/io2 family

Multi-Attach cho phép attach cùng một EBS volume vào nhiều EC2 instance cùng lúc — chỉ với họ io1/io2 và tất cả phải ở cùng 1 AZ.

  • Mỗi instance có full read & write lên volume hiệu năng cao.
  • Tối đa 16 EC2 instance tại một thời điểm.
  • Use case: tăng application availability cho clustered Linux apps (vd: Teradata).
  • Ứng dụng phải tự quản lý concurrent writes (ghi đồng thời).
  • Bắt buộc dùng file system cluster-aware — KHÔNG dùng XFS, EXT4...
Encryption – Mã hoá một EBS volume chưa mã hoá

Volume đang unencrypted được mã hoá đi vòng qua snapshot theo 4 bước:

  1. Tạo EBS snapshot của volume.
  2. Mã hoá snapshot (dùng thao tác copy).
  3. Tạo volume mới từ snapshot đã mã hoá → volume mới cũng được mã hoá.
  4. Attach volume đã mã hoá trở lại instance ban đầu.
🔒 Phải đi vòng qua snapshot vì không thể bật mã hoá trực tiếp trên một volume sẵn có.
Amazon EFS – Elastic File System

EFS = managed NFS (network file system) có thể mount đồng thời lên nhiều EC2, chạy đa AZ. Highly available, scalable, pay-per-use nhưng đắt (~3x gp2).

Đặc điểm & Use case
  • Dùng giao thức NFSv4.1; kiểm soát truy cập bằng Security Group.
  • Chỉ tương thích Linux AMI (KHÔNG Windows) — là POSIX file system với standard file API.
  • Encryption at rest bằng KMS.
  • Tự scale tự động, không cần capacity planning.
  • Scale: hàng nghìn NFS client đồng thời, throughput 10 GB+/s, lớn tới petabyte-scale.
  • Use case: content management, web serving, data sharing, WordPress.
Performance Mode (chọn lúc tạo EFS)
  • General Purpose (default): use case nhạy latency (web server, CMS...).
  • Max I/O: latency cao hơn nhưng throughput cao, highly parallel (big data, media processing).
Throughput Mode
  • Bursting: 1 TB = 50 MiB/s + burst tới 100 MiB/s.
  • Provisioned: tự đặt throughput bất kể storage size (vd: 1 GiB/s cho 1 TB).
  • Elastic: tự scale throughput lên/xuống theo workload — tới 3 GiB/s đọc & 1 GiB/s ghi; hợp workload khó đoán.
Storage Classes & Lifecycle
  • Storage Tiers (lifecycle management — chuyển file sau N ngày):
    • Infrequent Access (EFS-IA): lưu rẻ hơn nhưng tốn phí khi đọc lại.
    • Standard: file truy cập thường xuyên.
    • Archive: dữ liệu rất ít truy cập (vài lần/năm), rẻ hơn ~50%.
  • Dùng lifecycle policies để di chuyển file giữa các tier.
  • Availability & durability:
    • Standard: Multi-AZ → hợp production.
    • One Zone: 1 AZ → hợp dev; backup bật mặc định; có EFS One Zone-IA.
  • Chọn đúng storage class → tiết kiệm tới hơn 90% chi phí.
EBS vs EFS (vs Instance Store)

So sánh nhanh các loại storage để chọn đúng theo nhu cầu.

EBS – Elastic Block Store
  • Gắn 1 instance tại một thời điểm (trừ multi-attach io1/io2).
  • Locked ở mức 1 AZ.
  • gp2: IO tăng khi disk size tăng. gp3 & io1: tăng IO độc lập với size.
  • Migrate qua AZ: tạo snapshot → restore sang AZ khác.
  • Backup tốn IO → đừng chạy lúc app đang nhiều traffic.
  • Root EBS volume mặc định bị xoá khi terminate instance (có thể tắt).
EFS – Elastic File System
  • Mount 100s instance qua nhiều AZ.
  • Dùng để share website files (WordPress).
  • Chỉ cho Linux instance (POSIX).
  • Giá cao hơn EBS, bù lại tận dụng Storage Tiers để tiết kiệm.

Load Balancing là gì?

Load Balancer là các server đứng giữa: nhận traffic từ user rồi chuyển tiếp (forward) xuống nhiều server phía sau (vd: nhiều EC2 instance) — gọi là downstream.

Users ──▶ ┌────────────────┐ ──▶ EC2 Instance
Users ──▶ │ Load Balancer  │ ──▶ EC2 Instance
Users ──▶ └────────────────┘ ──▶ EC2 Instance
Người dùng chỉ thấy một điểm vào duy nhất (Load Balancer), còn traffic được rải đều xuống nhiều máy phía sau.
Vì sao dùng Elastic Load Balancer (ELB)?

ELB = Elastic Load Balancer — một managed load balancer do AWS quản lý.

ELB tốn phí nhưng AWS lo hết phần cực nhọc → bạn tiết kiệm công sức.

Cross-Zone Load Balancing

Cross-Zone Load Balancing quyết định cách các node của Load Balancer rải request xuống các instance nằm ở các Availability Zone (AZ) khác nhau.

Có bật Cross-Zone Load Balancing

Mỗi node Load Balancer rải request đều ra TẤT CẢ instance đã đăng ký ở MỌI AZ.

Client gửi: 50 → node AZ1, 50 → node AZ2
AZ1: 2 instance | AZ2: 8 instance → tổng 10 instance
Mỗi node rải đều ra cả 10 instance → mỗi instance nhận 10
✅ Kết quả: tải CÂN BẰNG hoàn toàn dù số instance mỗi AZ khác nhau
Dù AZ1 chỉ có 2 máy còn AZ2 có 8 máy, mọi instance vẫn nhận đúng 10 request như nhau.
KHÔNG bật Cross-Zone Load Balancing

Mỗi node chỉ rải request xuống các instance đăng ký trong CHÍNH AZ của nó.

Client gửi: 50 → node AZ1, 50 → node AZ2
AZ1 (2 instance): 50 / 2 = 25 mỗi máy
AZ2 (8 instance): 50 / 8 = 6.25 mỗi máy
⚠️ Kết quả: tải MẤT CÂN BẰNG giữa các AZ
Node chỉ biết các máy trong AZ của mình → AZ ít máy bị quá tải, AZ nhiều máy lại nhàn.

SNI – Server Name Indication

SNI giải quyết vấn đề gì?

SNI cho phép load nhiều SSL certificate lên một web server để phục vụ nhiều website trên cùng một máy.

  • Server nhìn hostname → trả về đúng certificate, không tìm thấy thì trả cert mặc định.

Auto Scaling Group (ASG) – Tổng quan

ASG là gì?

Tải web thay đổi theo thời gian; trên cloud có thể tạo/xoá server rất nhanh. ASG tự động hoá việc đó.

  • Scale out: thêm EC2 instance khi tải tăng.
  • Scale in: bớt EC2 instance khi tải giảm.
  • Đảm bảo số instance chạy trong khoảng minimum ↔ maximum.
  • Tự đăng ký instance mới vào Load Balancer.
  • Tự tạo lại instance nếu một instance bị terminate (vd: unhealthy).
  • ASG miễn phí — chỉ trả tiền cho EC2 bên dưới.

ASG – Launch Template & Attributes

Launch Template

ASG cần một Launch Template (bản cũ "Launch Configurations" đã deprecated) mô tả cách tạo instance:

  • AMI + Instance Type
  • EC2 User Data
  • EBS Volumes
  • Security Groups
  • SSH Key Pair
  • IAM Roles cho EC2 instance
  • Network + Subnets
  • Load Balancer information

Thuộc tính riêng của ASG

  • Min Size / Max Size / Initial (Desired) Capacity
  • Scaling Policies
🧠 Exam gotcha: "Launch Configuration" xuất hiện trong đáp án → thường là đáp án sai/cũ, dùng Launch Template.
ASG – Scaling với CloudWatch Alarms

Scale ASG bằng CloudWatch Alarm

  • Alarm giám sát một metric (vd: Average CPU, hoặc custom metric).
  • Metric được tính trung bình trên toàn bộ instance của ASG (overall), không phải từng máy.
  • Dựa trên alarm:
    • Scale-out policy → tăng số instance.
    • Scale-in policy → giảm số instance.
