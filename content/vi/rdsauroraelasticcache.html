Amazon RDS fundamentals & operations

Mục đích: Chạy database quan hệ mà không phải tự quản toàn bộ máy chủ, bản vá và backup.

Luồng database:

Managed database / storage / backup

1. RDS quản gì, bạn quản gì?

RDS hỗ trợ các engine như MySQL, PostgreSQL, MariaDB, Oracle, SQL Server và Db2; Aurora là lựa chọn tương thích MySQL/PostgreSQL với kiến trúc riêng.

AWS lo provisioning, OS patching và các tính năng managed đã cấu hình.

Bạn vẫn thiết kế schema, query, index, database users, capacity, backup retention và network security.

2. Cấu hình database

Chọn engine/version, instance class, storage, subnet group, SG, parameter/option group và maintenance window.

Đặt DB ở private subnets; chỉ cho app SG vào port database.

Đổi instance class tăng CPU/RAM; thêm replica mở rộng đọc.

Storage Auto Scaling tăng disk trong maximum storage đã đặt, không tự tăng CPU và không tự giảm disk.

3. Storage Auto Scaling

RDS tăng storage khi dung lượng trống thấp kéo dài và đã đủ thời gian từ lần thay đổi trước.

Các điều kiện điển hình: còn dưới 10%, kéo dài ít nhất 5 phút, đã ít nhất 6 giờ từ lần thay đổi hoặc đã hoàn tất storage optimization, lấy mốc muộn hơn.

Đặt maximum đủ lớn và alarm theo dõi storage. Auto Scaling không thay việc dọn dữ liệu hoặc lập kế hoạch capacity.

4. RDS so với EC2 và RDS Custom

RDS thường không cho SSH vào OS. DB trên EC2 cho kiểm soát nhiều hơn nhưng bạn tự lo patching, backup và HA.

RDS Custom cho Oracle/SQL Server cần tùy biến sâu hơn ở OS/database. Thay đổi vẫn phải nằm trong phạm vi hỗ trợ và phối hợp với automation của dịch vụ.

6. Use cases

Use cases: Web cần managed PostgreSQL/MySQL: RDS. Phần mềm doanh nghiệp cần chỉnh OS: cân nhắc RDS Custom. Cần HA: thêm Multi-AZ; cần giảm tải đọc: Read Replica; cần giảm query lặp: cache.

RDS Multi-AZ & Read Replicas

Mục đích: Phân biệt giải pháp chịu lỗi với giải pháp tăng tải đọc.

Phân biệt hai nhu cầu:

Multi-AZ = chịu lỗi / failover
Read Replica = tăng tải đọc

1. So sánh chính

Tiêu chíMulti-AZ DB instanceRead Replica
Mục tiêuAvailability và automatic failoverRead scaling, reporting, có thể hỗ trợ DR
ReplicationSynchronous sang standby ở AZ khácAsynchronous, có replica lag
Standby phục vụ đọc?KhôngCó endpoint để app gửi read query
Khi primary lỗiRDS chuyển endpoint tới standbyPromote theo quy trình phù hợp, đổi endpoint app

2. Multi-AZ DB instance

Ứng dụng dùng DB endpoint ổn định. Khi primary lỗi, AWS failover sang standby; app cần retry/reconnect và xử lý transaction bị gián đoạn.

Multi-AZ trong một Region không bảo vệ sự cố cả Region và không thay backup chống xóa nhầm dữ liệu.

3. Đừng nhầm Multi-AZ DB cluster

RDS Multi-AZ DB cluster: mô hình khác: một writer và hai readable standby qua ba AZ, dùng semisynchronous replication.

Nó hỗ trợ cả HA và tải đọc; không áp dụng câu “mọi standby Multi-AZ đều không đọc được”. AWS phân biệt hai mô hình.

4. Read Replica

Replica có thể ở cùng hoặc khác Region khi engine hỗ trợ.

App phải đưa read query tới replica endpoint; query yêu cầu dữ liệu mới nhất nên dùng primary khi cần.

Promote replica tạo DB độc lập, không còn tự theo primary cũ.
Số replica và tính năng phụ thuộc engine.
Replication cùng Region được miễn phí transfer theo cơ chế RDS hỗ trợ;
cross-Region có phí transfer.

5. Use cases

Use cases: DB production cần tự failover khi AZ lỗi: Multi-AZ. Báo cáo nặng làm chậm giao dịch: Read Replica. Người dùng ở Region khác cần đọc gần hơn hoặc có DR: cross-Region replica kèm kế hoạch promote.

Amazon Aurora architecture & scaling

Mục đích: Dùng database tương thích MySQL/PostgreSQL với storage phân tán và read scaling được tích hợp.

Hai đường truy cập:

Write → Writer endpoint → Primary instance
Read → Reader endpoint → Aurora Replicas
Compute → shared distributed storage

1. Compute tách khỏi storage

Aurora cluster thường có một writer và tối đa 15 Aurora Replicas. Các instance dùng chung distributed storage; storage tự mở rộng khi dữ liệu tăng.

Storage giữ 6 bản sao qua 3 AZ và tự sửa bản sao lỗi.

Cơ chế quorum thường được mô tả là 4 bản cho ghi, 3 bản cho đọc; các bản sao storage không phải 6 database instances.

2. Writer và Reader endpoint

EndpointDùng khi
Writer/cluster endpointGhi hoặc đọc-ghi; trỏ tới writer hiện tại
Reader endpointPhân phối kết nối đọc qua replicas
Instance endpointCần một instance cụ thể
Custom endpointTách nhóm replica cho một workload

Reader endpoint cân bằng ở mức connection, không tự chia từng SQL query.

Nếu không có replica, reader endpoint có thể trỏ tới writer; không coi tên endpoint là cơ chế cưỡng chế read-only.

3. Failover

Khi writer lỗi, Aurora có thể promote replica và cập nhật writer endpoint.

Đặt replica ở AZ khác giúp khôi phục compute nhanh hơn; storage đa AZ tự nó không đảm bảo không gián đoạn kết nối.

App vẫn cần reconnect/retry. Thời gian failover thực tế phụ thuộc tình huống; không coi các con số nhanh trong slide là SLA cho mọi lỗi.

4. Auto Scaling và custom endpoint

Aurora Auto Scaling tăng/giảm số reader theo metric như CPU hoặc connections. Nó tăng capacity đọc, khác Serverless v2 điều chỉnh compute capacity của instance.

Custom endpoint có thể đưa báo cáo nặng vào nhóm replica mạnh hơn. Reader endpoint vẫn tồn tại; app chọn endpoint theo workload.

5. Use cases

Use cases: OLTP cần MySQL/PostgreSQL-compatible và HA; SaaS đọc nhiều dùng reader endpoint; tách reporting khỏi truy vấn giao dịch bằng replica/custom endpoint.

Nhớ nhanh · SAA-C03

Aurora có kiến trúc lưu trữ và replication riêng; Reader Endpoint phân phối truy vấn đọc, Writer Endpoint dành cho ghi.

Aurora Serverless, Global & advanced capabilities

Mục đích: Chọn tính năng Aurora phù hợp tải biến động, người dùng toàn cầu và môi trường dev/test.

1. Aurora Serverless v2

Serverless v2 tự điều chỉnh compute capacity theo tải trong khoảng min/max ACU
đã cấu hình.
Phù hợp tải khó đoán; vẫn cần chọn engine, network, bảo mật và giới hạn
capacity.

Khác với reader Auto Scaling: Serverless v2 đổi capacity của instance, reader Auto Scaling đổi số replica.

Khả năng scale về 0/auto-pause phụ thuộc engine version và cấu hình, không phải mặc định mọi cluster đều dừng khi rảnh.

2. Aurora Global Database

Primary Region nhận ghi; secondary Regions nhận dữ liệu bất đồng bộ để đọc gần người dùng và phục vụ DR.

Khi Region chính lỗi, failover/promote Region dự phòng theo quy trình của Global Database.

Primary Region: writer → replication → Secondary Region: local reads
                                      └─ promote/failover khi DR
Replication thường rất nhanh nhưng bất đồng bộ vẫn có nguy cơ mất thay đổi
chưa replicate.
Đánh giá RPO/RTO và thử failover; không coi Multi-AZ là thay thế cho
cross-Region DR.

3. Database Cloning

Clone dùng copy-on-write: ban đầu dùng chung các block dữ liệu, chỉ cấp block mới khi có thay đổi. Tạo môi trường test nhanh hơn sao chép toàn bộ database.

Clone có compute riêng và vẫn có chi phí; query test chạy trên clone thay vì
writer production.
Không coi clone là backup độc lập thay cho snapshot/DR.

4. Babelfish và Machine Learning

Babelfish giúp Aurora PostgreSQL hiểu một phần T-SQL/TDS để giảm công sửa app SQL Server; phải kiểm tra tính năng tương thích, không đảm bảo mọi app chạy nguyên trạng.

Aurora ML có thể gọi SageMaker/Comprehend qua SQL cho use case hỗ trợ. Đây là integration, không phải mọi database tự có model dự đoán.

5. Use cases

Use cases: Tải thất thường: Serverless v2. Local reads toàn cầu và DR: Global Database. Bản production để dev/test: clone. Migration SQL Server cần giảm thay đổi code: đánh giá Babelfish.

RDS/Aurora backup, restore, security & RDS Proxy

Mục đích: Khôi phục dữ liệu, bảo vệ kết nối và tránh database bị quá tải bởi nhiều connection.

1. Automated backup và snapshot

Automated backup kết hợp backup với transaction logs để Point-in-Time Restore (PITR) trong retention window.

RDS DB instance hỗ trợ retention tới 35 ngày; đặt 0 tắt automated backup ở mô hình cho phép.

Aurora giữ continuous backup theo retention cấu hình.

Manual snapshot giữ tới khi tự xóa.

Restore tạo DB/cluster mới, không ghi đè DB đang chạy; phải chuyển ứng dụng sang endpoint mới sau khi kiểm tra dữ liệu.

2. Restore và migration

Xóa nhầm dữ liệu → PITR tới trước sự cố → DB mới → kiểm tra → đổi endpoint app

Một số restore MySQL từ S3 dùng backup tạo bởi Percona XtraBackup, cần đúng phiên bản/format hỗ trợ. Không phải upload bất kỳ file dump nào vào S3 là restore được.

Snapshot khác read replica: replica có thể replicate cả thao tác xóa nhầm, còn backup cho phép quay lại thời điểm trước đó.

3. Network, credential và encryption

Đặt DB private, SG chỉ nhận từ app.
TLS mã hóa khi truyền; KMS mã hóa khi lưu và backup.
Muốn mã hóa DB cũ thường snapshot → encrypted copy → restore mới.

Secrets Manager lưu/rotate password; IAM DB authentication dùng token cho DB user được cấu hình trên engine hỗ trợ.

Quyền quản lý RDS API không tự cấp quyền chạy SQL trong DB.

4. RDS Proxy

Proxy pool/reuse connection, hữu ích khi Lambda/ứng dụng mở nhiều connection ngắn.

Proxy nằm trong VPC, giúp giảm connection storm và cải thiện xử lý failover; không cache kết quả SQL hay làm query nặng tự nhanh hơn.

Lambda/EC2 → RDS Proxy → connection pool → RDS/Aurora

Có thể dùng password với Secrets Manager hoặc IAM authentication theo cấu hình hỗ trợ.

IAM không luôn bắt buộc cho client; end-to-end IAM cũng có thể bỏ lưu password trong Secrets Manager. AWS RDS Proxy authentication.

5. Event vận hành và event dữ liệu

RDS Event Notifications/EventBridge báo sự kiện DB như failover, tạo snapshot hoặc đổi trạng thái; không phải stream thay đổi từng row.

Một số engine hỗ trợ gọi Lambda từ SQL/DB logic.
Cần cả IAM permission và đường mạng tới Lambda; DB private có thể dùng NAT/VPC
Endpoint phù hợp.
Cần CDC thì dùng công cụ/luồng CDC, không dựa vào thông báo lifecycle.

6. Use cases

Use cases: Khôi phục xóa nhầm: PITR. Lambda mở quá nhiều kết nối: RDS Proxy. Bảo mật DB: private subnet + SG + TLS + KMS + quản lý secret. Cảnh báo failover: RDS event → SNS/EventBridge.

Amazon ElastiCache

Mục đích: Giữ dữ liệu thường dùng trong RAM để phản hồi nhanh và giảm số lần phải hỏi database.

1. Cache-aside

App → cache: có dữ liệu → trả kết quả
          └─ chưa có → đọc DB → ghi cache với TTL → trả kết quả
Ứng dụng phải thêm logic đọc/ghi cache; ElastiCache không tự đứng trước
database như RDS Proxy.
Chọn TTL và invalidation để không trả dữ liệu cũ quá lâu.

Write-through cập nhật cache cùng khi ghi DB, giúp dữ liệu sẵn để đọc nhưng tăng công việc ghi và có thể cache dữ liệu không ai dùng.

Cache-aside chỉ nạp khi cần nhưng lần đọc đầu có cache miss.

2. Redis/Valkey và Memcached

Lựa chọnĐiểm chính
Redis OSS/ValkeyData structures, sorted sets, replication/read replicas, Multi-AZ failover và snapshot tùy cấu hình
Node-based MemcachedCache key-value đơn giản, sharding, multi-thread; không có native replication/failover như Redis

Node-based Memcached không có backup như Redis/Valkey; Serverless Memcached có hỗ trợ snapshot/restore.

Vì vậy cần nhìn cả engine lẫn deployment model. AWS backup support.

3. Session và leaderboard

Lưu session trong cache giúp nhiều app instance dùng chung trạng thái đăng nhập. Redis/Valkey sorted sets hợp leaderboard vì lưu điểm và truy vấn thứ hạng nhanh.

Cache đọc phổ biến giảm query lặp trên RDS.

Read Replica vẫn chạy SQL trên dữ liệu DB; cache lưu kết quả/đối tượng để lấy nhanh, hai giải pháp có thể dùng cùng nhau.

4. Bảo mật và dữ liệu có thể mất

Dùng private network, SG giới hạn nguồn, TLS và authentication phù hợp engine/version: AUTH/RBAC hoặc IAM authentication khi hỗ trợ.

IAM quản lý cluster và IAM data authentication là các quyền/cấu hình khác nhau.

Thiết kế để chịu cache miss hoặc cache mất dữ liệu; với dữ liệu cần bền vững, phải có nguồn dữ liệu/backup đáp ứng yêu cầu.

Replica bất đồng bộ không đảm bảo không mất mọi write khi lỗi.

5. Use cases

Use cases: Product catalog đọc nhiều: cache-aside. Web nhiều EC2 cần session chung: Redis/Valkey. Xếp hạng game: sorted sets. Cache đơn giản tái tạo được: Memcached.
