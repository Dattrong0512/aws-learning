Disaster Recovery: RPO, RTO & recovery strategies

Mục đích: Chuẩn bị cách khôi phục data + application khi xảy ra sự cố lớn.

DR thường cân bằng: RPO + RTO + Cost

1. RPO vs RTO

RPO = Recovery Point Objective = chấp nhận mất tối đa bao nhiêu dữ liệu.

Ví dụ:

Backup mỗi 1 giờ
→ có thể mất tối đa gần 1 giờ data.

RTO = Recovery Time Objective = chấp nhận hệ thống down tối đa bao lâu.

Disaster lúc 10:00
App hoạt động lại 10:30

→ RTO = 30 phút

Recovery Point

↓
RTO

RPO = mất bao nhiêu data. RTO = down bao lâu.

AWS Backup & Backup Vault Lock

Mục đích: Quản lý và tự động hóa backup cho nhiều AWS services bằng một chính sách tập trung.

Resources → Backup Plan → Backup Jobs → Backup Vault → Recovery Points

1. AWS Backup hỗ trợ gì?

  • Scheduled/on-demand backup: backup theo lịch hoặc chạy ngay; chọn resource bằng ID hoặc tag.
  • Retention và lifecycle: quy định giữ backup bao lâu, khi nào chuyển cold storage nếu resource hỗ trợ.
  • Resource thường gặp: EC2/EBS, RDS/Aurora, S3, DynamoDB, EFS, FSx, DocumentDB/Neptune. Khả năng PITR, cold storage và copy khác nhau theo service.

2. Plan, Vault và Recovery Point

  • Backup Plan = chính sách. Cấu hình frequency, backup window, lifecycle, retention và resource assignment.
  • Backup Vault = nơi quản lý bản backup. Recovery Point = bản có thể dùng để restore.
  • Backup thường xuyên hơn tạo recovery points gần nhau hơn, giúp giảm RPO; vẫn cần test restore để kiểm tra RTO và khả năng phục hồi.
Plan: mỗi 12 giờ · giữ 30 ngày · áp dụng tag Backup=Daily
↓
Resources được chọn → Recovery Points trong Vault

3. Copy sang Region hoặc account khác

  • Cross-Region: copy backup sang Region khác để phục hồi khi Region nguồn gặp sự cố.
  • Cross-account: copy sang backup account để tăng isolation khi production account bị compromise.
  • Cần đúng vault policy, IAM/service role và KMS permissions; kiểm tra resource có hỗ trợ kiểu copy đó.

4. PITR

Point-In-Time Recovery = restore về thời điểm cụ thể trong khoảng được hỗ trợ. Chỉ áp dụng cho supported services, không tự có cho mọi resource.

10:36: dữ liệu còn tốt
↓
10:37: lỗi xảy ra
↓
PITR về 10:36 nếu nằm trong recovery window

5. Backup Vault Lock

WORM = Write Once Read Many. Vault Lock bảo vệ recovery points khỏi xóa hoặc thay retention trái chính sách.

  • Governance mode: người có permission phù hợp vẫn có thể thay đổi/gỡ lock.
  • Compliance mode: sau grace period, lock không thể thay đổi/gỡ; kể cả root không bypass retention.
  • Lock không chứng minh backup sạch. Dữ liệu đã bị ransomware phá hoại vẫn có thể được backup và lock; cần nhiều recovery points, retention phù hợp và restore testing.

6. Use cases

Use cases:

  • Gắn tag cho EC2/EBS/RDS để một plan quản lý backup toàn bộ môi trường.
  • DR: giữ bản copy ở Region khác; tăng isolation bằng backup account riêng.
  • Compliance/ransomware: Vault Lock giữ bản backup đến hết retention, chọn recovery point trước incident khi restore.

VMware workload → VMware Cloud on AWS

Bảng nhớ nhanh AWS Backup — SAA-C03

Mục đích: So sánh các cơ chế backup và bảo vệ dữ liệu để chọn đúng cách khôi phục theo dịch vụ, thời điểm và retention.

1. Backup dữ liệu gì?

Service / cơ chếDữ liệuChức năng / khi chọn
RDS Automated BackupsRDS databaseBackup tự động + transaction logs; hỗ trợ PITR tối đa 35 ngày khi bật
Aurora Automated BackupsAurora clusterContinuous, incremental backup; PITR tối đa 35 ngày; luôn bật
RDS / Aurora Manual SnapshotDatabaseBản tại một thời điểm, giữ đến khi chủ động xóa
Amazon Data Lifecycle Manager (DLM)EBS volumes / EBS-backed AMIsTạo, giữ và xóa EBS snapshots/AMIs theo lịch
EBS SnapshotEBS volumeBackup incremental; restore thành EBS volume mới
AWS BackupEBS, RDS, Aurora, EFS, DynamoDB, FSx, S3…Quản lý tập trung: schedule, retention, cross-Region/cross-account copy khi resource hỗ trợ
AWS Backup Continuous BackupTài nguyên hỗ trợ như RDS, Aurora, S3PITR trong recovery window được cấu hình; không áp dụng cho mọi resource
S3 VersioningS3 objectsGiữ nhiều versions; phục hồi khi ghi đè/xóa nhầm nếu version cần dùng vẫn còn
S3 Replication (SRR/CRR)S3 objectsSao chép sang bucket cùng Region hoặc khác Region
S3 Object LockS3 object versionsWORM: chống xóa/sửa version trong retention; governance có quyền bypass phù hợp
DynamoDB PITRDynamoDB tableContinuous backup; restore về thời điểm trong tối đa 35 ngày thành table mới
DynamoDB On-Demand BackupDynamoDB tableTạo full backup khi cần, giữ đến khi xóa
EFS Automatic BackupEFS file systemAWS Backup tự backup theo policy đã cấu hình

Replication có thể truyền thay đổi/xóa theo cấu hình, nên vẫn cần backup/version history để quay về trước lỗi. Object Lock bảo vệ versions; không tự tạo một bản backup độc lập.

2. Retention và đặc điểm

Loại backupRetention / đặc điểm
RDS AutomatedDB instance: 0–35 ngày, 0 là tắt; Multi-AZ DB cluster: 1–35 ngày
Aurora Automated1–35 ngày; không thể tắt automated backups
DynamoDB PITRRecovery window 1–35 ngày, mặc định 35 khi bật
RDS / Aurora Manual SnapshotGiữ đến khi xóa
EBS SnapshotIncremental; giữ đến khi xóa hoặc lifecycle policy xử lý
AWS Backup ContinuousPITR tối đa 35 ngày; tùy service và retention đã cấu hình
AWS Backup PeriodicRetention theo backup plan; hỗ trợ lưu dài hạn, khả năng cold storage tùy resource

AWS Backup continuous hỗ trợ RDS instances/Aurora phù hợp, nhưng không hỗ trợ RDS Multi-AZ DB clusters. Copy continuous backup sang Region/account khác tạo snapshot copy, không giữ cửa sổ PITR của bản nguồn.

3. Use cases

Use cases:

  • Xóa nhầm dữ liệu database: PITR về trước lỗi nếu còn trong recovery window.
  • Backup EBS hằng ngày và giữ 7 ngày: DLM; nhiều dịch vụ/accounts cần quản lý chung: AWS Backup.
  • Lưu bản database nhiều tháng/năm: manual snapshot hoặc periodic backup có retention phù hợp.
  • S3 bị ghi đè: khôi phục version cũ; cần chống xóa version theo retention: Object Lock với mode phù hợp.
