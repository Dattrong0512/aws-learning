AWS CloudFormation

Mục đích: Viết hạ tầng AWS thành code để tạo/update resource tự động, thay vì cấu hình thủ công trên Console.

YAML / JSON Template
↓
CloudFormation
↓
Stack
↓
AWS Resources

Template và Stack

Template = file YAML/JSON mô tả hạ tầng cần tạo.

Ví dụ:

VPC · EC2 · ALB · RDS

Stack = các resource thật được CloudFormation tạo từ template.

Có thể dùng cùng template cho: Dev · Test · Prod

Các phần hay gặp:

  • Resources = resource cần tạo

  • Parameters = input

  • Outputs = output, ví dụ endpoint

  • Conditions = điều kiện có tạo resource hay không

Change Set và Rollback

Change Set = xem trước CloudFormation sẽ:

Add · Modify · Delete · Replace

resource nào trước khi update.

Rollback = nếu update lỗi, CloudFormation cố đưa stack về trạng thái trước.

Rollback không phải backup dữ liệu.

DeletionPolicy

  • Retain = xóa stack nhưng giữ resource

  • Snapshot = tạo snapshot trước khi xóa nếu resource hỗ trợ

StackSets

= triển khai cùng một CloudFormation template tới:

Nhiều AWS Accounts · + · Nhiều Regions

Phù hợp với AWS Organizations / multi-account.

Drift Detection

Drift = resource thật bị sửa khác với template.

Ví dụ:

Template:
SG allow 443

Ai đó sửa Console:
SG allow 22

→ Drift

Drift Detection giúp phát hiện sự khác biệt đó.

Infrastructure Composer và Service Role

Infrastructure Composer = giao diện trực quan để thiết kế CloudFormation template.

Service Role = IAM Role mà CloudFormation dùng để:

Create · Update · Delete

AWS resources.

Nhớ nhanh

  • CloudFormation = Infrastructure as Code
  • Template = bản thiết kế YAML/JSON
  • Stack = resources được tạo từ template
  • Change Set = xem trước thay đổi
  • Rollback = update lỗi → quay lại trạng thái trước
  • StackSets = deploy nhiều account/Region
  • Drift Detection = phát hiện resource bị sửa khác template

Câu nhớ: Template → CloudFormation → Stack → AWS Resources

Amazon SES & Amazon Pinpoint

Mục đích:

  • SES = gửi/nhận email cho application
  • Pinpoint = trong tài liệu cũ, dùng để chia nhóm khách hàng và chạy campaign
SES
= Email service

Pinpoint
= Customer segment + Campaign

Amazon SES

SES = Simple Email Service

Dùng để application gửi email như:

  • xác nhận đăng ký
  • reset password
  • hóa đơn
  • newsletter

Flow:

Application / Lambda
↓
SES API / SMTP
↓
Email
↓
User

SES giúp không cần tự vận hành mail server.

SES không phải Gmail/Outlook có giao diện inbox cho người dùng.

Verified Identity và Sandbox

Muốn gửi email bằng SES phải verify:

  • email address
  • hoặc domain

Sandbox = chế độ giới hạn ban đầu.

Trong sandbox thường chỉ gửi được tới:

  • email/domain đã verify
  • mailbox simulator

Khi có Production Access:

  • không cần verify người nhận
  • vẫn phải verify sender

Sender luôn cần Verified Identity.

Amazon Pinpoint

Trong tài liệu cũ: Pinpoint = dùng để:

  • chia nhóm khách hàng (segments)
  • tạo chiến dịch (campaigns)
  • tạo customer journeys
  • theo dõi engagement

Ví dụ:

Khách hàng chưa mua hàng
↓
Segment
↓
Campaign giảm giá
↓
Email / SMS / Push

Khác nhau:

SES
= gửi email

Pinpoint
= chọn nhóm khách hàng + chạy campaign

Pinpoint trong tài liệu này chủ yếu cần nhớ để phân biệt vai trò với SES.

Nhớ nhanh

  • SES = gửi/nhận email cho application
  • Verified Identity = verify sender email/domain
  • Sandbox = chế độ giới hạn trước Production Access
  • Pinpoint = customer segment + campaign + engagement

Câu nhớ: SES = gửi email, Pinpoint = chọn ai để gửi và chạy chiến dịch.

6. Automation

Automation Runbook là kịch bản tự động hóa gồm nhiều bước do AWS Systems Manager Automation thực hiện theo trình tự/luồng đã định để quản lý tài nguyên AWS.

Thay vì admin thao tác thủ công từng bước, runbook tự chạy cả quy trình; có thể gọi AWS API, chạy script, chờ hoặc yêu cầu approval.

7. State Manager

= giữ máy ở desired configuration.

Ví dụ muốn mọi EC2 luôn có CloudWatch Agent:

Desired:
CloudWatch Agent phải được cài

Actual:
EC2 chưa có Agent

→ đưa máy về trạng thái mong muốn

State Manager = đảm bảo cấu hình của máy luôn đúng như mong muốn.

8. Điều kiện vận hành

Execution role của Automation phải có quyền ở từng dịch vụ đích; không phải mọi bước đều cần SSM Agent trên máy. Session Manager có thể ghi logs vào S3/CloudWatch Logs khi cấu hình, nhưng nội dung SSH tunnel/port forwarding không được ghi theo cách này.

Run Command hỗ trợ giới hạn concurrency/ngưỡng lỗi; Patch Manager không dùng để nâng major version OS.

9. Use cases

Use cases: Runbook tạo AMI, cập nhật cấu hình và xác minh EC2; Maintenance Window chọn giờ chạy; State Manager giữ CloudWatch Agent luôn được cài.

Nhớ nhanh · SAA-C03

Systems Manager quản vận hành fleet: Run Command thực thi lệnh; Patch Manager vá máy; Session Manager truy cập không cần mở SSH.

AWS Cost Explorer, Budgets & Cost Anomaly Detection

Mục đích: Theo dõi chi phí, đặt ngân sách và phát hiện chi tiêu bất thường.

Cost Explorer
= tiền đã chi vào đâu?

Budgets
= có vượt mức đã đặt không?

Cost Anomaly Detection
= chi phí có bất thường không?

1. Cost Explorer

Cost Explorer = xem và phân tích chi phí AWS.

Có thể filter/group theo:

  • Service

  • Account

  • Region

  • Tags

Ví dụ:

Bill tăng
↓
Cost Explorer
↓
EC2 tăng?
Data Transfer tăng?
S3 tăng?

Có Forecast để dự đoán chi phí tương lai dựa trên dữ liệu trước đó.

Cost Explorer = phân tích chi phí và xu hướng.

2. Savings Plans Recommendations

Cost Explorer có thể phân tích usage và:

gợi ý Savings Plans

để giảm chi phí nếu workload dùng ổn định.

Có:

  • Coverage = bao nhiêu usage được Savings Plan cover

  • Utilization = phần đã cam kết được sử dụng bao nhiêu

Đây chỉ là recommendation, không tự mua Savings Plan.

3. AWS Budgets

Budgets = đặt ngưỡng chi phí/usage và cảnh báo khi gần hoặc vượt mức.

Ví dụ:

Monthly Budget = $500

Forecast > $500
↓
Send Alert

Có thể alert theo:

  • Actual cost

  • Forecast cost

Lưu ý:

Budget không tự chặn chi phí chỉ vì bạn tạo budget.

Có thể cấu hình Budget Actions để thực hiện một số hành động khi đạt ngưỡng.

4. Cost Anomaly Detection

Cost Anomaly Detection = dùng machine learning để phát hiện chi phí tăng bất thường.

Ví dụ:

Data Transfer bình thường = $20/day

Hôm nay = $150/day
↓
Anomaly Detection
↓
Alert

Khác Budget:

Budget
= vượt ngưỡng mình đặt?

Anomaly Detection
= khác bất thường so với pattern bình thường?

Có thể phát hiện bất thường ngay cả khi tổng chi phí chưa vượt budget.

5. AWS Compute Optimizer

AWS Compute Optimizer phân tích cấu hình và utilization metrics để đề xuất rightsizing, tránh cấp dư tài nguyên hoặc cải thiện hiệu suất. Cần opt in và có đủ dữ liệu metrics.

EC2 m5.2xlarge ít được sử dụng
↓ CPU / memory nếu có / network / IOPS / throughput
Compute Optimizer
↓ recommendation minh họa: m5.large nếu đáp ứng workload
Review peak load và yêu cầu ứng dụng
↓
Thay cấu hình để giảm chi phí

CPU trung bình 10% chưa đủ để khẳng định nên đổi instance type cụ thể. Compute Optimizer chủ yếu đưa ra đề xuất, không mặc định tự resize EC2/EBS.

ResourceĐề xuất
EC2Instance type/size phù hợp
Auto Scaling GroupRightsizing compute của ASG
EBSVolume type, IOPS, throughput
LambdaMemory phù hợp
ECS FargateCPU và memory
RDS / AuroraCấu hình database phù hợp
DynamoDB, NAT Gateway, ElastiCacheTối ưu theo khả năng và điều kiện của từng resource được hỗ trợ

EC2 memory metrics phải được cung cấp qua agent hoặc nguồn được hỗ trợ.

AWS Outposts

Mục đích: Đưa hạ tầng AWS xuống datacenter của doanh nghiệp để chạy workload tại chỗ nhưng vẫn dùng cách quản lý quen thuộc của AWS.

AWS Region
↕ Service Link
AWS Outposts tại Datacenter
↓
Local Workloads

AWS Outposts là gì?

Outposts = phần cứng AWS được đặt ngay tại datacenter của bạn.

Có thể chạy một số AWS resources được hỗ trợ ngay tại on-prem.

Phù hợp khi cần:

  • low latency với hệ thống local

  • xử lý/lưu dữ liệu tại địa điểm cụ thể

  • vẫn muốn dùng AWS tools/API

Không phải mọi AWS service đều chạy được trên Outposts.

Kết nối với AWS Region

Outposts vẫn kết nối về AWS Region cha thông qua:

Service Link

Outposts
↓ Service Link
AWS Region

Service Link dùng cho traffic quản lý và kết nối với AWS Region.

Outposts không phải một AWS cloud độc lập hoàn toàn offline.

Trách nhiệm

AWS = quản lý hạ tầng Outposts.

Doanh nghiệp = chuẩn bị:

  • datacenter

  • điện

  • làm mát

  • network

  • application/data

IAM, Security Group và encryption vẫn cần cấu hình bình thường.

Outposts vs Direct Connect vs Storage Gateway

ServiceDùng để làm gì?
OutpostsChạy AWS compute/resources ngay tại datacenter
Direct ConnectĐường mạng riêng từ on-prem tới AWS
Storage GatewayKết nối storage on-prem với AWS storage

Nhớ:

Outposts
= AWS chạy tại On-Prem

Direct Connect
= kết nối On-Prem ↔ AWS

Storage Gateway
= nối Storage On-Prem ↔ AWS

Nhớ nhanh

  • AWS Outposts = mang hạ tầng AWS xuống datacenter
  • Use case chính = low latency + yêu cầu data/local processing
  • Service Link = kết nối Outposts về AWS Region
  • Outposts ≠ Direct Connect = Outposts có compute tại chỗ; DX chỉ là đường mạng

Câu nhớ: Outposts = AWS infrastructure chạy ngay trong datacenter của bạn.

AWS Batch

Mục đích: Chạy batch jobs số lượng lớn mà không phải tự quản lý server/scheduler.

Job Definition
↓
Submit Job
↓
Job Queue
↓
Scheduler
↓
Compute Environment
↓

Thành phần chính

Job Definition = cấu hình job sẽ chạy như thế nào:

  • Container image
  • Command
  • CPU / RAM
  • IAM Role
  • Job = một lần chạy cụ thể.
  • Job Queue = hàng đợi chứa các job chưa chạy.
  • Compute Environment = tài nguyên dùng để chạy job, thường là:
  • EC2
  • Fargate

↓

↓
Job Queue
↓
AWS Batch tự cấp compute
↓

↓

AWS Batch = Queue + Scheduler + Compute cho batch jobs.

Batch vs Lambda vs Fargate

  • AWS Batch = điều phối nhiều batch jobs, phù hợp job nặng/chạy lâu.
  • Lambda = event-driven function, phù hợp tác vụ ngắn; Lambda thông thường tối đa 15 phút.
  • Fargate = nơi chạy container mà không quản lý server; có thể làm compute bên dưới AWS Batch.
Batch
= quản lý job / queue / scheduling

Fargate
= cung cấp compute để container chạy

IAM

Job Role = quyền của code bên trong container.

Ví dụ:

Batch Job
↓ Job Role
S3 Read / Write

Quyền submit Batch job không có nghĩa container tự có quyền truy cập S3.

Nhớ nhanh

  • AWS Batch = chạy và điều phối batch jobs
  • Job Definition = job chạy như thế nào
  • Job Queue = job đang chờ
  • Compute Environment = EC2/Fargate dùng để chạy job
  • Spot = tiết kiệm cho job chịu được interruption

Câu nhớ: Job Definition → Queue → Compute → Container chạy.

Multi-Node Parallel (MNP) & Batch Scheduling Policy vs EventBridge Scheduler

Cơ chế trên AWS BatchChức năng & Giới hạn cần nhớ
Multi-Node Parallel (MNP)Cho phép một job HPC/ML lớn chạy đồng thời trên nhiều EC2 nodes phối hợp qua MPI (main node điều phối các child nodes); không hỗ trợ trên Fargate
AWS Batch Scheduling PolicyPhân bổ công bằng (fair-share) và ưu tiên tài nguyên giữa các nhóm job đang nằm trong Job Queue (không phải bộ hẹn giờ cron)
Amazon EventBridge SchedulerQuyết định thời điểm kích hoạt chạy job định kỳ (ví dụ mỗi ngày lúc 08:00 sáng gửi job vào AWS Batch hoặc ECS)

  • KMS

Nếu destination là S3/Redshift thì vẫn cần permission phù hợp.

PrivateLink chỉ áp dụng khi connector hỗ trợ.

AppFlow vs Glue vs DMS

  • AppFlow = SaaS integration đơn giản
  • Glue = ETL / transform data phức tạp hơn
  • DMS = migrate/replicate database

Ví dụ:

↓ AppFlow
S3
↓ Glue
Transform Data

Nhớ nhanh

  • AppFlow = SaaS ↔ AWS data transfer
  • Trigger = On Demand / Schedule / Event
  • Incremental = chỉ lấy data mới/thay đổi
  • Glue = xử lý/ETL sâu hơn
  • DMS = database migration/replication

Câu nhớ: AppFlow = nối SaaS với AWS để chuyển data bằng flow được quản lý.

Amazon EventBridge Scheduler

Mục đích: Chạy task theo thời gian/lịch mà không cần tự duy trì cron server.

Rate / Cron / One-time
↓
EventBridge Scheduler
↓
Execution Role
↓
Target

Các kiểu schedule

Rate = lặp sau một khoảng thời gian.

Ví dụ:

rate(5 minutes)

Cron = chạy theo lịch cụ thể.

Ví dụ:

Mỗi ngày 08:00

One-time = chạy đúng một lần tại thời điểm đã đặt.

Rate = mỗi bao lâu, Cron = lúc nào theo lịch, One-time = chạy một lần.

Target và Execution Role

Scheduler có thể gọi:

  • Lambda
  • SQS
  • Step Functions
  • nhiều AWS APIs khác

Flow:

Đến giờ
↓
Scheduler assume Execution Role
↓
Gọi Target

Execution Role phải có quyền phù hợp như:

  • invoke Lambda
  • send message SQS
  • start Step Functions

Retry và DLQ

Nếu gọi target thất bại:

Scheduler
↓
Retry
↓ vẫn fail
SQS DLQ

Retry = thử lại.

DLQ = giữ event thất bại để xử lý sau.

Target nên xử lý idempotent vì retry có thể gọi trùng.

Scheduler vs EventBridge Event Bus

Scheduler = trigger theo thời gian

Ví dụ:

Mỗi đêm 01:00
↓
Run Lambda

EventBridge Event Bus = trigger theo event

Ví dụ:

EC2 state changed
↓
EventBridge Rule
↓
Lambda

Nhớ nhanh

EventBridge Scheduler = cron/rate/one-time managed service

Rate = lặp theo khoảng thời gian

Cron = lịch cụ thể

  • One-time = chạy một lần
  • Execution Role = quyền để Scheduler gọi target
  • Retry + DLQ = xử lý lỗi delivery

Câu nhớ: Scheduler = chạy theo giờ, Event Bus = chạy theo event.
