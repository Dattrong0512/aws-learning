AWS Organizations & Service Control Policies (SCP)

Mục đích: AWS Organizations dùng để quản lý nhiều AWS accounts trong cùng một tổ chức, giúp tách workload, billing và quyền quản trị.

AWS Organizations = Multi-Account Management + Consolidated Billing + OU + SCP

1. Management Account & Member Account

Management Account = account quản lý Organization

Member Account = các account thành viên

Ví dụ:

Management Account
├── Dev Account
├── Test Account
├── Prod Account
└── Finance Account

Một member account chỉ thuộc một Organization tại một thời điểm.

2. Vì sao dùng nhiều Account?

Thay vì:

1 AWS Account
├── Dev
├── Test
├── Prod
└── Finance

tách thành: Dev Account · Test Account · Prod Account · Finance Account

Giúp: Tách quyền · Tách billing · Tách workload · Giảm blast radius

Dev gặp security issue
↓
giảm nguy cơ ảnh hưởng trực tiếp Prod

3. Consolidated Billing

Organizations có thể gom chi phí nhiều account:

4. Organizational Unit - OU

OU = nhóm các AWS accounts có cùng policy/governance.

Organization Root
├── Development OU
│   ├── Dev Account A
│   └── Dev Account B
│

    └── Finance Account

↓

↓

↓

OU = nhóm account để quản policy, không phải network/VPC.

5. Service Control Policy - SCP

SCP = giới hạn quyền tối đa mà account được phép dùng.

SCP = Maximum Permission Boundary ở cấp Organization

Quan trọng: SCP ≠ cấp quyền

SCP = giới hạn quyền

IAM · Allow s3:*

nhưng SCP: Deny s3:*

S3 ❌

Explicit Deny trong SCP thắng IAM Allow.

8. Blocklist Strategy

↓

9. Allowlist Strategy

Chỉ Allow những service cần dùng

EC2 ✅ · CloudWatch ✅ · S3 ❌ · Lambda ❌ · DynamoDB ❌

Allowlist = chỉ cho những gì được liệt kê.

IAM policy evaluation, boundaries & cross-account access

Mục đích: Hiểu AWS kết hợp nhiều lớp policy để quyết định một request cuối cùng là Allow hay Deny.

Default = Implicit Deny

Explicit Deny = thắng mọi Allow

Ví dụ:

Deny sqs:*
+
Allow sqs:DeleteQueue
↓
DeleteQueue ❌

Chỉ cần có Explicit Deny phù hợp → request bị chặn.

1. Các loại Policy chính

Identity-based Policy = gắn vào User / Group / Role = principal được làm gì

Resource-based Policy = gắn vào resource = ai được truy cập resource

Ví dụ resource policy: S3 Bucket Policy · SQS Queue Policy · SNS Topic Policy · Lambda Resource Policy

2. SCP, Boundary, Session Policy

  • SCP = giới hạn quyền tối đa ở Organization / OU / Account
  • Permission Boundary = giới hạn quyền tối đa của IAM User / Role
  • Session Policy = thu hẹp quyền của temporary session

Quan trọng: SCP / Boundary / Session Policy ≠ tự cấp quyền

Chúng chỉ giới hạn quyền

3. Effective Permission

Có thể nhớ đơn giản:

Identity Allow
∩
Permission Boundary
∩
SCP
∩
Session Policy (nếu có)
↓
Effective Permission

và:

Explicit Deny
→ DENY ngay
Identity Policy:
Allow iam:CreateUser

Boundary:
Allow s3:*
Allow ec2:*

↓
Không có phần giao
↓
CreateUser ❌

Boundary Allow một service không có nghĩa là tự cấp service đó.

4. IAM Conditions

Condition thêm context vào quyết định.

Có thể kiểm tra: MFA · IP Address · VPC Endpoint · Principal Tag · Resource Tag · Organization ID

5. ABAC

ABAC = Attribute-Based Access Control

User: · Department = Data · EC2: · Project = DataAnalytics

↓

↓

→ quản quyền dựa trên tag thay vì tạo policy riêng cho từng user.

6. MFA Condition

↓

Dù user có: Allow ec2:*

thì: Terminate EC2 ❌

vì Explicit Deny thắng.

7. S3 Bucket ARN vs Object ARN

Điểm rất hay nhầm:

s3:ListBucket
→ arn:aws:s3:::my-bucket
s3:GetObject
s3:PutObject
s3:DeleteObject
→ arn:aws:s3:::my-bucket/*

Nhớ: Bucket = bucket ARN

Object = bucket ARN + /*

Account ngoài Organization
→ ❌

→ không cần liệt kê từng AWS account trong policy.

AWS IAM Identity Center

Mục đích: AWS IAM Identity Center dùng để đăng nhập một lần và quản lý quyền truy cập tập trung cho nhiều AWS accounts và business applications.

1 User
↓
1 Login / SSO
↓
Nhiều AWS Accounts / Applications

Identity Center = central login + central access management.

1. Thay vì tạo IAM User ở từng Account

Không nên:

User Bob
├── IAM User ở Dev
├── IAM User ở Test
└── IAM User ở Prod

Với Identity Center:

Bob
↓
IAM Identity Center
↓
Dev / Test / Prod

→ quản onboarding/offboarding dễ hơn và tránh permanent IAM User/access key trong từng account.

2. Identity Source

Identity Center cần biết: User là ai? · Group nào?

Identity source có thể là: Identity Center built-in store · Active Directory · Okta · OneLogin · Other external IdP

Ví dụ:

Employee
↓
Okta
↓
IAM Identity Center
↓
AWS Accounts

3. Permission Set

Permission Set = bộ quyền được chuẩn bị sẵn để dùng trong AWS account.

ReadOnly · DeveloperAccess · DatabaseAdmin · FullAccess

Permission set có thể chứa: AWS Managed Policies · Customer Managed Policies · Inline Policy

Khi assign permission set vào account, Identity Center tạo quyền truy cập tương ứng thông qua role/session trong account đó.

4. Assignment

  • Assignment trả lời 3 câu: WHO? = User / Group
  • WHERE? = AWS Account nào?
  • WHAT? = Permission Set nào?

↓
FullAccess
Developers Group
↓
Prod Account
↓
ReadOnlyAccess

Cùng một group nhưng quyền có thể khác theo từng account.

User login vào portal:

6. Group ở Identity Center ≠ IAM Group

Identity Center Group = nhóm user để assign access nhiều account/app

IAM Group = nhóm IAM Users trong một AWS account

AWS Directory Service & Active Directory integration

Mục đích: AWS Directory Service giúp ứng dụng trên AWS sử dụng Active Directory (AD): hoặc tạo directory trên AWS, hoặc kết nối với AD công ty đã có.

AD là nơi quản lý tài khoản nhân viên, máy tính và nhóm. Khi Bob đăng nhập, AD giúp kiểm tra Bob là ai. Bob trong AD khác với IAM User trong AWS account.

1. Ba lựa chọn cần phân biệt

1.1. AWS Managed Microsoft AD

AWS tạo và quản lý hạ tầng cho một Microsoft AD chạy trên AWS. Bạn có thể tạo user, group trong AD này để ứng dụng sử dụng.

Bob được tạo trong Microsoft AD trên AWS
↓
Bob đăng nhập ứng dụng
↓
AD trên AWS xác thực Bob

Dùng khi: ứng dụng hoặc máy Windows trên AWS cần Microsoft AD.

  • Nếu công ty đã có AD ở văn phòng, có thể thiết lập trust giữa hai AD.
  • Khi đó user như Bob vẫn có thể nằm ở AD công ty và dùng danh tính đó để truy cập tài nguyên phù hợp trên AWS.

1.2. AD Connector

AD Connector là cầu nối từ AWS đến AD công ty đã có. Nó không tạo một AD mới để lưu tài khoản Bob.

Bob nằm trong AD công ty
↓
Bob đăng nhập dịch vụ AWS
↓
AD Connector chuyển yêu cầu về AD công ty
↓
AD công ty xác thực Bob

Dùng khi: công ty đã có AD và muốn dịch vụ AWS sử dụng những user đó. Tạo user hoặc đổi mật khẩu Bob vẫn thực hiện ở AD công ty.

1.3. Simple AD

Simple AD là một directory cơ bản, độc lập trên AWS. Bạn tạo và quản lý user trong Simple AD.

Bob được tạo trong Simple AD
↓
Ứng dụng trên AWS dùng tài khoản Bob

Dùng khi: workload cần chức năng directory cơ bản, nhưng không cần Microsoft AD đầy đủ hoặc kết nối với AD công ty.

Simple AD không hỗ trợ trust với AD khác và không dùng làm identity source cho IAM Identity Center.

3. Liên hệ với IAM Identity Center

Nếu dùng AD làm nguồn danh tính:

IAM Identity Center → gán Bob quyền vào Dev / Test / Prod
  • Bob có tài khoản trong AD chưa có nghĩa là được vào AWS account. Quản trị viên vẫn phải gán quyền cho Bob hoặc group của Bob trong IAM Identity Center.

4. Use cases

Use cases:

  • Migrate workload Windows/managed directory lên AWS nhưng vẫn thiết lập trust hai chiều với corporate AD.
  • Dùng AD Connector khi muốn AWS xác thực employee với on-prem AD mà không tạo bản sao directory ở AWS.
  • Dùng Simple AD cho ứng dụng AWS độc lập cần directory AD-compatible nhưng không cần liên kết on-premises.

AWS Control Tower

Mục đích: AWS Control Tower giúp thiết lập và quản trị môi trường nhiều AWS accounts theo một baseline chung. Nó dùng AWS Organizations làm nền tảng, tạo landing zone, cấp phát account và theo dõi việc tuân thủ các quy tắc.

Hãy nhớ: Control Tower là công cụ dựng và quản lý; landing zone là môi trường được dựng ra. Sau đó, khi team cần account mới, quản trị viên có thể cấp account vào môi trường này qua Account Factory.

AWS Organizations
↓
Control Tower dựng landing zone
↓
Dev / Test / Prod accounts
↓
Áp dụng controls + theo dõi compliance
  • Thay vì mỗi team tự tạo account với cấu hình riêng, quản trị viên dùng Account Factory để cấp account trong cấu trúc Organization và áp dụng baseline governance.

1. Guardrail: preventive khác detective

Preventive control chặn hành động vi phạm trước khi hành động được thực hiện. Ví dụ dùng SCP để hạn chế thao tác ở những AWS Regions không được phép.

User gọi API ở Region bị hạn chế
↓
Preventive control kiểm tra
↓
Deny

Detective control kiểm tra cấu hình sau khi resource được tạo hoặc thay đổi, thường qua AWS Config rule. Ví dụ: phát hiện resource thiếu tag.

Resource được tạo nhưng thiếu tag
↓
AWS Config đánh giá
↓
NON_COMPLIANT
LoạiCơ chế trong ví dụKết quả
PreventiveSCPChặn hành động vi phạm.
DetectiveAWS Config rulePhát hiện và báo resource không tuân thủ.

Cần ngăn việc tạo resource sai → preventive. Cần tìm resource đã sai → detective. Phát hiện vi phạm không có nghĩa hành động đã bị chặn hoặc resource đã được sửa.

2. Notification và remediation flow

Giả sử team muốn tìm resource thiếu tag:

Resource trong member account
↓
AWS Config rule đánh giá tag
↓
NON_COMPLIANT
↓
SNS thông báo cho admin
↓
Lambda thêm tag theo quy tắc đã định
↓
AWS Config đánh giá lại
  • SNS và Lambda là workflow cần cấu hình thêm. Lambda cần quyền sửa resource và phải biết tag nào là đúng; không nên tự đoán CostCenter cho resource production.
  • Preventive control hoạt động ở bước sớm hơn: nó từ chối hành động không được phép, chẳng hạn gọi API ở Region bị hạn chế, thay vì đợi AWS Config phát hiện sau đó.

LDAP, SAML 2.0, SCIM & Custom Identity Broker

Mục đích: Phân biệt vai trò từng giao thức danh tính doanh nghiệp và hai luồng đăng nhập liên kết (federation) vào AWS.

1. Bảng phân biệt LDAP, IdP, SAML 2.0, SCIM và STS

Thành phần / Giao thứcChức năng cốt lõi
LDAPGiao thức tra cứu thư mục và kiểm tra username/password trực tiếp với directory (ví dụ Active Directory)
Identity Provider (IdP)Hệ thống xác thực người dùng và phát hành bằng chứng đăng nhập liên kết (AD FS, Okta, Entra ID, Keycloak)
SAML 2.0Chuẩn truyền thông điệp xác thực (SAML Assertion) từ IdP sang AWS để đăng nhập SSO mà không cần lộ mật khẩu cho AWS
SCIMGiao thức tự động đồng bộ vòng đời Users và Groups (tạo, sửa, xóa) từ IdP vào IAM Identity Center
Custom Identity BrokerỨng dụng trung gian tự xây dựng khi hệ thống nội bộ chỉ có LDAP và không có IdP hỗ trợ SAML/OIDC
AWS STS & Federation EndpointSTS cấp temporary credentials; Federation Endpoint đổi temporary credentials thành sign-in URL vào AWS Console

2. Hai luồng xác thực liên kết cần phân biệt

Luồng A — Không có SAML (dùng Custom Identity Broker):
Employee → Custom Identity Broker → kiểm tra LDAP → gọi AWS STS lấy temporary credentials → gọi AWS Federation Endpoint → mở AWS Console

Luồng B — Có SAML 2.0 Federation (ưu tiên, không cần tự viết Broker):
Employee → IdP (xác thực với LDAP) → trả SAML Assertion → gửi tới AWS SAML Endpoint / STS (AssumeRoleWithSAML) → mở AWS Console
