5. SQS Standard Queue

Standard là lựa chọn mặc định khi không cần strict ordering.

Standard = throughput rất cao = at-least-once delivery = best-effort ordering

At-least-once nghĩa là: Một message có thể được deliver hơn 1 lần

Do đó consumer phải: Idempotent

Order ID = 123
↓ xử lý lần 1
↓ duplicate
xử lý lần 2

Consumer nên kiểm tra: Order 123 đã xử lý chưa?

để tránh charge/payment 2 lần.

Amazon Data Firehose

Mục đích: Đưa dữ liệu streaming tới storage/analytics destination bằng dịch vụ managed, không tự quản shard và consumer fleet.

1. Delivery pipeline

Producer / Kinesis Data Streams / logs
 → Firehose → buffer / optional transform → destination + backup S3 khi cấu hình

Destination gồm S3, Redshift, OpenSearch và HTTP/vendor được hỗ trợ. Delivery Redshift dùng S3 làm staging trước COPY.

2. Buffer và latency

Firehose thường gom dữ liệu theo size/time rồi delivery; phù hợp near real-time ingestion, không phải chọn mặc định cho logic phải phản ứng từng event tức thời.

Có cấu hình giảm/zero buffering ở một số destination, nhưng không biến Firehose thành replayable stream cho nhiều consumer.

Service tự quản delivery capacity; vẫn có quota và giới hạn theo source/destination.

3. Transform và format conversion

Lambda có thể biến đổi record trước delivery.

Format conversion native chuyển JSON sang Parquet/ORC cho S3, dùng schema Glue Data Catalog; CSV cần transform sang JSON trước, không tự convert trực tiếp mọi format.

Compression/columnar format giúp giảm lưu trữ và dữ liệu scan khi query. AWS Firehose format conversion.

4. Replay, backup và permission

Firehose không cung cấp retention stream cho consumer tùy ý replay như Kinesis Data Streams. Nếu cần nhiều consumer/replay, đặt KDS ở trước và Firehose là một consumer delivery.

Có retry và S3 backup cho all/failed records tùy destination/cấu hình.

Service role cần quyền source, destination, Lambda và KMS; thiết kế giám sát lỗi và reprocess dữ liệu backup.

5. Use cases

Use cases: Logs/clickstream → S3 data lake; data → Redshift/OpenSearch; Lambda transform → JSON → Parquet. Cần xử lý real-time nhiều consumer và đọc lại event: Kinesis Data Streams.

Nhớ nhanh · SAA-C03

Data Firehose được quản lý để giao stream data đến các đích lưu trữ/phân tích; không yêu cầu tự quản consumer theo shard như Data Streams.

Amazon MQ giúp chuyển ứng dụng đang dùng giao thức/broker truyền thống lên AWS; khác SNS/SQS là dịch vụ messaging AWS-native.

SQS vs SNS vs Kinesis vs Firehose vs MQ

Mục đích: Chọn messaging theo kiểu nhận dữ liệu, replay và yêu cầu tương thích của ứng dụng.

2. Queue khác stream

SQS workers thường chia nhau xử lý message; xóa message khi hoàn tất.

Kinesis giữ record trong retention window ngay cả sau khi consumer đọc, để nhiều consumer đọc độc lập hoặc replay.

SQS Standard có at-least-once/best-effort order; FIFO dùng message group/deduplication để hỗ trợ order phù hợp.

Kinesis order theo shard, không phải một thứ tự toàn cục qua mọi shard.

3. SNS + SQS

Một event → SNS ┬→ Queue A → xử lý đơn hàng
               └→ Queue B → analytics

Mỗi hệ thống có queue, retry và scale riêng.

SNS push tới queue; worker pull từ SQS.

SNS không phải thay thế mọi queue; archive/replay của SNS FIFO là tính năng riêng, không đồng nghĩa mọi SNS topic là stream như KDS.

4. Kinesis + Firehose và MQ

KDS giữ stream cho analytics/replay; Firehose đưa một nhánh tới S3/warehouse.
Chỉ cần managed delivery thì có thể dùng Firehose trực tiếp mà không thêm KDS.
MQ hợp migration app cần JMS/AMQP/MQTT/STOMP hoặc semantics broker theo
engine.
Broker có capacity hữu hạn và cần chọn deployment HA; app mới có thể dùng
SQS/SNS nếu phù hợp.

5. Use cases

Use cases: Background jobs: SQS. Một event tới nhiều hệ thống: SNS + SQS. Telemetry nhiều consumer/replay: KDS. Logs vào data lake: Firehose. Legacy broker app cần ít sửa code: MQ.
