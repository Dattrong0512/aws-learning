Amazon CloudWatch: metrics, logs, alarms & insights

Mục đích: Amazon CloudWatch dùng để monitor hệ thống AWS bằng metrics, logs, dashboard và alarms.

CloudWatch = Metrics + Logs + Dashboard + Alarms

Nó trả lời: "Hệ thống đang chạy thế nào?"

Khác với: CloudTrail = ai đã gọi AWS API nào?

1. Các nhóm chức năng và EventBridge

Nhóm chức năngDùng để làm gì?
MetricsThu thập số đo theo thời gian: CPU, latency, request count
LogsTập trung application/service logs
DashboardsHiển thị biểu đồ và trạng thái hệ thống
AlarmsTheo dõi điều kiện/trạng thái để cảnh báo hoặc gọi action
InsightsPhân tích logs và quan sát workload chuyên biệt như containers/Lambda
CloudWatch Events → Amazon EventBridgeNhận events, dùng rules lọc và chuyển tới targets như Lambda/SQS

Đây là các nhóm chức năng, không phải các loại monitoring loại trừ nhau. CloudWatch Events là tên cũ của Amazon EventBridge; alarm theo dõi metric, EventBridge định tuyến sự kiện như EC2 đổi trạng thái hoặc alarm đổi trạng thái.

2. CloudWatch Metrics

Metric = một giá trị được đo theo thời gian.

Ví dụ:

EC2 / Lambda / RDS...
↓
Metrics
↓
CloudWatch
↓
Dashboard / Alarm

3. Namespace & Dimension

3.1. Namespace

Dùng để nhóm metrics theo service/application.

AWS/EC2 · AWS/Lambda · AWS/RDS

3.2. Dimension

Dùng để xác định metric thuộc resource nào.

Metric = CPUUtilization

Dimension = InstanceId = i-123456

→ cùng là CPUUtilization nhưng mỗi EC2 có time series riêng.

Amazon EventBridge

Mục đích: Amazon EventBridge là serverless event bus dùng để nhận event, lọc event và tự động gửi event tới service khác.

EventBridge = nhận event + filter event + route event tới target

"Có chuyện gì xảy ra"
↓
EventBridge phát hiện
↓
"Thì làm việc gì đó"

1. Flow cơ bản

Event Source
↓
EventBridge Bus
↓
Rule
↓
Target

Ví dụ:

EC2 bị Stop
↓
EventBridge
↓
Rule match
↓
Lambda / SNS / SQS

Rule quyết định khi nào chạy, Target mới là service thực sự làm việc.

2. Event Source

EventBridge có thể nhận event từ: AWS Services · SaaS Applications · Custom Applications · CloudTrail

EC2 state change · S3 event · CodeBuild failed · CloudTrail API call · Custom application event

3. Rule

Rule có 2 kiểu chính:

3.1. Event Pattern

Chạy khi một event phù hợp điều kiện.

Rule kiểm tra JSON
↓
Match?
↓
Target

↓
EventBridge Rule
↓
SNS Alert

Chạy theo thời gian.

↓
EventBridge
↓
Lambda
00:00 mỗi ngày
↓
EventBridge
↓

4. Target

Target là service xử lý event sau khi rule match.

Có thể là: Lambda · SQS · SNS · Step Functions · ECS · AWS Batch · Kinesis · CodePipeline · CodeBuild · SSM

↓

↓
SQS
↓

1. CloudTrail vs CloudWatch

CloudTrail = ai đã làm gì trên AWS?

CloudWatch = hệ thống đang hoạt động thế nào?

EC2 bị xóa
→ CloudTrail

CPU EC2 = 95%
→ CloudWatch

5. Các loại Event

AWS Config & compliance automation

Mục đích: AWS Config dùng để theo dõi configuration của AWS resource theo thời gian và kiểm tra resource có tuân thủ rule hay không.

AWS Config = Configuration History + Compliance Check

Nó trả lời: Resource đang cấu hình thế nào? · Trước đây cấu hình ra sao? · Có compliant với rule không?

1. Ví dụ dễ hiểu

Bạn có rule: Security Group · không được mở SSH 22 cho 0.0.0.0/0

Nếu có SG: Port 22 · Source = 0.0.0.0/0

Config đánh giá: NON_COMPLIANT ❌

Nếu chỉ cho IP công ty: Port 22 · Source = Company IP

→

COMPLIANT ✅

Config = kiểm tra cấu hình có đúng policy không.

2. AWS Config theo dõi gì?

Ví dụ:

Security Group · S3 Bucket · EC2 · EBS · ALB · IAM · ...

Có thể biết: Configuration hiện tại · Configuration trước đây · Thời điểm configuration thay đổi · Compliance status

3. Resource Timeline

Config lưu lịch sử thay đổi của resource.

10:00 · S3 Bucket = Private · 11:00 · S3 Bucket = Public · 12:00 · S3 Bucket = Private

Config Timeline giúp xem: Resource thay đổi lúc nào · Configuration trước/sau · Compliance thay đổi thế nào

Có thể liên kết với CloudTrail để xem API call nào gây ra thay đổi.

4. Config Rules

Rule dùng để kiểm tra configuration.

S3 Bucket
→ không được Public

Security Group
→ không mở SSH toàn Internet

ALB
→ phải có SSL Certificate

Có 2 loại: AWS Managed Rule = AWS làm sẵn

Custom Rule = logic riêng của bạn = thường dùng Lambda

AWS X-RayTruy vết phân tán (Distributed Tracing): ghi segments/subsegments và dựng Service Map đầu-cuối để khoanh vùng chính xác service gây nghẽn cổ chai hoặc lỗi 4xx/5xxTích hợp API Gateway, Lambda, ECS, EC2, SQS, SNS, DynamoDB, RDS; bật qua IaC (TracingConfig: Active trên Lambda, TracingEnabled: true trên API Gateway) kèm quyền IAM ghi trace
Amazon Managed GrafanaDashboard quan sát trực quan hoàn toàn managed (không cần tự vận hành máy chủ Grafana)Truy vấn đồng thời từ CloudWatch, Managed Prometheus, X-Ray, OpenSearch, Timestream, Athena, RDS; đăng nhập SSO qua IAM Identity Center
