High availability & Elastic Load Balancing

Mục đích: Chia request tới nhiều máy và giữ ứng dụng hoạt động khi một máy hoặc AZ gặp lỗi.

1. Scalability và High Availability

Vertical scaling là đổi sang máy mạnh hơn/yếu hơn. Horizontal scaling là thêm/bớt máy. High Availability (HA) là có tài nguyên dự phòng và cơ chế chuyển sang tài nguyên còn khỏe.

Một máy lớn giúp tăng capacity nhưng vẫn là điểm lỗi duy nhất. Với web app, thường dùng load balancer và ASG qua nhiều AZ.

2. Load Balancer làm gì?

Load balancer nhận connection từ client rồi chuyển tới target phía sau.

ELB: dịch vụ managed: AWS vận hành hạ tầng load balancer, bạn cấu hình listener, target và health check.

Client → Route 53 → Load Balancer
                    ├─ healthy target ở AZ A
                    └─ healthy target ở AZ B

Internet-facing load balancer nhận traffic từ Internet; internal load balancer phục vụ kết nối trong mạng private.

Client thường dùng DNS name, không cố định IP của ALB.

3. Health check và capacity còn lại

Health check giúp tránh gửi traffic tới target lỗi trong hoạt động bình thường.

Khi một AZ mất, AZ còn lại phải đủ capacity; ELB không tự tạo thêm EC2 nếu không có ASG/cơ chế scale.

Database, file và session cũng cần thiết kế chịu lỗi. Đưa session ra external store giúp user tiếp tục làm việc khi request chuyển sang máy khác.

4. Use cases

Use cases: Web/API có nhiều EC2/ECS tasks: ELB chia tải, ASG quản số máy. Microservice private: internal ALB/NLB. Dùng Route 53 Alias để trỏ tên miền tới ELB, ACM cho TLS và CloudWatch để theo dõi.

Nhớ nhanh · SAA-C03

Vertical scaling tăng sức mạnh từng máy; horizontal scaling thêm máy; HA cần phân tán miền lỗi và chuyển traffic tới target khỏe.

ALB vs NLB vs GWLB

Mục đích: Chọn load balancer theo giao thức và cách cần xử lý traffic.

1. Hiểu đơn giản 4 loại Load Balancer

Loại

Hiểu đơn giản

Khi nào chọn?

ALB

Phân phối theo nội dung HTTP request

Website, API, Microservices

NLB

Phân phối theo kết nối mạng, hỗ trợ IP tĩnh

TCP/UDP, game, IP allowlist

GWLB

Chuyển traffic qua hệ thống kiểm tra bảo mật

Firewall, IDS/IPS

CLB

2. ALB — Application Load Balancer (Layer 7)

ALB hiểu nội dung HTTP request nên có thể định tuyến theo URL, hostname, header...

Ví dụ:

Client
   ↓
ALB (HTTPS)
   │
   ├── /users  → EC2 User Service
   │
   ├── /orders → EC2 Order Service
   │
   └── /images → Lambda

Một ALB có thể phục vụ nhiều microservices thông qua các Target Groups.

3. NLB — Network Load Balancer (Layer 4)

NLB phân phối kết nối mạng, không phân tích URL như ALB.

Game Clients
      ↓
 NLB (UDP/TCP)
      │
      ├── Game Server A
      ├── Game Server B
      └── Game Server C

Đặc biệt:

  • Hỗ trợ IP tĩnh theo AZ.

  • Có thể gán Elastic IP cho Internet-facing NLB.

  • Phù hợp giao thức TCP, UDP, TLS và workload yêu cầu latency thấp.

  • Có thể đặt NLB → ALB khi cần cả IP tĩnh và HTTP routing.

4. GWLB — Gateway Load Balancer (Layer 3)

GWLB không chủ yếu phân phối HTTP request đến ứng dụng, mà đưa traffic đi qua security appliances.

Internet
    ↓
Gateway Load Balancer
    ↓
Firewall / IDS / IPS
    │
    ├── Appliance A
    └── Appliance B
    ↓
Application

Ví dụ: Công ty muốn toàn bộ traffic được kiểm tra bởi firewall của bên thứ ba trước khi đến EC2.

GWLB dùng GENEVE, UDP port 6081 để chuyển traffic đến các appliance

Nhớ nhanh · SAA-C03

ALB = Layer 7 / HTTP routing; NLB = Layer 4 / TCP-UDP và IP tĩnh; GWLB = đưa traffic qua security appliances; CLB = legacy.

ELB targets, health, sessions & TLS

Mục đích: Hiểu load balancer chọn target, bảo vệ kết nối và xử lý request khi deploy hoặc scale-in.

Luồng request:

Client
↓ TLS / Listener
Load Balancer
↓ Rule → Target Group
Healthy Target

1. Listener, rule và target group

Listener nhận traffic ở protocol/port, ví dụ HTTPS 443. Rule chọn target group; target group chứa các backend và cấu hình health check.

Health check kiểm tra port/path như /health, theo interval và số lần thành công/thất bại đã đặt. Matcher có thể cấu hình mã HTTP thành công, không phải luôn chỉ 200. Endpoint nên phản ánh khả năng phục vụ của ứng dụng.

2. Security Group và IP client

Cho client vào ALB SG trên port cần thiết; app SG chỉ cho nguồn ALB SG trên port backend/health check. Không cần mở toàn bộ backend ra Internet.

Với ALB, ứng dụng lấy IP client từ X-Forwarded-For thay vì chỉ nhìn IP connection của ALB.

NLB có cơ chế client IP preservation phụ thuộc target/protocol; vẫn phải cấu hình network security đúng.

3. Sticky session

ALB stickiness dùng cookie để giữ một client về một target: cookie do LB tạo như AWSALB hoặc application-based cookie.

NLB stickiness dùng source IP khi được hỗ trợ, không dùng HTTP cookie.

Stickiness có thể làm tải lệch và không bảo vệ session khi target chết.

Lưu session trong ElastiCache/DynamoDB giúp các máy dùng chung state. ALB sticky sessions.

4. Cross-zone load balancing

Bật cross-zone: node LB có thể đưa traffic tới target ở các AZ khác.
Tắt: node chỉ đưa tới target trong AZ của mình; số máy chênh nhau có thể làm
tải mỗi máy không đều.
ALB bật ở mức load balancer, có thể chỉnh ở target group.
NLB/GWLB mặc định tắt; hành vi phí transfer khác nhau theo loại LB, nên kiểm
tra khi triển khai.

5. TLS và SNI

ACM cung cấp/quản lý certificate cho HTTPS/TLS listener.

SNI cho client gửi hostname trong TLS handshake để ALB/NLB chọn đúng certificate; CLB không hỗ trợ nhiều certificate theo SNI như vậy.

TLS client → LB và TLS LB → backend là hai chặng riêng. Muốn mã hóa xuyên các chặng, cấu hình cả listener và backend protocol phù hợp.

6. Deregistration delay và Use cases

Use cases: Khi target bị deregister, LB ngừng đưa request mới tới đó và cho request đang chạy thời gian hoàn tất. Đây là deregistration delay; thời gian mặc định thường 300 giây, cần chỉnh theo độ dài request.

Dùng cho deploy hoặc ASG scale-in để tránh cắt request.
Kết hợp graceful shutdown của app; không coi delay là cách cứu mọi request
trên target đã hỏng.
Nhớ nhanh · SAA-C03

Health check xác định target khỏe; sticky session và TLS termination giải quyết nhu cầu khác nhau. Phân biệt kết nối client–LB với LB–target.

Auto Scaling Groups & Launch Templates

Mục đích: Tự duy trì số EC2 cần thiết và tạo lại máy bằng cấu hình nhất quán.

1. Minimum, desired và maximum

Minimum là số máy tối thiểu; desired là số máy ASG đang cố duy trì; maximum là
giới hạn cao nhất.
Nếu một máy bị terminate hoặc được xác định unhealthy, ASG tạo máy thay thế để
về desired.

Chọn subnet ở nhiều AZ để phân bố máy. ASG không bảo vệ dữ liệu chỉ nằm trên máy bị xóa, nên ứng dụng nên stateless hoặc dùng external storage.

2. Launch Template

Launch Template lưu AMI, instance type, SG, IAM instance profile, User Data, key pair và disk. ASG chọn subnet/AZ và gắn target group theo cấu hình của group.

Template có version.

Đổi template không tự làm mọi máy cũ biến thành máy mới; dùng Instance Refresh để thay fleet theo cấu hình mới với kiểm soát capacity.

3. ASG và ELB

Launch Template → ASG tạo EC2 → đăng ký target group → ELB gửi request
                       ↑
          health check / scaling policy

ASG dùng EC2 health check và có thể bật ELB health check để thay máy mà app không phục vụ được. Cần health check grace period để không xóa máy đang bootstrap.

4. Launch và terminate có kiểm soát

Lifecycle hook tạm dừng ở một bước launch/terminate để cài đặt, hoàn tất công việc hoặc drain kết nối.

Mixed Instances Policy kết hợp nhiều instance type cùng On-Demand/Spot, giúp lấy capacity linh hoạt và giảm phí.

5. Use cases

Use cases: Web fleet nhiều AZ sau ALB; worker xử lý SQS có thể tạo/xóa theo backlog; rollout bản vá bằng AMI mới và Instance Refresh.

Nhớ nhanh · SAA-C03

ASG duy trì số EC2 cần thiết qua nhiều AZ; Launch Template định nghĩa máy được launch, còn scaling policy quyết định khi nào thêm/bớt máy.

ASG scaling policies, metrics & cooldowns

Mục đích: Tăng máy khi thiếu capacity và giảm máy khi dư, dựa trên tín hiệu phản ánh tải ứng dụng.

Luồng scale theo tải:

Metric / Alarm
↓ Scaling Policy
Auto Scaling Group
↓ tăng hoặc giảm desired capacity
EC2 instances

1. Các kiểu scaling

PolicyCách hoạt độngVí dụ
Target trackingGiữ metric gần mục tiêuCPU trung bình khoảng 50%
Step scalingVượt ngưỡng càng nhiều thì tăng càng mạnhCPU 70–85% thêm 1; trên 85% thêm 3
Simple scalingMột alarm kích hoạt một thay đổi, rồi chờ cooldownCPU cao → thêm 2 máy
ScheduledĐổi capacity theo lịch đã biếtThêm máy trước giờ cao điểm
PredictiveDự báo từ pattern lịch sử để chuẩn bị trướcTải tăng lặp lại mỗi sáng

2. Chọn metric

CPU hợp khi ứng dụng bị giới hạn bởi CPU. ALBRequestCountPerTarget hợp web khi request tương đối tương đồng. Network metric hợp workload bị nghẽn băng thông.

Worker SQS nên dùng backlog per instance, không chỉ tổng message: 1.000 message với 2 worker khác với 1.000 message với 100 worker.

Metric target tracking phải phản ánh mức sử dụng trên mỗi đơn vị capacity.

3. Warmup, grace period và cooldown

Warmup là thời gian instance mới ổn định trước khi được tính phù hợp vào quyết định scaling. Health check grace period tránh đánh unhealthy quá sớm sau launch.

Cooldown chủ yếu dùng cho simple scaling, tránh phản ứng liên tục trước khi tác dụng lần trước hiện rõ.

Target tracking/step scaling dùng warmup; không có quy tắc chung rằng mọi scaling đều bị khóa 300 giây.

4. Tăng nhanh, giảm thận trọng

Tạo AMI có sẵn phần mềm giúp máy phục vụ sớm.
Cho request/job đang chạy hoàn tất trước scale-in; dùng deregistration
delay/lifecycle hook khi cần.
Luôn đặt maximum đủ cho tải cần thiết và theo dõi quota/capacity.

5. Use cases

Use cases: Web biến động: target tracking. Chiến dịch biết giờ bắt đầu: scheduled. SQS backlog tăng rất nhanh: step scaling hoặc target tracking trên backlog per worker.

Nhớ nhanh · SAA-C03

Target tracking giữ metric gần target; step scaling theo ngưỡng; scheduled scaling chủ động theo giờ. Chọn theo pattern tải và thời gian khởi động.

AWS Elastic Beanstalk

Mục đích: Elastic Beanstalk giúp deploy web application lên AWS nhanh mà không cần tự dựng từng phần như EC2, Auto Scaling, Load Balancer và monitoring.

Code
↓
Elastic Beanstalk
↓
EC2 + ASG + Load Balancer

Elastic Beanstalk = PaaS, không phải serverless.

1. Cách hoạt động

Developer chủ yếu lo: Application Code

Beanstalk hỗ trợ: Provision infrastructure · Deploy application · Auto Scaling · Load Balancing · Health Monitoring

Hỗ trợ: Java · .NET · Node.js · Python · Go · PHP · Docker

Bạn vẫn có thể truy cập và cấu hình resource bên dưới.

2. Web Server Tier

Dùng cho web/API nhận HTTP request.

Client
↓
Load Balancer
↓
EC2 trong Auto Scaling Group

Phù hợp: Website · REST API · Synchronous Request

3. Worker Tier

Dùng cho background job.

Web App
↓
SQS
↓
Worker Environment
↓
Process Job

Ví dụ:

Send Email · Resize Image · Generate Report

Web Tier = HTTP Worker Tier = SQS + async job

4. Deployment

  • Các kiểu deploy quan trọng: Rolling = update từng nhóm instance
  • Immutable = tạo instance mới rồi thay instance cũ
  • Traffic Splitting = chia traffic giữa version cũ và mới

5. Database

Production database nên tách khỏi lifecycle của Beanstalk:

Elastic Beanstalk
↓
Application
↓
RDS riêng

→ terminate environment không làm mất database production.

6. Cost

Elastic Beanstalk bản thân không có phí riêng.

Bạn trả tiền cho resource bên dưới: EC2 · Load Balancer · RDS · S3 · ...

7. AWS App Runner

AWS App Runner chạy web applications hoặc APIs từ source code hoặc container image mà không cần tự quản lý EC2, ECS hay Kubernetes. Dịch vụ lo hạ tầng, triển khai, load balancing, HTTPS endpoint và automatic scaling.

Java Spring Boot REST API
↓
Source code / Container image
↓
AWS App Runner
↓ tự triển khai và tự scale
HTTPS Endpoint
↓
Users gọi GET /products

Ví dụ: đóng gói Spring Boot backend thành container image trên ECR, deploy bằng App Runner để người dùng gọi GET /products. App Runner phù hợp ứng dụng nhận HTTP requests; batch jobs theo lịch nên dùng dịch vụ điều phối như AWS Batch kết hợp EventBridge Scheduler.

So với Beanstalk, App Runner giảm việc quản lý hạ tầng web/container; Beanstalk cho phép truy cập và tùy chỉnh tài nguyên EC2/ASG/Load Balancer bên dưới.

Cập nhật từ 30/04/2026: App Runner không nhận khách hàng mới; khách hàng hiện hữu tiếp tục sử dụng. AWS khuyến nghị ECS Express Mode cho nhu cầu mới; vẫn giữ khái niệm App Runner để học tài liệu SAA-C03.

8. Use cases

Use cases:

  • Team muốn deploy web app nhanh nhưng vẫn dùng EC2/ASG.
  • Web tier ghi job vào SQS và Worker tier xử lý.
  • Ứng dụng truyền thống cần platform managed hơn là tự dựng hạ tầng.
