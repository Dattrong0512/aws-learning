AWS encryption patterns & KMS

Purpose: Understand the three places where encryption occurs and how AWS KMS manages encryption keys.

  • In Transit = encryption during transmission
  • At Rest = encryption at rest
  • Client-Side = the client encrypts itself before sending

Only the client with the key can decrypt.

This is a stronger layer of protection if you want data to remain encrypted even for storage service administrators.

4. AWS KMS

KMS = manage encryption keys + control key usage + audit key usage

KMS integrates with: S3 · EBS · RDS · SSM · CloudTrail · IAM · ...

The application does not retrieve the plaintext KMS key.

5. KMS Key Types

  • Symmetric = same key to Encrypt / Decrypt = commonly used AWS service
  • Asymmetric = Public Key + Private Key = Encrypt/Verify with public = Decrypt/Sign with private
  • Key types by ownership: AWS Owned Key = Fully managed by AWS
  • AWS Managed Key = AWS managed = alias of the form aws/service-name
  • Customer Managed Key = customer lifecycle management + policy = most detailed control

Customer Managed Key Suitable when you need custom key policy, cross-account, audit or lifecycle control.

6. Key Policy

IAM Policy ≠ automatically have the right to use KMS Key

KMS needs: Key Policy

to determine who can use the key.

For example:

Key Policy
↓
Allow Role A
↓
kms:Decrypt

Cross-account also often requires appropriate key policy configuration.

7. Rotation

AWS Managed Keys
→ AWS self-rotates

Customer Managed Key
→ automatic rotation can be enabled

Imported key material has different rotation limits.

8. KMS Key by Region

KMS key is Regional resource.

Region A · KMS Key A · Region B · KMS Key B

When copying encrypted snapshot to another Region:

Decrypt with Key A
↓
Encrypt with Key B
↓
Snapshot in Region B

9. Multi-Region Key

MRK has: Primary Key + Replica Key

in different Regions.

They have the same: Key ID · Key Material · Rotation Properties

→ Convenient for client-side encryption that needs to decrypt in many Regions.

MRK ≠ Global Resource

Primary and replicas are still managed by each Region.

10. Use cases

Use cases:

  • SSE-KMS for S3/EBS/RDS when needing CloudTrail audit, key policy and revoke access by key.
  • Client-side encryption for SSN/PII before replicating via DynamoDB Global Tables or Aurora Global Database.
  • Customer managed key and key policy have conditions to share encrypted snapshot/AMI for DR account.
