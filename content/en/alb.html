High availability & Elastic Load Balancing

Purpose: Split requests to multiple machines and keep the application running when one machine or AZ fails.

1. Scalability and High Availability

Vertical scaling is changing to a stronger/weaker device. Horizontal scaling is adding/removing machines. High Availability (HA) means having spare resources and a mechanism to switch to healthy resources.

A large machine increases capacity but is still the single point of failure. With web apps, often use load balancer and ASG across multiple AZs.

2. What does Load Balancer do?

The load balancer receives the connection from the client and then transfers it to the downstream target.

ELB: managed service: AWS operates the load balancer infrastructure, you configure listener, target and health check.

Client → Route 53 → Load Balancer
                    ├─ healthy target in AZ A
                    └─ healthy target in AZ B

Internet-facing load balancer receives traffic from the Internet; internal load balancer serves connection in private network.

Clients often use DNS names, not fixed ALB IPs.

3. Check health and remaining capacity

Health check helps avoid sending traffic to an error target during normal operation.

When one AZ is lost, the remaining AZ must have enough capacity; ELB does not automatically create additional EC2 without ASG/scaling mechanism.

Databases, files, and sessions also need fault-tolerant design. Putting the session to an external store helps users continue working when the request is transferred to another machine.

4. Use cases

Use cases: Web/API has many EC2/ECS tasks: ELB shares load, ASG manages number of machines. Microservice private: internal ALB/NLB. Use Route 53 Alias ​​to point the domain to ELB, ACM for TLS and CloudWatch for monitoring.

Quick review · SAA-C03

Vertical scaling increases the power of each machine; horizontal scaling more machines; HA needs to distribute error domains and transfer traffic to healthy targets.

2. ALB — Application Load Balancer (Layer 7)

ALB understands the HTTP request content so it can route by URL, hostname, header...

For example:

Client
   ↓
ALB (HTTPS)
   │
   ├── /users  → EC2 User Service
   │
   ├── /orders → EC2 Order Service
   │
   └── /images → Lambda

An ALB can serve multiple microservices through Target Groups.

3. NLB — Network Load Balancer (Layer 4)

NLB distributes network connections, not URL parsing like ALB.

Game Clients
      ↓
 NLB (UDP/TCP)
      │
      ├── Game Server A
      ├── Game Server B
      └── Game Server C

Special:

  • Supports static IP according to AZ.

  • Elastic IP can be assigned to Internet-facing NLB.

  • Suitable for TCP, UDP, TLS protocols and workloads that require low latency.

  • NLB → ALB can be set when both static IP and HTTP routing are needed.

4. GWLB — Gateway Load Balancer (Layer 3)

GWLB does not primarily deliver HTTP requests to the application, but rather sends traffic through security appliances.

Internet
    ↓
Gateway Load Balancer
    ↓
Firewall / IDS / IPS
    │
    ├── Appliance A
    └── Appliance B
    ↓
Application

For example: The company wants all traffic to be inspected by a third-party firewall before reaching EC2.

GWLB uses GENEVE, UDP port 6081 to transfer traffic to appliances

ALB = Layer 7 / HTTP routing; NLB = Layer 4 / TCP-UDP and static IP; GWLB = send traffic through security appliances; Club = legacy.

ELB targets, health, sessions & TLS

Purpose: Understand how load balancers choose targets, protect connections, and handle requests when deploying or scaling-in.

Request flow:

Client
↓ TLS / Listener
Load Balancer
↓ Rule → Target Group
Healthy Target

1. Listener, rule and target group

Listener receives traffic at protocol/port, for example HTTPS 443. Rule selects target group; target group contains backends and health check configuration.

Health check checks port/path such as /health, according to set interval and number of success/failures. Matcher can configure successful HTTP codes, not always just 200. Endpoints should reflect the service capabilities of the application.

2. Security Group and IP client

Let the client enter the ALB SG on the necessary port; SG app shows ALB SG power on backend/health check port. No need to open the entire backend to the Internet.

With ALB, the application gets the client IP from X-Forwarded-For instead of just looking at the ALB's IP connection.

NLB has a client IP preservation mechanism depending on target/protocol; Network security must still be configured correctly.

3. Sticky session

ALB stickiness uses cookies to keep a client on a target: cookies created by LB such as AWSALB or application-based cookies.

NLB stickiness uses source IP when supported, not HTTP cookies.

Stickiness can distort the load and not protect the session when the target dies.

Saving sessions in ElastiCache/DynamoDB helps machines share the same state. ALB sticky sessions.

4. Cross-zone load balancing

Enable cross-zone: LB node can send traffic to targets in other AZs.
Off: node only sends to targets in its AZ; Different numbers of machines can do it
Load each machine unevenly.
ALB turns on at load balancer level, can be adjusted at target group.
NLB/GWLB defaults to off; Transfer fee behavior varies by LB type, so check
Check when deployed.

5. TLS and SNI

ACM provides/manages certificates for HTTPS/TLS listeners.

SNI lets the client send its hostname in the TLS handshake so ALB/NLB can select the correct certificate; CLB does not support multiple certificates through SNI.

TLS client → LB and TLS LB → backend are two separate hops. To encrypt across hops, configure both the listener and the backend protocol accordingly.

6. Deregistration delay and Use cases

Use cases: When the target is deregistered, the LB stops sending new requests to it and gives the running request time to complete. This is deregistration delay; The default time is usually 300 seconds, need to adjust according to request length.

Used for deployment or ASG scale-in to avoid cutting requests.
Combine graceful shutdown of the app; Don't consider delay as a way to save every request
on target is broken.
Quick review · SAA-C03

Health check determines healthy target; sticky session and TLS termination address different needs. Distinguish client–LB connection from LB–target connection.

Auto Scaling Groups & Launch Templates

Purpose: Automatically maintain the required number of EC2 instances and recreate instances with a consistent configuration.

1. Minimum, desired and maximum

Minimum is the minimum number of machines; desired is the number of machines ASG is trying to maintain; maximum is
highest limit.
If a machine is terminated or determined to be unhealthy, ASG creates a replacement machine
about desired.

Select subnet in multiple AZs to distribute machines. ASG does not protect data that is only located on the device from being deleted, so the application should be stateless or use external storage.

2. Launch Template

Launch Template saves AMI, instance type, SG, IAM instance profile, User Data, key pair and disk. ASG selects subnet/AZ and attaches the target group according to the group's configuration.

Template has version.

Changing the template does not automatically make every old device a new device; Use Instance Refresh to replace the fleet to a new configuration with capacity control.

3. ASG and ELB

Launch Template → ASG creates EC2 → registers target group → ELB sends request
                       ↑
          health check / scaling policy

ASG uses EC2 health check and can turn on ELB health check to replace devices that the app cannot serve. Need health check grace period to not delete bootstrap device.

4. Controlled launch and termination

Lifecycle hook pauses at a launch/terminate step to install, complete work, or drain the connection.

Mixed Instances Policy combines multiple instance types with On-Demand/Spot, helping to get flexible capacity and reduce costs.

5. Use cases

Use cases: Web fleet multiple AZs after ALB; SQS processing worker can create/delete according to backlog; Patch rollout using new AMI and Instance Refresh.

Quick review · SAA-C03

ASG maintains the required number of EC2s across multiple AZs; Launch Template defines the machines to be launched, while scaling policy decides when to add/remove machines.

ASG scaling policies, metrics & cooldowns

Purpose: Increase capacity when lacking capacity and reduce capacity when excess, based on signals reflecting application load.

Stream scales according to load:

Metric / Alarm
↓ Scaling Policy
Auto Scaling Group
↓ increase or decrease desired capacity
EC2 instances

1. Scaling types

PolicyHow it worksFor example
Target trackingKeep metrics close to targetAverage CPU is about 50%
Step scalingThe more you exceed the threshold, the stronger the increaseCPU 70–85% add 1; above 85% add 3
Simple scalingAn alarm triggers a change, then waits for a cooldownHigh CPU → add 2 machines
ScheduledChange capacity according to known scheduleAdd machines before peak hours
PredictiveForecast from historical patterns to prepare in advanceThe load increases repeatedly every morning

2. Select metrics

CPU is suitable when the application is limited by CPU. ALBRequestCountPerTarget is suitable for web when requests are relatively similar. Network metrics for workloads with bandwidth congestion.

SQS workers should use backlogs per instance, not just total messages: 1,000 messages with 2 workers is different from 1,000 messages with 100 workers.

Metric target tracking should reflect usage per unit of capacity.

3. Warmup, grace period and cooldown

Warmup is the time a new instance takes to stabilize before being properly factored into a scaling decision. Health check grace period avoid hitting unhealthy too soon after launch.

Cooldowns are mainly used for simple scaling, avoiding continuous reactions before the previous effect is visible.

Target tracking/step scaling using warmup; There is no general rule that every scaling is locked for 300 seconds.

4. Increase quickly, decrease cautiously

Creating an AMI with available software helps the machine to serve soon.
Let the running request/job complete before scale-in; Use deregistration
delay/lifecycle hook when needed.
Always set maximum for the required load and monitor quota/capacity.

5. Use cases

Use cases: Web volatility: target tracking. Campaign knows start time: scheduled. SQS backlog grows very fast: step scaling or target tracking on backlog per worker.

Quick review · SAA-C03

Target tracking keeps metrics close to target; step scaling by threshold; scheduled scaling proactively by the hour. Choose according to loading pattern and boot time.

AWS Elastic Beanstalk

Purpose: Elastic Beanstalk helps deploy web applications to AWS quickly without having to manually build each part such as EC2, Auto Scaling, Load Balancer and monitoring.

Code
↓
Elastic Beanstalk
↓
EC2 + ASG + Load Balancer

Elastic Beanstalk = PaaS, not serverless.

1. How it works

Developers mainly worry about: Application Code

Beanstalk supports: Provision infrastructure · Deploy application · Auto Scaling · Load Balancing · Health Monitoring

Support: Java · .NET · Node.js · Python · Go · PHP · Docker

You can still access and configure the resources below.

2. Web Server Tier

Used for web/API to receive HTTP requests.

Client
↓
Load Balancer
↓
EC2 in Auto Scaling Group

Suitable: Website · REST API · Synchronous Request

3. Worker Tier

Used for background jobs.

Web App
↓
SQS
↓
Worker Environment
↓
Process Job

For example:

Send Email · Resize Image · Generate Report

Web Tier = HTTP Worker Tier = SQS + async job

4. Deployment

  • Important deployment types: Rolling = update each group of instances
  • Immutable = create a new instance and replace the old instance
  • Traffic Splitting = divide traffic between old and new versions

5. Database

Production database should be separate from the Beanstalk lifecycle:

Elastic Beanstalk
↓
Application
↓
Private RDS

→ Terminating the environment does not destroy the production database.

6. Cost

Elastic Beanstalk itself has no separate fees.

You pay for the resources below: EC2 · Load Balancer · RDS · S3 · ...

7. AWS App Runner

AWS App Runner Run web applications or APIs from source code or container images without needing to manage EC2, ECS or Kubernetes yourself. Services take care of infrastructure, deployment, load balancing, HTTPS endpoint and automatic scaling.

Java Spring Boot REST API
↓
Source code / Container image
↓
AWS App Runner
↓ self-deploy and self-scale
HTTPS Endpoint
↓
Users calls GET /products

For example, package the Spring Boot backend into a container image on ECR, deploy with App Runner for users to call GET /products. App Runner matches the receiving application HTTP requests; Scheduled batch jobs should use a dispatch service like AWS Batch combined with EventBridge Scheduler.

Compared to Beanstalk, App Runner reduces web/container infrastructure management; Beanstalk allows accessing and customizing the underlying EC2/ASG/Load Balancer resources.

Updated from April 30, 2026: App Runner is not accepting new customers; Existing customers continue to use it. AWS recommends ECS Express Mode for new needs; still keep the App Runner concept to learn SAA-C03 material.

8. Use cases

Use cases:

  • Team wants to deploy web app quickly but still uses EC2/ASG.
  • The Web tier writes the job to SQS and the Worker tier processes it.
  • Traditional applications need a managed platform rather than building the infrastructure yourself.
