Disaster Recovery: RPO, RTO & recovery strategies

Purpose: Prepare how to restore data + applications when a major incident occurs.

DR is usually balanced: RPO + RTO + Cost

1. RPO vs RTO

RPO = Recovery Point Objective = maximum amount of data loss accepted.

For example:

Backup every 1 hour
→ can take up to nearly 1 hour of data.

RTO = Recovery Time Objective = accept maximum system downtime.

Disaster time 10:00
App works again 10:30

→ RTO = 30 minutes

↓

RPO = how much data is lost. RTO = how long to down.

AWS Backup & Backup Vault Lock

Purpose: Manage and automate backups for multiple AWS services using a centralized policy.

Resources → Backup Plan → Backup Jobs → Backup Vault → Recovery Points

1. What does AWS Backup support?

  • Scheduled/on-demand backup: Backup scheduled or run immediately; Select resource by ID or tag.
  • Retention and lifecycle: Specify how long to keep backups and when to transfer to cold storage if the resource supports it.
  • Common resources: EC2/EBS, RDS/Aurora, S3, DynamoDB, EFS, FSx, DocumentDB/Neptune. PITR, cold storage and copy capabilities vary by service.

2. Plan, Vault and Recovery Point

  • Backup Plan = policy. Configure frequency, backup window, lifecycle, retention and resource assignment.
  • Backup Vault = place to manage backups. Recovery Point = version that can be used to restore.
  • Backing up more frequently creates recovery points closer together, helping to reduce RPO; still need to test restore to check RTO and recovery ability.
Plan: every 12 hours · keep for 30 days · apply tag Backup=Daily
↓
Selected Resources → Recovery Points in Vault

3. Copy to Region or another account

  • Cross-Region: Copy backup to another Region to recover when the source Region has problems.
  • Cross-account: Copy to backup account to increase isolation when production account is compromised.
  • Need correct vault policy, IAM/service role and KMS permissions; Check if the resource supports that type of copy.

4. PITR

Point-In-Time Recovery = restore to a specific point in time within the supported range. Only applies to supported services, not available for all resources.

10:36: data is still good
↓
10:37: error occurred
↓
PITR returns 10:36 if in recovery window

5. Backup Vault Lock

WORM = Write Once Read Many. Vault Lock protects recovery points from unauthorized deletion or retention changes.

  • Governance mode: People with appropriate permissions can still change/remove the lock.
  • Compliance mode: After the grace period, the lock cannot be changed/removed; Even root does not bypass retention.
  • Lock does not prove a clean backup. Data that has been damaged by ransomware can still be backed up and locked; Needs lots of recovery points, appropriate retention and restore testing.

6. Use cases

Use cases:

  • Tag EC2/EBS/RDS to create a backup management plan for the entire environment.
  • DR: keep a copy in another Region; Increase isolation with a separate backup account.
  • Compliance/ransomware: Vault Lock keeps backups until the end of retention, choosing a recovery point before the incident when restoring.
Quick review · SAA-C03

AWS Backup manages multi-service backup policies; Backup Vault Lock helps protect retention, not replacing restore testing.

Purpose: Compare backup and data protection mechanisms to choose the right recovery based on service, timing, and retention.

1. What data to backup?

Replication can propagate changes/deletions according to configuration, so backup/version history is still needed to go back to before the error. Object Lock protects versions; Do not create an independent backup yourself.

2. Retention and characteristics

Backup typeRetention / characteristics
RDS AutomatedDB instance: 0–35 days, 0 is off; Multi-AZ DB cluster: 1–35 days
Aurora Automated1–35 days; Automated backups cannot be turned off
DynamoDB PITRRecovery window 1–35 days, default 35 when enabled
RDS / Aurora Manual SnapshotKeep until deleted
EBS SnapshotIncremental; Keep until deleted or processed by lifecycle policy
AWS Backup ContinuousPITR up to 35 days; depending on the configured service and retention
AWS Backup PeriodicRetention according to backup plan; Supports long-term storage, cold storage capabilities depending on resources

AWS Backup continuous supports RDS instances/Aurora accordingly, but does not support RDS Multi-AZ DB clusters. Copy continuous backup to another Region/account to create a snapshot copy, without keeping the PITR window of the source copy.

3. Use cases

Use cases:

  • Wrongly deleting database data: PITR forward error if still in recovery window.
  • Backup EBS daily and keep for 7 days: DLM; Many services/accounts need common management: AWS Backup.
  • Save database copies for many months/years: manual snapshot or periodic backup with appropriate retention.
  • S3 overwritten: restore old version; Need to prevent version deletion according to retention: Object Lock with appropriate mode.
Quick review · SAA-C03

Remember to distinguish between backup, replication, archive and DR: each solution has a different purpose, recovery time and scope.
