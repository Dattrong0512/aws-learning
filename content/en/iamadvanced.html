AWS Organizations & Service Control Policies (SCP)

Purpose: AWS Organizations is used to manage multiple AWS accounts within the same organization, helping to separate workload, billing, and administration rights.

AWS Organizations = Multi-Account Management + Consolidated Billing + OU + SCP

1. Management Account & Member Account

Management Account = Organization management account

Member Account = member accounts

For example:

Management Account
├── Dev Account
├── Test Account
├── Prod Account
└── Finance Account

One member account belongs only one Organization at a time.

2. Why use multiple accounts?

Instead:

1 AWS Account
├── Dev
├── Test
├── Prod
└── Finance

split into: Dev Account · Test Account · Prod Account · Finance Account

Help: Separation of rights · Separation of billing · Separation of workload · Reduce blast radius

Dev encountered a security issue
↓
reduce the risk of direct effects Prod

4. Organizational Unit - OU

OU = group of AWS accounts with the same policy/governance.

Organization Root
├── Development OU
│   ├── Dev Account A
│   └── Dev Account B
│

    └── Finance Account

OUs can be nested:

↓

↓

↓

OU = account group to manage policy, not network/VPC.

5. Service Control Policy - SCP

SCP = maximum permission limit that the account is allowed to use.

SCP = Maximum Permission Boundary at the Organization level

Important: SCP ≠ grant permissions

SCP = limit permissions

IAM · Allow s3:*

but SCP: Deny s3:*

S3 ❌

Explicit Deny in SCP wins over IAM Allow.

Only Allow the services you need to use

Allowlist = only for what is listed.

IAM policy evaluation, boundaries & cross-account access

Purpose: Understand how AWS combines multiple policy layers to decide whether a final request is Allow or Deny.

Default = Implicit Deny

Explicit Deny = wins all Allow

For example:

Deny sqs:*
+
Allow sqs:DeleteQueue
↓
DeleteQueue ❌

Just have Explicit Deny matches → request is blocked.

1. Main types of Policy

Identity-based Policy = attached to User / Group / Role = what does principal do?

Resource-based Policy = attached to resource = who can access the resource

Resource policy example: S3 Bucket Policy · SQS Queue Policy · SNS Topic Policy · Lambda Resource Policy

2. SCP, Boundary, Session Policy

  • SCP = limit maximum permissions to Organization / OU / Account
  • Permission Boundary = limit the maximum permissions of IAM User / Role
  • Session Policy = narrow temporary session permissions

Important: SCP / Boundary / Session Policy ≠ self-authorization

They only limit rights

3. Effective Permission

Can simply remember:

∩

∩
SCP
∩
Session Policy (if any)
↓
Effective Permission

and:

Explicit Deny
→ DENY now

Allow iam:CreateUser

Allow s3:*
Allow ec2:*

↓
There is no delivery
↓
CreateUser ❌

Boundary Allow a service does not mean providing that service yourself.

4. IAM Conditions

Condition adds context to the decision.

Can check: MFA · IP Address · VPC Endpoint · Principal Tag · Resource Tag · Organization ID

5. ABAC

ABAC = Attribute-Based Access Control

User: · Department = Data · EC2: · Project = DataAnalytics

Policy can give:

↓

because Explicit Deny wins.

1 User

AWS Directory Service & Active Directory integration

Purpose: AWS Directory Service helps applications on AWS use Active Directory (AD): either create a directory on AWS, or connect to an existing company AD.

AD is where employee accounts, computers, and groups are managed. When Bob logs in, AD helps check Who is Bob?. Bob in AD different from IAM User in your AWS account.

1. Three options need to be distinguished

1.1. AWS Managed Microsoft AD

AWS creates and manages the infrastructure for one Microsoft AD runs on AWS. You can create users and groups in this AD for applications to use.

Bob is created in Microsoft AD on AWS
↓
Bob logs into the application
↓
AD on AWS authenticates Bob

Use when: Windows applications or machines on AWS need Microsoft AD.

  • If the company already has an AD in the office, it can be set up trust between two ADs.
  • Then a user like Bob can still reside in corporate AD and use that identity to access appropriate resources on AWS.

1.2. AD Connector

AD Connector is bridge From AWS to AD the company has it. It does not create a new AD to save the Bob account.

Bob is in the company AD
↓
Bob logs into the AWS service
↓
AD Connector forwards the request to corporate AD
↓
AD company authenticates Bob

Use when: The company already has AD and wants AWS services to use those users. Creating a user or changing Bob's password is still done in the company AD.

1.3. Simple AD

Simple AD is one basic, independent directory on AWS. You create and manage users in Simple AD.

Bob is created in Simple AD
↓
The application on AWS uses the Bob account

Use when: The workload needs basic directory functionality, but does not need full Microsoft AD or connection to corporate AD.

Simple AD Does not support trust with other AD and Do not use as an identity source for IAM Identity Center.

2. Quick comparison

ServiceWhere is Bob's account located?Main idea
AWS Managed Microsoft ADCan be in AD on AWS; You can also use users from trusted ADThere is Microsoft AD on AWS
AD ConnectorCompany AD already existsConnect AWS to existing AD
Simple ADSimple AD on AWSBasic, independent directory

3. Contact IAM Identity Center

If using AD as an identity source:

AD → determines who Bob is
IAM Identity Center → assign Bob permission to Dev / Test / Prod
  • Bob having an account in AD does not mean he can access an AWS account. Administrators must still assign permissions to Bob or Bob's group in IAM Identity Center.

4. Use cases

Use cases:

  • Migrate Windows/managed directory workloads to AWS but still establish two-way trust with corporate AD.
  • Use AD Connector when you want AWS to authenticate employees with on-prem AD without creating a directory copy in AWS.
  • Use Simple AD for standalone AWS applications that need directory AD-compatible but do not need on-premises federation.

5. Active Directory Forest Trust

AWS Control Tower

Purpose: AWS Control Tower helps set up and manage multiple AWS accounts under a common baseline. It uses AWS Organizations as its foundation, creating landing zones, allocating accounts, and tracking compliance with rules.

Remember: Control Tower is Construction and management tools; landing zone is created environment. Then, when the team needs a new account, the administrator can provision the account into this environment Account Factory.

AWS Organizations
↓
Control Tower builds landing zone
↓
Dev / Test / Prod accounts
↓
Apply controls + monitor compliance
  • Instead of each team creating its own account with its own configuration, administrators use Account Factory to level accounts in the Organization structure and apply baseline governance.

1. Guardrail: prevention is different from detective

Preventive control block violations before action is taken. Usage example SCP to restrict operations in unauthorized AWS Regions.

User calls API in restricted Region
↓
Preventive control check
↓
Deny

Detective control check configuration after the resource is created or changed, often passed AWS Config rule. For example: detecting a resource missing tags.

Resource is created but tag is missing
↓
AWS Config review
↓
NON_COMPLIANT
TypeThe mechanism in the exampleResults
PreventiveSCPBlock violations.
DetectiveAWS Config ruleDetect and report non-compliant resources.

Need to prevent creating wrong resources → preventive. Need to find the wrong resource → detective. Detecting a violation does not mean the action has been blocked or the resource has been fixed.

2. Notification and remediation flow

Suppose the team wants to find a resource that is missing a tag:

Resource in member account
↓
AWS Config rule evaluates the tag
↓
NON_COMPLIANT
↓
SNS notifies admin
↓
Lambda adds tags according to defined rules
↓
AWS Config reevaluated
  • SNS and Lambda are workflows that require additional configuration. Lambda needs permission to edit the resource and must know Which tag is correct?; Don't guess yourself CostCenter for resource production.
  • Preventive control operates in an earlier step: it Refuse unauthorized action, for example calling an API in a restricted Region, instead of waiting for AWS Config to detect it later.

3. Use cases

Administration situationHow to deal with Control Tower
Build a standard Landing ZoneCreate a multi-account environment with Organization structure, baseline governance and compliance dashboard
Limit AWS RegionsTurn on Preventive Control (SCP) to immediately block API calls in unauthorized Regions
Check & add TagUse AWS Config (Detective) to detect resources missing tags → report to SNS → run Lambda to tag according to clear rules

4. Three types of Control (Preventive / Proactive / Detective), Account Factory & Drift

Control typeTime of inspectionEnforcement mechanism
PreventiveImmediately upon calling the AWS API actionSCP/RCP blocks the offending operation
Proactive controlsBefore CloudFormation creates or updates resourcesCloudFormation Hooks check template/resource properties
DetectiveAfter the resource has been created or changedAWS Config Rules detect non-compliance status
Components & Drift in Control TowerFunction / Expression of deviation from the standard state

Control Tower builds and manages landing zones according to guardrails/controls; Organizations takes care of the multi-account structure, Account Factory creates standard accounts.

LDAP, SAML 2.0, SCIM & Custom Identity Broker

Purpose: Differentiate the roles of each enterprise identity protocol and the two federation login flows to AWS.

1. Distinguishing table for LDAP, IdP, SAML 2.0, SCIM and STS

Composition/ProtocolCore functions
LDAPDirectory lookup protocol and username/password check directly against directory (e.g. Active Directory)
Identity Provider (IdP)System that authenticates users and issues federated login credentials (AD FS, Okta, Entra ID, Keycloak)
SAML 2.0Standard for transmitting authentication messages (SAML Assertion) from IdP to AWS for SSO login without revealing the password to AWS
SCIMProtocol Automatically synchronize Users and Groups lifecycle (create, edit, delete) from IdP to IAM Identity Center
Custom Identity BrokerThe middleware application builds itself when the internal system only has LDAP and There is no IdP that supports SAML/OIDC
AWS STS & Federation EndpointSTS grants temporary credentials; Federation Endpoint changes temporary credentials to sign-in URL into AWS Console

2. Two federated authentication flows need to be distinguished

Flow A — Without SAML (using Custom Identity Broker):
Employee → Custom Identity Broker → check LDAP → call AWS STS to get temporary credentials → call AWS Federation Endpoint → open AWS Console

Stream B — With SAML 2.0 Federation (preferred, no need to write Broker yourself):
Employee → IdP (authenticate with LDAP) → return SAML Assertion → send to AWS SAML Endpoint / STS (AssumeRoleWithSAML) → open AWS Console
