Amazon Data Firehose

Purpose: Bring streaming data to storage/analytics destination using managed service, not self-managing shard and consumer fleet.

1. Delivery pipeline

Producer / Kinesis Data Streams / logs
 → Firehose → buffer / optional transform → destination + backup S3 when configuring

Destination includes S3, Redshift, OpenSearch and HTTP/vendor supported. Delivery Redshift uses S3 as staging before COPY.

2. Buffer and latency

Firehose often collects data by size/time and then delivers it; suitable for near real-time ingestion, not having to default to logic that must respond to each event instantaneously.

There is a configuration to reduce/zero buffering at some destinations, but does not make Firehose a replayable stream for many consumers.

Service self-managed delivery capacity; There are still quotas and limits based on source/destination.

3. Transform and format conversion

Lambda can transform records before delivery.

Format conversion native converts JSON to Parquet/ORC for S3, using Glue Data Catalog schema; CSV needs to be transformed to JSON first, not directly converting all formats.

Compression/columnar format helps reduce storage and scan data when querying. AWS Firehose format conversion.

4. Replay, backup and permissions

Firehose does not provide retention streams for consumers to freely replay like Kinesis Data Streams does. If multiple consumers/replays are needed, put KDS first and Firehose as a consumer delivery.

There are retry and S3 backup for all/failed records depending on destination/configuration.

Service role needs source, destination, Lambda and KMS permissions; Design error monitoring and reprocess backup data.

5. Use cases

Use cases: Logs/clickstream → S3 data lake; data → Redshift/OpenSearch; Lambda transform → JSON → Parquet. Need to process real-time multiple consumers and read back events: Kinesis Data Streams.

Quick review · SAA-C03

Data Firehose is managed to deliver stream data to storage/analysis destinations; Does not require consumer self-management by shard like Data Streams.

SQS vs SNS vs Kinesis vs Firehose vs MQ

Purpose: Select messaging based on data reception, replay and application compatibility requirements.

1. Key comparison

2. Queue another stream

SQS workers often share message processing; delete message when finished.

Kinesis keeps records in the retention window even after a consumer reads, allowing multiple consumers to read independently or replay.

SQS Standard has at-least-once/best-effort order; FIFO uses message group/deduplication to support consistent ordering.

Kinesis orders by shard, not a global order across all shards.

3. SNS + SQS

An event → SNS ┬→ Queue A → order processing
               └→ Queue B → analytics

Each system has its own queue, retry and scale.

SNS push to queue; worker pulls from SQS.

SNS does not have to replace every queue; archive/replay of SNS FIFO is a separate feature, it does not mean every SNS topic is streamed like KDS.

4. Kinesis + Firehose and MQ

KDS keeps the stream for analytics/replay; Firehose pushes a branch to S3/warehouse.
As long as managed delivery is needed, you can use Firehose directly without adding KDS.

engine. engine.

SQS/SNS as appropriate.

5. Use cases

Use cases: Background jobs: SQS. One event to many systems: SNS + SQS. Telemetry multiple consumers/replay: KDS. Logs to data lake: Firehose. Legacy broker app needs few code changes: MQ.
