AWS Snow Family

Purpose: Understand how to transfer data using a physical device when transferring over the network takes too long or the workplace lacks connectivity.

1. Why use equipment?

Hundreds of TB via slow transmission can take weeks/months. Snowball Edge copies data on-premises and then transports the device to AWS for import into S3.

Create job → receive device → copy data → send back to AWS → import to S3

Compare network transmission time with receive/copy/send/import time; Actual bandwidth, cost and deadline must also be considered.

2. Snowball Edge and edge compute

Storage Optimized prioritizes capacity; Compute Optimized prioritizes processing at the place of data creation.

Edge compute integrates data filtering, inference or media processing at low-Internet sites before sending data to the cloud.

Data on the device is encrypted; Key management, job credentials and shipping are still important parts of the process.

3. Import and archive

Import into S3 and then use Lifecycle to switch to the appropriate Glacier layer, do not choose the "Snowball import directly into Glacier vault" route.

Do not use the device for continuous synchronization that requires frequent updates; online recurring copy is more suitable for DataSync.

4. Note current availability

From November 7, 2025, Snowball Edge is only available to existing customers.

The Snowcone/Snowmobile in the old document is not the new option that is always available.

Keep the concept of offline migration for learning, but when implementing, check the service/solution currently provided. AWS Snowball availability.

5. Use cases

Use cases: Data center has a lot of data and limited WAN: offline bulk transfer if eligible. Site disconnected needs to be handled locally: edge compute. The NAS has a good enough connection and needs scheduled copying: DataSync.

Snow Family uses large-scale data movement/processing when network lines are not suitable; Select device according to data size and edge compute request.

Amazon FSx managed file systems

Purpose: Choose a managed file system with protocols and features suitable for the existing application.

Types of file systems: FSx for Windows File Server · FSx for Lustre · FSx for NetApp ONTAP · FSx for OpenZFS

1. FSx menu

OpenZFSNFS, snapshot/clone/compression ZFSLinux/ZFS workload needs low latency

2. Windows File Server

Integrated AD, file permissions/ACL and user quotas. Linux clients can also mount SMB; This is not an EC2 Windows-only service.

Multi-AZ deployment increases BP; Backup protects data.
On-prem access via VPN/DX with appropriate route, SG and file permissions.
Windows SMB shares often choose Windows FSx instead of EFS NFS.

3. Luster and S3

Luster helps multiple compute nodes process files in parallel with high throughput. You can link datasets in S3, read them as files and export the results to S3.

Scratch is for temporary processing, not replicating data to protect file server errors like Persistent. Persistent combines data that needs to be kept and longer workloads. Choose deployment according to durability and supported features, don't assume every FSx has the same HA model.

4. ONTAP and OpenZFS

ONTAP is suitable for applications that rely on NetApp, multiple protocols, snapshots/clones and tiering. OpenZFS is suitable for ZFS/NFS applications and corresponding snapshot/clone features.

Quick Clone does not replace independent backup. Encrypt at rest using KMS; encryption in transit and file permissions depend on protocol/filesystem.

5. Use cases

Use cases: Company Windows share + AD: FSx Windows. HPC reads dataset S3: Luster. Lift-and-shift NetApp NAS: ONTAP. Workload is using ZFS: OpenZFS. Shared Linux files across multiple AZs: compare EFS first.

AWS Storage Gateway

Purpose: For on-prem applications to use the familiar file/block/tape protocol with storage in AWS.

1. Gateway and local cache

Gateway: appliance connects on-premises applications to the cloud.

Local cache holds recently used data for quick access; Data is transmitted to AWS according to the gateway mechanism.

Storage Gateway serves seamless hybrid access. It is different from DataSync which runs a transfer job and Snowball which transfers data by device.

2. S3 File Gateway

App on-prem --NFS/SMB--> File Gateway + cache --HTTPS--> S3 objects

The app sees the file share, S3 saves the object. Gateway has IAM role to access bucket; SMBs can use AD. Share/file permissions and S3 permissions are classes that need to be configured.

Do not consider the local cache as a permanent place for all data or that the gateway file is a shared POSIX filesystem like EFS.

3. Volume Gateway

Provide block volumes via iSCSI. Cached volumes keep the main data in AWS, caching the portion in use locally to reduce local storage. Stored volumes keep all core data on-premises and backed up to AWS.

Backup uses EBS snapshots to serve restore.

Stored is suitable when you need to access the entire dataset with local latency; cached is suitable when you want to reduce on-prem capacity.

4. Tape Gateway

Provides iSCSI virtual tape library (VTL) for existing backup software. Tape stored on AWS, can be archived to Glacier Flexible Retrieval/Deep Archive according to configuration.

No more buying and shipping physical tape; Restoring tape archives still has retrieval time/costs to consider.

5. Use cases

Use cases: NFS/SMB share backed by S3: File Gateway. Block storage on-prem with cloud backup: Volume Gateway. Replace the tape library but keep the backup software: Tape Gateway.

6. Compare Volume Gateway: Cached Volumes vs Stored Volumes

AWS DataSync & Transfer Family

Purpose: Distinguish between copying data between the storage system and the endpoint receiving files from users/partners.

1. DataSync

DataSync runs the task of transferring data between supported storage such as NFS/SMB/HDFS/object storage and S3/EFS/FSx. There is scheduling, data checking, bandwidth limit and transmission over TLS.

NAS on-prem → DataSync agent/task → S3 / EFS / FSx
On-prem file storage often requires an agent; AWS-to-AWS in the same regular account
no agent needed.
Some cloud/cross-account sources have different rules by location and task mode.

2. Metadata and sync

It is possible to keep permissions/metadata supported in source/destination pairs. Copying NFS to S3 does not turn S3 into a POSIX filesystem with full file permissions as the source.

This is a transfer task that runs on schedule or on demand, not CDC database or real-time filesystem replication. AWS metadata behavior.

3. Transfer Family

Managed endpoint for clients to use SFTP/FTPS/FTP to transfer files to S3/EFS according to supported protocols; AS2 serves B2B exchanges with its own support backend.

Partners using SFTP client → Transfer Family → S3 prefix are authorized
Authentication can be service-managed, AD or custom provider depending on the protocol.
IAM role/policy and filesystem permissions limit where each user can access.
FTP is unencrypted and only uses the VPC endpoint; Do not choose FTP for sensitive files
via the Internet.

4. Select by task

RequestSelect
Copy large NAS to AWS, with schedule/verificationDataSync
Partners still use SFTP client to send filesTransfer Family
On-premises apps continue to use hybrid file/block/tapeStorage Gateway
Just need a private network lineVPN/Direct Connect; Also need transfer tool

5. Use cases

Use cases: Migration NFS → EFS: DataSync. Scheduled file synchronization: DataSync. Instead of self-managed SFTP server, data goes to S3: Transfer Family.

AWS storage selection guide

Purpose: Choose storage based on how the application accesses data first, then consider durability, latency and cost.

Select according to how the application reads/writes:

Block → EBS
Shared File → EFS / FSx
Object → S3
Local temporary disk → Instance Store

1. Block, file or object?

DemandService
Object/API, data lake, static assets, backupS3
Disk for EC2, boot or databaseEBS
NFS/POSIX files are shared by many Linux clientsEFS
SMB/AD or specialized file systemFSx
Local disk is very fast, data can be recreatedInstance Store

Do not choose S3 as disk mount for databases that need block I/O. Don't choose EBS so that multiple apps across AZs can share files. Archive object: select the S3 Glacier class according to the required retrieval time.

2. Where is the data located and can it be lost?

EBS is in one AZ, if you want to go to another AZ, you need a snapshot/restore.
Regional EFS across multiple AZs; One Zone reduces fees but accepts AZ risk.
Instance Store loses data over the instance/host life cycle.
FSx has different deployments; Check HA/backup of specific type.
Backup prevents accidental deletion; replication/failover serves availability, not replacement
replace each other.

3. Hybrid access or migration?

TaskService
Continue file/block/tape at on-prem, AWS backendStorage Gateway
Online bulk copy/sync has verificationDataSync
Receive SFTP/FTPS files from partnersTransfer Family
Offline bulk transferSnowball/physical transfer solutions are also available

4. Use cases

Use cases: Windows shared drive: FSx Windows. WordPress multiple EC2: EFS. Separate DB Disk: EBS io2/gp3 by I/O. Data lake: S3. Before closing, check RPO/RTO, throughput, encryption and transfer/retrieval cost.

Quick review · SAA-C03

Block storage → EBS; shared NFS → EFS; Specialized SMB/FS → FSx; object/backup → S3; Data migration → DataSync/Snow.
