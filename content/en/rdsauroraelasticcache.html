Amazon RDS fundamentals & operations

Purpose: Run a relational database without having to manage the entire server, patches and backups yourself.

Database flow:

Application
↓ Database endpoint
RDS
↓
Managed database / storage / backup

1. What does RDS manage, what do you manage?

RDS supports engines such as MySQL, PostgreSQL, MariaDB, Oracle, SQL Server and Db2; Aurora is a MySQL/PostgreSQL compatible option with its own architecture.

AWS takes care of provisioning, OS patching, and configured managed features.

You still design the schema, query, index, database users, capacity, backup retention and network security.

2. Configure database

Select engine/version, instance class, storage, subnet group, SG, parameter/option group and maintenance window.

Set DB in private subnets; Just put the SG app into the database port.

Changing instance class increases CPU/RAM; Add replica extension read.

Storage Auto Scaling increases disk within the set maximum storage, does not automatically increase CPU and does not automatically reduce disk.

3. Storage Auto Scaling

RDS increases storage when low free space is persistent and enough time has elapsed since the previous change.

Typical conditions: less than 10% left, lasts at least 5 minutes, has been at least 6 hours since the change or storage optimization has been completed, set a later date.

Set maximum large enough and alarm monitors storage. Auto Scaling does not replace data cleaning or capacity planning.

4. RDS vs. EC2 and RDS Custom

RDS usually does not allow SSH into the OS. DB on EC2 gives more control but you take care of patching, backup and HA yourself.

RDS Custom for Oracle/SQL Server needs deeper customization in OS/database. Changes must still be within the scope of support and coordination with the service's automation.

6. Use cases

Use cases: Web needs managed PostgreSQL/MySQL: RDS. Enterprise software needs OS customization: consider RDS Custom. Need HA: add Multi-AZ; need to reduce reading load: Read Replica; need to reduce repeated queries: cache.

RDS Multi-AZ & Read Replicas

Purpose: Distinguish fault-tolerant solutions from solutions that increase read capacity.

Distinguish between two needs:

Multi-AZ = fault tolerance/failover
Read Replica = increased read load

1. Key comparison

CriteriaMulti-AZ DB instanceRead Replica
TargetAvailability and automatic failoverRead scaling, reporting, can support DR
ReplicationSynchronous to standby in another AZAsynchronous, has replica lag
Standby serving reading?NoThere is an endpoint for the app to send read queries
When primary failsRDS moves the endpoint to standbyPromote according to the appropriate process, change the app endpoint

2. Multi-AZ DB instance

The application uses a stable DB endpoint. When primary fails, AWS failsover to standby; app needs to retry/reconnect and handle interrupted transactions.

Multi-AZ in a Region does not protect against the failure of the entire Region and does not replace backups to prevent accidental deletion of data.

3. Don't mistake Multi-AZ DB cluster

RDS Multi-AZ DB cluster: Another model: one writer and two readable standbys across three AZs, using semisynchronous replication.

It supports both HA and read load; The statement “all Multi-AZ standbys are unreadable” does not apply. AWS differentiates between two models.

4. Read Replica

Replica can be in the same or different Region when the engine supports it.

The app must send the read query to the replica endpoint; query requires the latest data so use primary when necessary.

Promote replica creates an independent DB, no longer following the old primary.
The number of replicas and features depends on the engine.
Replication in the same Region is free to transfer according to the RDS support mechanism;
cross-Region has a transfer fee.

5. Use cases

Use cases: DB production needs to failover itself when AZ fails: Multi-AZ. Heavy reports slow down transactions: Read Replica. Users in other Regions need to read more closely or have DR: cross-Region replica with promotion plan.

Multi-AZ prioritizes high availability/failover; Read Replica prioritizes scale reads. Read Replica does not replace the backup or HA synchronization mechanism.

Amazon Aurora architecture & scaling

Purpose: Use a MySQL/PostgreSQL compatible database with distributed storage and integrated read scaling.

Two access routes:

Write → Writer endpoint → Primary instance
Read → Reader endpoint → Aurora Replicas
Compute → shared distributed storage

1. Compute is separate from storage

Aurora clusters typically have one writer and up to 15 Aurora Replicas. Instances share distributed storage; Storage expands automatically as data increases.

Storage holds 6 replicas across 3 AZs and automatically corrects failed replicas.

The quorum mechanism is often described as 4 copies for writing, 3 copies for reading; Storage copies are not 6 database instances.

2. Writer and Reader endpoints

EndpointUse when
Writer/cluster endpointWrite or read-write; Points to the current writer
Reader endpointDistribute read connections across replicas
Instance endpointNeed a specific instance
Custom endpointSplit replica groups for a workload

The Reader endpoint is balanced at the connection level, not dividing each SQL query itself.

Without a replica, the reader endpoint can point to the writer; Do not consider the endpoint name as a read-only enforcement mechanism.

3. Failover

When the writer fails, Aurora can promote the replica and update the writer endpoint.

Placing the replica in another AZ helps restore compute faster; Multi-AZ storage by itself does not guarantee uninterrupted connectivity.

App still needs reconnect/retry. Actual failover time depends on the situation; don't consider the quick numbers in the slide as an SLA for every defect.

4. Auto Scaling and custom endpoints

Aurora Auto Scaling increases/decreases the number of readers according to metrics such as CPU or connections. It increases read capacity, unlike Serverless v2 which adjusts the compute capacity of the instance.

Custom endpoints can push heavy reporting into a more powerful replica pool. Reader endpoint still exists; app selects endpoints according to workload.

5. Use cases

Use cases: OLTP requires MySQL/PostgreSQL-compatible and HA; Read-intensive SaaS uses reader endpoint; Separate reporting from transaction query using replica/custom endpoint.

Quick review · SAA-C03

Aurora has its own storage and replication architecture; Reader Endpoint serves read queries, Writer Endpoint is for writes.

Aurora Serverless, Global & advanced capabilities

Purpose: Choose Aurora features that are appropriate for fluctuating loads, global users, and dev/test environments.

1. Aurora Serverless v2

Serverless v2 automatically adjusts compute capacity according to load within the min/max ACU range
configured.
Unpredictable load matching; Still need to choose engine, network, security and limits
capacity. capacity.

Unlike the Auto Scaling: Serverless v2 reader that changes the capacity of the instance, the Auto Scaling reader changes the number of replicas.

The ability to scale to 0/auto-pause depends on engine version and configuration, not by default every cluster stops when idle.

2. Aurora Global Database

Primary Region receives records; Secondary Regions receive data asynchronously to read near users and serve DR.

When the main Region fails, failover/promote the backup Region according to the Global Database process.

Primary Region: writer → replication → Secondary Region: local reads
                                      └─ promote/failover khi DR
Replication is usually very fast but asynchronous still carries the risk of losing changes
not replicated yet.
Evaluate RPO/RTO and failover testing; Do not consider Multi-AZ a substitute for it
cross-Region DR.

3. Database Cloning

Clone uses copy-on-write: initially shares the same data blocks, only providing new blocks when there are changes. Creating a test environment is faster than copying the entire database.

Clone has its own compute and still has costs; query test runs on clone instead
writer production.
Do not consider clones as independent backups instead of snapshots/DRs.

4. Babelfish and Machine Learning

Babelfish helps Aurora PostgreSQL understand part of T-SQL/TDS to reduce the effort to repair SQL Server applications; Must check compatibility features, not guaranteed all apps run as they are.

Aurora ML can call SageMaker/Comprehend via SQL for use case support. This is an integration, not every database has its own prediction model.

5. Use cases

Use cases: Erratic load: Serverless v2. Local global reads and DR: Global Database. Production version for dev/test: clone. Migration of SQL Server needs to reduce code changes: Babelfish review.

RDS/Aurora backup, restore, security & RDS Proxy

Purpose: Restore data, protect connections and avoid database being overloaded by many connections.

1. Automated backups and snapshots

Automated backup combines backups with transaction logs for Point-in-Time Restore (PITR) in the retention window.

RDS DB instances support retention for up to 35 days; Set 0 to disable automated backup in enabled models.

Aurora keeps continuous backups according to configured retention.

Manual snapshots are kept until they are automatically deleted.

Restore creates a new DB/cluster, does not overwrite the running DB; must move the application to the new endpoint after checking the data.

2. Restore and migrate

Wrongly deleting data → PITR before the problem → new DB → check → change app endpoint

Some MySQL restores from S3 use backups created by Percona XtraBackup, requiring correct version/format support. You don't have to upload any dump files to S3 to restore.

Snapshot is different from read replica: replica can replicate mistakenly deleted operations, while backup allows returning to a previous point in time.

3. Network, credentials and encryption

Set DB private, SG only receives from app.
TLS encryption in transit; KMS encrypts when saving and backing up.
If you want to encrypt the old database, usually snapshot → encrypted copy → new restore.

Secrets Manager saves/rotates passwords; IAM DB authentication uses tokens for DB users configured on the supporting engine.

RDS API management permissions do not automatically grant permissions to run SQL in the DB.

4. RDS Proxy

Proxy pool/reuse connection, useful when Lambda/application opens many short connections.

The proxy resides in the VPC, helping to reduce connection storms and improve failover handling; Does not cache SQL results or make heavy queries automatically faster.

Lambda/EC2 → RDS Proxy → connection pool → RDS/Aurora

Passwords can be used with Secrets Manager or IAM authentication according to supported configuration.

IAM is not always required for clients; End-to-end IAM can also unstore passwords in Secrets Manager. AWS RDS Proxy authentication.

5. Operational events and data events

RDS Event Notifications/EventBridge reports DB events such as failover, snapshot creation or state change; Not a stream that changes each row.

Some engines support calling Lambda from SQL/DB logic.
Requires both IAM permission and network connection to Lambda; Private DB can use NAT/VPC
Appropriate endpoints.
If you need CDC, use the CDC tool/stream, don't rely on lifecycle notifications.

6. Use cases

Use cases: Accidentally deleted recovery: PITR. Lambda opened too many connections: RDS Proxy. DB security: private subnet + SG + TLS + KMS + secret management. Failover warning: RDS event → SNS/EventBridge.

Amazon ElastiCache

Purpose: Keep frequently used data in RAM for quick response and reduce the number of database queries.

1. Cache-aside

App → cache: has data → returns results
          └─ not available → read DB → write cache with TTL → return result
The application must add cache read/write logic; ElastiCache does not front itself
database like RDS Proxy.
Select TTL and invalidation to avoid returning old data for too long.

Write-through updates the cache at the same time as writing to the DB, making data available for reading but increasing write work and possibly caching unused data.

Cache-aside only loads when needed but the first read has a cache miss.

2. Redis/Valkey and Memcached

ChooseMain point
Redis OSS/ValkeyData structures, sorted sets, replication/read replicas, Multi-AZ failover and snapshots depending on configuration
Node-based MemcachedSimple key-value cache, sharding, multi-thread; no native replication/failover like Redis

Node-based Memcached does not have backup like Redis/Valkey; Serverless Memcached has snapshot/restore support.

So we need to look at both the engine and the deployment model. AWS backup support.

3. Sessions and leaderboards

Storing sessions in cache helps multiple app instances share the same login state. Redis/Valkey sorted sets are suitable for leaderboards because they store scores and query rankings quickly.

Common read cache reduces repeated queries on RDS.

Read Replica still runs SQL on the DB data; cache stores results/objects for quick retrieval, two solutions can be used together.

4. Security and data may be lost

Use private network, source-limited SG, TLS and appropriate authentication engine/version: AUTH/RBAC or IAM authentication when supported.

IAM cluster management and IAM data authentication are different permissions/configurations.

Designed to tolerate cache misses or cache data loss; For data that needs to be sustainable, there must be a data source/backup that meets the requirements.

Asynchronous replication does not guarantee that all writes will not be lost in case of error.

5. Use cases

Use cases: Product catalog read a lot: cache-aside. Multiple EC2 web needs common session: Redis/Valkey. Game ranking: sorted sets. Simple, renewable cache: Memcached.

Quick review · SAA-C03

ElastiCache Redis/Valkey or Memcached places data in RAM to reduce backend load and reduce latency; DAX is specific to DynamoDB.
