Amazon ECS – Orchestration, tasks, and services

Purpose: Amazon ECS is AWS's container orchestration service. You declare the container you need to run, its quantity and resources; ECS takes care of deploying, monitoring and replacing tasks when they fail.

1. 3 main concepts

ECS conceptNature
Task DefinitionThe blueprint declares the container image, CPU/RAM, ports, environment variables and IAM Roles
TaskAn actual running instance is instantiated from the Task Definition

2. ECS Cluster

Cluster is Logical group contains Service, Task and compute capacity.

3. EC2 vs Fargate

ECS + EC2 = EC2 administrator = instance type + patch + ASG + capacity

ECS + Fargate = AWS manages the server = you only choose CPU/RAM for the Task

Remember:

EC2
→ more controls
→ suitable for stable workload / need to optimize cost

Fargate
→ less infrastructure management
→ suitable for fluctuating workloads

ECS Anywhere and External launch type

ECS Anywhere Allows registering servers/VMs on-premises or outside of AWS to the ECS cluster to manage containers using ECS.

External launch type (EXTERNAL) used to run ECS tasks/services on these external instances; You still manage the server, OS and capacity.

Server/VM outside of AWS
↓ install ECS Agent + SSM Agent, register cluster

↓ launch type: EXTERNAL
Container Tasks on servers outside of AWS

For example, container management processes data at the factory from the ECS while the data remains on-premises.

AWS Fargate

Purpose: AWS Fargate is serverless compute for containers — used with ECS or EKS. You declare the CPU/RAM of task/pod; AWS provision, patch and operate the entire platform server.

Container run flow:

Container image + CPU/RAM
↓ ECS Task / EKS Pod
Fargate
↓
AWS operates compute

1. What is Fargate not?

🧠 Fargate Do not replace ECS/EKS. ECS/EKS is orchestration; Fargate just is launch/compute type — how you run the container, not the orchestration system.

2. Fargate vs EC2 launch type

CriteriaFargateEC2
Server managementAWS takes care of everythingYou manage
Charge unitCPU/RAM of taskInstance hours
Infrastructure controlLow (no SSH)High (SSH, custom)
Appropriate workloadSmall, irregular, serverlessLarge, stable, cost-optimized

3. What does Fargate still need?

VPC + Subnet — each task has its own ENI. Security Group — controls traffic in/out of tasks. IAM role — task execution role + task role. Image — from ECR or other registry. Logs — CloudWatch Logs (via execution role).

4. Fargate + EFS

Fargate task can be mounted Amazon EFS to have persistent shared storage for serverless containers — multiple multi-AZ tasks read/write the same file system.

5. Limits to remember

CPU/RAM must be a supported pair. For example, task 4 vCPU uses 8–30 GB of RAM; This is not Fargate's maximum level. .

Cannot SSH into the underlying infrastructure.

Some workloads need host-level control (eg custom kernel, GPU) → must use EC2 launch type.

6. Use cases

Use cases: 

APIs/microservices run on ECS that the team wants to focus on containers, no
Manage EC2 nodes.
Job on demand: run tasks when there is work; Use EFS if many tasks need it
persistent shared files.

7. Principles for calculating Compute fees on Fargate

Fargate only charges for compute vCPU and Memory allocated during the time the Task/Pod actually runs (don't pay for idle EC2); Expanded storage, data transfer and Load Balancer are charged separately.

Quick review · SAA-C03

Fargate runs containers without needing to manage EC2 hosts; Still have to configure CPU/RAM, network, IAM and scaling of workload.

Amazon ECR

Purpose: Amazon ECR (Elastic Container Registry) is a private Docker/OCI image registry managed by AWS — where container images for ECS, Fargate, or EKS are stored.

1. Typical usage flow

CI build image → push ECR (tag/digest) → ECS/EKS pull → container runs

2. Main point

Image is referenced by tag (vd :latest) or digest (sha256 — immutable, more secure).

Task execution role (ECS/Fargate) needs permissions ecr:GetAuthorizationToken + ecr:BatchGetImage to pull images.

Repository policy Together with IAM, you can control who can push/pull, especially with cross-accounts. Pull errors can also be due to missing NAT routes or ECR VPC endpoints.

Image scanning Vulnerability scanning (basic scan or Enhanced Scanning with Inspector).

Lifecycle policy manually clean up old images (e.g. keep the 5 newest images, delete the rest) — save costs.

Can replicate images to another Region/account; production should pin immutable tag or digest instead of dependency :latest.

Encrypt at rest: AWS managed key or KMS CMK.

3. Security

ClassMechanism
Control planeIAM (create/edit/delete repository)
Data planeRepository policy + IAM (push/pull)
At restSSE with AWS managed key or KMS CMK
In transitTLS (HTTPS)

4. Use cases

Use cases:

CI build/push image into ECR; ECS/EKS pulls according to digest to deploy the correct version.

Repository cross-account with IAM/repository policy; Scan for vulnerabilities and use lifecycle policy to clean up old images.

5. ECR Basic Scanning vs Enhanced Scanning

ECR scan modeScanning Range & Timing
Basic ScanningScan for basic OS packages vulnerabilities when pushing images or upon manual request
Enhanced ScanningIntegration Amazon Inspector to continuously and automatically scan both OS packages and programming language libraries as soon as new CVEs appear
Quick review · SAA-C03

ECR saves container images; ECS/EKS/Fargate uses images to run workloads. Distinguish between repository image and runtime container.

Amazon EKS

Purpose: Amazon EKS (Elastic Kubernetes Service) is a Kubernetes control plane managed by AWS — for teams that need Kubernetes APIs, ecosystem (Helm, operators), and portability.

1. Architecture

AWS-managed control plane (API server · etcd · scheduler)
↓
Workload: EC2 node groups or Fargate pods

2. Three ways to run workloads on EKS

WayDescriptionWhen to use
Managed node groupsAWS manages your ASG+ node (EC2) for youDefault, simplest
Self-managed nodesYou create/manage EC2 nodes yourselfNeeds maximum control
Fargate profilesPod runs on Fargate (serverless)Don't want to manage the node

3. IAM and Kubernetes RBAC

🧠 IAM access does not automatically grant Kubernetes permissions. IAM allows you to call the EKS API (create cluster, describe…); but the permissions in the cluster (get pods, deploy...) are due Kubernetes RBAC decide. Need to map IAM principal → Kubernetes role.

4. EKS vs ECS

CriteriaEKSECS
PlatformKubernetes (open-source, portable)AWS-native, proprietary
ComplexityHigher (learn Kubernetes)Lower, easy to start
EcosystemHelm, operators, tooling K8sLimited to AWS
PortabilityCan run on-prem / other cloudsMainly AWS; ECS Anywhere supports on-premises
When to chooseStandardized K8s, need portabilityWant simple AWS-native

run tasks on external instances; Kubernetes is still the choice when needing the Kubernetes ecosystem.

5. Fargate + EKS

Fargate can be used with EKS Fargate profile (select namespace/label → pod running on Fargate).

EKS is still the control plane layer; Workload must be compatible with Fargate capabilities (eg cannot run daemonset on Fargate).

6. Node groups, networking & persistent storage

1. EKS Node Management

  • Managed Node Group: AWS manages the EC2 Nodes and Auto Scaling Group (ASG) lifecycle.

  • Self-Managed Nodes: Self-manage EC2 Nodes, suitable when deep customization is needed.

  • Multi-AZ: Distribute Nodes in Private Subnets in multiple AZs to increase HA.

  • ALB/NLB: Allows application access from outside.

  • NAT Gateway / VPC Endpoints: Let Nodes/Pods access the Internet or AWS Services when needed.

2. EKS Storage

Kubernetes uses PVC (PersistentVolumeClaim) to request storage.

                      AWS Storage
                      (EBS / EFS / FSx)

Storage

When to use?

EBS

Block Storage, attached to EC2 Node in the same AZ

EFS

Shared File System multi-AZ, multiple Pods can access at the same time

FSx

HPC, high performance or specialized filesystem

EKS Fargate Limitations

  • Does not support EBS Volume: Use EFS if you need Persistent Shared Storage.

  • Does not support DaemonSet: Does not run workloads that require direct management of the host.

  • No need to manage EC2 Nodes: AWS Fargate provides compute.

Quickly remember SAA-C03

  • Managed Node Group → AWS manages EC2 Nodes.

  • EKS EC2 + EBS → Persistent Block Storage.

  • EKS Fargate + EFS → Persistent Shared Storage.

  • HPC + EKS EC2 → FSx for Lustre.

  • Fargate → No EBS, no DaemonSet.

10. Five EKS Compute modes, Autoscaling Streams & Three easily confused Endpoints

EKS Scaling/Compute componentExact role
Kubernetes Metrics ServerCollect actual CPU/RAM of Pods/Nodes assigned to HPA (do not create/delete Pods yourself)
HPA vs VPAHorizontal Pod Autoscaler (HPA) increase/decrease number of Pods; Vertical Pod Autoscaler (VPA) Adjust CPU/RAM requests of each Pod
Cluster Autoscaler vs KarpenterCluster Autoscaler increases/decreases nodes via ASG; Karpenter Direct allocation of EC2 optimizes Pending Pods configuration without being tied to a fixed ASG
EKS Auto ModeAWS automatically manages compute, autoscaling, networking, and core add-ons
Load increases → Metrics Server → HPA increases the number of Pods → Lack of space (Pending Pods) → Karpenter / Cluster Autoscaler adds EC2 Nodes
