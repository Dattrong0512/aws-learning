Amazon DocumentDB

Purpose: Amazon DocumentDB is a managed document database compatible with MongoDB API, used to store data in JSON document format with flexible schema.

DocumentDB = Document Database = MongoDB-compatible = Managed by AWS

1. Document Model

Other relational databases: RDS / Aurora = Table = Row / Column = Clear Schema

DocumentDB: Document = JSON-like object = each document can have different fields

For example:

Product A
{
  name: "Phone",
  color: "Black"
}

Product B
{
  name: "Laptop",
  ram: "16GB",
  cpu: "M3"
}

→ No need for all records to have the same column.

2. MongoDB Compatibility

Applications can use:

MongoDB Driver
↓
DocumentDB

But remember: DocumentDB ≠ MongoDB self-hosted

DocumentDB = AWS service compatible with MongoDB API

So still need to check which MongoDB features are supported.

3. Managed Cluster

AWS admin: Provisioning · Patching · Backup · Replication · Storage scaling

Application still has to worry about: Document Design · Indexes · Queries · Security

4. Availability & Storage

DocumentDB has replication across multiple AZs:

Application
↓
DocumentDB Cluster
↓
Replicas across AZs

Objective: High Availability + Failover

Storage can expand automatically as data increases.

5. Index

If you want to query quickly, you still need an index.

Query by email
↓
Index: email
↓
Search faster

If there is no suitable index:

Full Scan
↓
Query is slow

Managed database does not mean automatically optimized queries.

6. DocumentDB vs RDS vs Neptune

  • RDS / Aurora = SQL = relational = join multiple tables
  • DocumentDB = JSON document = flexible schema = MongoDB-compatible
  • Neptune = Graph Database = relationship / traversal
Bank Transaction
→ RDS / Aurora

Product Catalog
→ DocumentDB

Social Network Relationship
→ Neptune

Quick review · SAA-C03

DocumentDB = document database compatible with MongoDB API; RDS/Aurora = relational SQL; Neptune = graph. Managed does not mean the query is self-optimized.

Amazon Neptune

Purpose: Amazon Neptune is a managed graph database used when data has many relationships and connections between them need to be queried.

Neptune = Graph Database = Node + Relationship

1. Graph Model

Graph includes: Node / Vertex = entity

Edge = relationship between entities

For example:

User A
↓ FRIEND_OF
User B
↓ BOUGHT
Product X

Or:

User
↓ LIKES
Post
↓ HAS_COMMENT
Comment

Neptune is strong when the question needs to go through many relationships.

2. When to use Neptune?

Use cases:

User A
↓ friend
User B
↓ bought
Product X

Query: "What product did User A's friend buy?"

Neptune can traverse the graph directly instead of having to join multiple tables.

3. Use Cases

Social Network
↓
Friend / Like / Share relationships
Fraud Detection
↓
Account → Device → Transaction → Address
↓
Look for suspicious connections
Recommendation
↓
User → Product → Related Product
Knowledge Graph
↓
Entity → Relationship → Entity

4. Availability

AWS admin: Cluster · Replication · Backup · Failover

Read replicas can be used to scale reading workload.

5. Neptune Streams

Neptune Streams = records changes in the graph sequentially.

Graph changes
↓
Neptune Streams
↓
Consumer/Lambda
↓
OpenSearch / S3 / Cache
User A LIKE Product X
↓
Neptune Streams
↓
Lambda
↓
Update Recommendation Index

No need to poll the entire graph to find out what just changed.

6. Neptune vs Other Databases

  • RDS / Aurora = relational SQL
  • DocumentDB = JSON document
  • Neptune = relationship / graph traversal
  • Timestream = data over time

7. Graph query language: SPARQL vs Gremlin/openCypher

Data model on NeptuneQuery language

Quick review · SAA-C03

Neptune is for data with many relationships that need traversal; Different from relational SQL database and document database.

Amazon Timestream

Purpose: Amazon Timestream is a serverless time-series database used to store and analyze timestamp data.

Timestream = Time Series Database = Timestamp + Measurements

1. Time Series Data

For example:

10:00 → CPU = 40%
10:01 → CPU = 55%
10:02 → CPU = 80%

Or IoT: Timestamp · DeviceId · Temperature · Humidity · Battery

Time is the most important part of data.

2. Data Model

A record usually has: Timestamp + Dimensions + Measures

Timestamp = 10:00 · Dimensions: · deviceId = sensor-01 · region = ap-southeast-1 · Measures: · temperature = 30 · humidity = 70

3. Multi-measure Record

If multiple measurements have the same timestamp:

10:00 · Temperature = 30 · Humidity = 70 · Battery = 90%

Can be saved together: 1 Timestamp + many Measures

→ reduce the number of records/writes.

4. Storage Tiering

Timestream divides the data itself:

Recent Data
↓
Memory Store
= query nhanh
Old Data
↓
Historical Storage
= cheaper

You can still query both.

5. Query

Timestream supports SQL for temporal analysis.

Average CPU per 5 minutes · Highest temperature today · Request latency in the last 1 hour

Time-series Data
↓
Timestream
↓
SQL / Aggregation
↓
Dashboard / Analytics

6. Scheduled Query

The query can be run periodically:

Raw CPU Metrics
↓
Scheduled Query
↓
Average CPU every 5 minutes
↓
Summary Table

Suitable for creating aggregates for dashboards.

9. Timestream should not be used for

Customer · Order · Payment Transaction

If this is transactional business data, regular CRUD/relationship is needed.

Those cases are often more suitable for:

RDS / Aurora · DynamoDB

Quick review · SAA-C03

Timestream specializes in time-series data by timestamp; Adapt IoT metrics, monitoring and data that changes over time.

AspectFeatures on Amazon Keyspaces
Platform architectureNoSQL managed, CQL-compatible serverless Apache Cassandra; automatically cloned via 3 Availability Zones with single-digit millisecond latency
On-Demand ModePay according to each actual read/write request, suitable for unpredictable load fluctuations
Provisioned Mode (+ Auto Scaling)Preset read/write capacity for stable load to optimize costs
