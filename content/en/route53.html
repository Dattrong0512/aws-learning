DNS & Amazon Route 53 fundamentals

Purpose: Use easy-to-remember domain names instead of IPs and manage how DNS returns application endpoints.

1. How does DNS work?

DNS translates a name like api.example.com to an IP or destination name.

Resolver asks name servers when there is no cache; The authoritative name server is where the official answer for the zone is located.

Client → DNS resolver → Root → TLD (.com) → authoritative server
       ← IP is cached according to TTL
Client → connects directly to the application

Route 53: managed authoritative DNS, supporting domain registration and health-aware routing.

It returns a DNS answer, not a proxy web request.

2. Records need to be distinguished

RecordMeaning
AName → IPv4
AAAAName → IPv6
CNAMEName → other name; Do not use at zone apex
NSName server is responsible for zone/delegation
Alias of Route 53Point to a supporting AWS resource or appropriate record in the zone; Can be used at apex

For example example.com → ALB uses Alias; www.example.com can use CNAME.

Alias does not arbitrarily point to every hostname outside of AWS like CNAME and is not a direct way to point to EC2's IP using Alias.

3. TTL

TTL: the time the resolver/client can cache the answer.

High TTL reduces DNS queries but is slow to reflect changes; Low TTL supports faster endpoint changes but increases queries.

Record includes name, type, value/target, TTL when applicable and routing policy. Changing DNS does not close open connections and does not force all caches to update immediately.

4. Public and Private Hosted Zones

Public zones serve public domain names on the Internet.

Private zone serving VPC is associated and hybrid network through appropriate Resolver; private names do not automatically open network access to the application.

To get private DNS working in VPC, enable the necessary DNS properties and check the association. A hosted zone only contains records, not where the website is stored.

5. Registrar is different from DNS service

You can buy a domain from another registrar and then use Route 53: create a public hosted zone, update the name servers in the registrar according to the zone's NS.

It is not required to transfer domain ownership to AWS.

6. Use cases

Use cases: Root domain pointing to ALB: Alias. Internal name for database/service: Private Hosted Zone. Public domain purchased outside of AWS: delegate DNS to Route 53.

7. Route 53 A Alias Record Support Destination

Route 53 Alias Record Can be used right away zone apex (example.com — where not created CNAME) and freely point the query to two target groups: (1) AWS Resources is supported (ALB/NLB, CloudFront, API Gateway, S3 Website Endpoint, Global Accelerator, Elastic Beanstalk, VPC Interface Endpoint) and (2) another DNS Record of the same type in the same Hosted Zone.

Quick review · SAA-C03

DNS translates domain names into records; Route 53 manages hosted zones, DNS records, and routing policy. Public and private hosted zones address different needs.

Route 53 routing policies

Purpose: Select endpoints returned in DNS by rollout rate, latency, location or health.

DNS Flow:

Client
↓ DNS query
Route 53 routing policy
↓ returns the appropriate endpoint
Client connects to endpoint

1. Simple

A record has one or more values; The client chooses when receiving multiple values.

Simple does not attach health checks directly to records; Alias ​​has Evaluate Target Health according to supported target types.

Suitable for a simple endpoint, no need for complex selection policies.

2. Weighted

Assign weight to records with the same name/type.
Weight 1 and 9 give a DNS answer rate of about 10%/90%; There is no need for the total weight to be equal
100.
DNS cache makes the actual request rate not absolutely accurate.

Weight 0 is usually not selected when there is a healthy positive weight record.

If all positive record weights are unhealthy, record weight 0 can be considered; If all weights are 0, divide equally.

Do not use weight 0 as an access ban mechanism.

3. Latency-based

Choose the Region with the best measured latency for the query side, not necessarily the closest by geographical distance.

Suitable for apps running multiple regions that need quick response, can combine health to eliminate error endpoints.

4. Failover

Active-passive: if primary is healthy, return primary; If primary fails, switch to secondary according to configured health. Suitable for DR site or backup notification site.

5. Geolocation

Select by queryer's location: continent, country or US state. More specific regions are preferred; create default record for unmatched location.

Content/language matching by country.

DNS routing is not a mechanism to prevent unauthorized access; want to enforce permissions/areas that need to be controlled in the application/edge.

6. Geoproximity

Choose according to the distance between user and resource, with bias to expand/retract service area. Positive bias increases resource traffic, negative bias decreases. Other geolocation is divided by national borders and latency is selected by latency.

7. IP-based

Use CIDR collection to map the query source/client address provided by DNS to the location/endpoint.

Suitable when you know the company's/ISP's IP range and want your own route; The DNS resolver and EDNS client subnet can affect the addresses Route 53 sees.

8. Multi-Value Answer

Return up to 8 healthy records per query when configuring health check. The client connects itself to a value; There is no connection management proxy like ELB.

9. Use cases

Use cases: Canary about 10%: Weighted. Global app prioritizes latency: Latency-based. By language/country: Geolocation. Change service area by bias: Geoproximity. Primary/backup: Failover.

Quick review · SAA-C03

Simple/Weighted/Latency/Failover/Geolocation/Geoproximity/Multivalue are chosen according to traffic navigation goals, not the same type of load balancing.

Route 53 health checks & failover

Purpose: Use health checks to select healthy endpoints and switch to a backup location when a failure occurs.

1. Three ways to determine health

WayWhen used
Endpoint health checkPublic HTTP/HTTPS/TCP endpoint
Calculated health checkCombine the results of multiple health check children
CloudWatch alarm health checkMetric/alarm signal, useful for private resources
Route 53 health checker on the Internet does not go directly to the internal private IP
VPC.
With private apps, you can use monitoring inside VPC → metric/alarm → health
check.

2. Evaluate Target Health

Alias to supported resources such as ELBs can obtain the target's health using Evaluate Target Health, without creating a separate Route 53 endpoint check.

Not all alias targets support this; CloudFront does not support Evaluate Target Health = Yes.

Check the health of a specific endpoint, avoid checking the domain itself that is failing over because the results will depend on its DNS routing. AWS health-check configuration.

3. Active-passive failover

Primary healthy → DNS returns primary
Primary unhealthy → DNS returns secondary according to configured health

Primary needs appropriate health signal: health check or Evaluate Target Health with Alias support. Secondary must be truly ready to serve and have data/capacity that meets DR.

4. DNS has cache

Failover DNS only changes the answer for the next query; Do not transfer current connection
open.
TTL, error detection time, and client retry all affect interruption time
paragraph.

If all endpoints are unhealthy, Route 53 has fail-open behavior depending on the policy; Do not consider health check as a firewall that always blocks all faulty endpoints.

5. Use cases

Use cases: Active-passive between two Regions; primary ALB and static recovery page; Calculated checks reflect multiple dependencies. Try actual DR, checking both DNS and database and application status.

Quick review · SAA-C03

Route 53 health check supports DNS failover; DNS caching/TTL affects redirection speed and DNS does not automatically regenerate failed infrastructure.

Hybrid DNS & Route 53 Resolver

Purpose: For AWS and on-premises to resolve each other's private domain names.

1. Resolver in VPC

Route 53 Resolver handles AWS-provided names, public DNS and associated Private Hosted Zone. VPN/Direct Connect connection creates a network connection but does not automatically make all private DNS on both sides understand each other.

2. Inbound endpoint

Inbound: query direction going into AWS: DNS on-prem forward domain AWS/private zone to the IP of the inbound endpoint.

On-prem machine → DNS on-prem → VPN/DX → Inbound endpoint → Private Hosted Zone

There is no need to turn private records into public for internal users to look up.

3. Outbound endpoint

Outbound: Query direction going out of AWS: Resolver forwarding rule selects suffix like corp.example.com and then sends query through outbound endpoint to DNS on-prem.

EC2 → VPC Resolver → rule for corp.example.com → Outbound → DNS on-prem

The rule must be associated with the VPC in use; can share cross-account rules via AWS RAM.

4. Availability and network

Use IP endpoints in at least two AZs, SGs for DNS TCP/UDP 53 and VPN/DX lines to the DNS server. Check route/firewall both ways.

Do not forward the same domain around to both sides and then back to yourself. Resolvable DNS still needs route/SG to connect to the return IP.

5. Use cases

Use cases: On-prem look up the private database name in AWS: Inbound. EC2 looks up Active Directory domain on-prem: Outbound + forwarding rule. Multiple accounts share the same hybrid DNS: share rules.

6. Three types of Resolver Rule: Forward Rule, System Rule & Delegation Rule

Ingredients / RulesDistinguishing function
Inbound EndpointReceive DNS queries from On-premises going into VPC Resolver (Private Hosted Zone resolution)
Outbound Endpoint + Forward RulePass the DNS query of the specified domain (eg corp.example.com) from VPC to DNS Server On-premises IP
System RuleKeep a specific subdomain (eg aws.corp.example.com) back to AWS VPC Resolver to process, causing an exception to override the parent Forward Rule
Delegation RuleAuthorize subdomain resolution based on records NS to the authoritative DNS server via Outbound Endpoint
Quick review · SAA-C03

Inbound Resolver Endpoint: query from on-prem to AWS; Outbound Endpoint + forwarding rule: query from VPC to DNS on-prem.
