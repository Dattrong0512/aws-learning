AWS Global Infrastructure fundamentals

Purpose: Understand where AWS places resources to choose the right deployment location, reduce latency, and avoid service outages when problems occur.

1. Region and Availability Zone

Region: a geographical area, for example Singapore.

Each Region has many Availability Zones (AZ); Each AZ includes one or more data centers with independent power sources and connections.

AZs in the same Region are connected by a low latency network.
EC2, EBS and subnet are in one AZ; Other services may have a Region scope
or global.

2. Multi-AZ and Multi-Region

Multi-AZ: run the application in multiple AZs in the same Region. If one AZ fails, the other AZ will continue to serve, if the application still has enough capacity and the data is protected.

Multi-Region: Deploy in many Regions to serve global users or restore when the whole Region has problems.

Must consider additional costs and ways to synchronize data.

User → Load Balancer
                ├─ EC2 is in AZ A
                └─ EC2 in AZ B

3. Select Region

Consider the user's location, what country the data request must be in, whether the service needed is available and the cost.

Edge location is used to bring content/services closer to users; not an AZ to place EC2 yourself.

AZ names like ap-southeast-1a may map differently between accounts. When you need to compare the same physical location between accounts, use AZ ID.

4. Use cases

Use cases: The website needs to tolerate one data center: ALB and EC2/ASG across at least two AZs, the database has Multi-AZ. Global application needs to recover when Region fails: add DR architecture in another Region.

Quick review · SAA-C03

Region is a geographical area; AZ is a separate error domain in Region. Multi-AZ handles AZ errors, while Multi-Region extends recovery capabilities when the entire Region fails.

IAM identities: Root, Users & Groups

Purpose: Determine who is using AWS and manage the rights of each person in the account.

1. AWS account and root user

ConceptNature & Scope
AWS AccountThe isolation unit contains resources and billing on AWS
Root UserThe account's special identity has very broad permissions, only used for tasks that require root privileges

Turn on MFA for root, protect recovery information, do not create root access keys and do not use root for daily work.

Do not treat the root user as a way to bypass all protection mechanisms: SCP and some mechanisms such as S3 Object Lock Compliance can still limit operations.

2. IAM Users and Groups

IAM IdentityFeatures & Rules
IAM UserLong-term identity; can have password (to Console) and/or access key (API/CLI call — two separate credential types)
IAM GroupGroup IAM Users to grant common permissions; A user can belong to many groups, but the group cannot nest another group and does not contain an IAM Role
Group Developers → policy allows viewing EC2

                 └─ User Binh

3. Login for employees

Prioritize IAM Identity Center or federation: employees log in and receive access to roles with temporary credentials.

No need to create and share long-term access keys for each person.

If using IAM User, log in with account ID/alias, user name and password. Each session only has permissions for the identity/role in use.

4. IAM is global in scope

No need to recreate IAM User in each Region. However, the accessed resource may be located in a specific Region and the policy may limit that scope.

5. Use cases

Use cases: The audit team uses read-only roles; The development team has limited permissions according to the environment. Use groups to manage common rights for existing IAM Users; Use Identity Center to manage employee access across multiple accounts.

Quick review · SAA-C03

IAM User is a long-term identity; Group collects Users; IAM Role grants permissions through a temporary session. Employees with multiple accounts should prioritize Identity Center.

IAM policies, Roles & permission model

Purpose: Grant the right permissions, on the right resources, without having to share passwords or access keys.

1. Read a policy

Policy: JSON rule set.

Each Statement answers: allow or prohibit, what to do, on what resources and under what conditions.

FieldMeaning
EffectAllow or Deny
ActionAPI/action, e.g. s3:GetObject
ResourceResource ARN; object ARN is different from bucket ARN
ConditionConditions like MFA, IP or tag
PrincipalWho is authorized; appears in resource/trust policy, not in identity policy

The commonly used version is 2012-10-17; This is the policy language version. For example, the identity policy only allows reading objects in a prefix:

{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::example-bucket/reports/*"}]}

2. Identity policy and resource policy

Identity policy attached to user/group/role: what does this identity do? A resource policy is attached to a bucket, queue or key and specifies who may access that resource.

With direct cross-account access, Allow is often needed on both the identity and
resource side.
KMS also has its own key policy; Having S3 permissions may not be able to decrypt the object
SSE-KMS.

3. How to consider rights

If there is no appropriate Allow, it will be denied by default.

Explicit Deny wins over Allow.

Rights are also limited by SCP, permissions boundary or session policy where those mechanisms apply; they are not self-authorizing.

Least privilege means only granting actions and resources that are truly needed, instead of using * for everything.

4. Role and STS

Role is an identity that is assumed when needed.
Trust policy determines who gets assumed; Permission policy determines what role to do
what.
STS issues temporary access keys, secret keys and session tokens.
EC2/Lambda/user → assume role → temporary credential → call AWS API

IAM Roles Anywhere

IAM Roles Anywhere for the server, container or application to run outside of AWS Use IAM roles to receive temporary credentials, instead of keeping long-term access keys.

Other on-premises / cloud applications + X.509 certificate
↓ authenticate with the registered CA as trust anchor

Requires a valid certificate from a trusted CA and an appropriate role trust policy. For example, on-premises server uploads backup to S3.

6. Service-Linked Role

Service-Linked Role (SLR) is a type of service role that is specifically associated with an AWS service. That service assumes the role to operate on AWS resources for you; AWS defines the necessary trust and permissions.

For example, Auto Scaling Group needs permission to launch, terminate EC2, and register/unregister instances with the load balancer. SLR provides these rights; The EC2 Instance Role remains application-specific within EC2.

AWS serviceSLR is used for
EC2 Auto ScalingManage EC2 lifecycle and register instances with load balancer
Elastic Load BalancingManage AWS resources needed by the load balancer, such as network interfaces
Application Auto ScalingScale the resources of supported services, for example ECS service or DynamoDB

Many services automatically create SLRs when needed if the configurator has permission iam:CreateServiceLinkedRole. Do not manually edit permissions managed by the service. · ·

7. Use cases

Use cases: EC2 reads an S3 prefix using the instance role; Lambda logs using execution role. Deploy to another account using AssumeRole, with appropriate trust policy and assume rights on both sides.

IAM credentials, authentication & security tools

Purpose: Log in and call AWS securely, and find credentials or permissions that are no longer needed.

Two main ways of access:

Console → password + MFA
CLI / SDK → credentials → AWS API

1. Console, CLI and SDK

Console
= browser interface; CLI runs command; SDK calls AWS from code.

CLI/SDK uses temporary credential from SSO/role or long-term access key, IAM User access key is not required.

Temporary credentials include access key ID, secret access key and session token. Do not hard-code credentials into the application; Do not commit the credentials file.

2. MFA and password policy

MFA requires additional authentication factors in addition to passwords.

Prioritize MFA for root and high privileges.

IAM's password policy controls IAM User password length, complexity, expiration, and reuse; Does not replace MFA and does not apply to all federation systems.

3. Profile and CloudShell

CLI profile separates configuration between accounts/roles. aws configure sso set up SSO; aws configure can store access keys in ~/.aws/credentials and Region configuration in ~/.aws/config.

CloudShell: terminal in Console, has CLI available and uses current login session permissions.

It does not grant itself administrative rights.

4. Permission checking tool

ToolsUsed to
Credentials ReportView IAM User password, access key and MFA status for the entire account
Access AdvisorView service usage information to consider narrowing permissions
IAM Access AnalyzerIAM Access Analyzer is a service that helps analyze AWS access permissions, detecting permissions that are too broad, permissions that are not in use, or resources that may be accessed unintentionally.

Usage data is the basis for review, not the reason for immediate removal: some tasks only run monthly or when DR.

5. Use cases

Use cases: Employees use SSO profiles for CLI; workload uses role. Check access keys that have not been used for a long time, delete excess keys and reduce permissions after checking actual needs.

Quick review · SAA-C03

Console uses interactive login; CLI/SDK can use temporary credentials. Access Analyzer checks permissions; Credentials Report checks IAM User information.
