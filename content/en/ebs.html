Amazon EBS: persistent block storage

Purpose: Provide durable disk for EC2, used for operating system, filesystem and database.

Usage flow:

EC2
↓ attach block volume in the same AZ
EBS
↓
Filesystem/Database

1. Volume belongs to one AZ

EBS: block storage over the network.

Volume and EC2 must be in the same AZ; Usually a volume is attached to one instance, an instance can have many volumes.

Volume remains when the device is stopped.

When terminating, DeleteOnTermination decides whether to delete the volume; root is usually on, data volume is usually off.

Check the property instead of assuming that the data is always present.

2. Select volume type

TypeSuitable
gp3Universal SSD; Configure capacity, IOPS, and throughput separately
gp2Universal SSD; Baseline IOPS depends on capacity, small volumes have bursts
io1/io2Provisioned IOPS for stable I/O; io2 for databases needs low latency and high durability
st1HDD for large data, frequent sequential read/write
sc1HDD for rarely accessed data, prioritizing cost
SSD can be used as a boot volume; st1/sc1 is not used as a boot volume.
IOPS is the number of operations per second; throughput is the amount of data per second.
Database random I/O is different from processing large files sequentially.

4. gp3 and volume expansion

Baseline gp3: 3,000 IOPS and 125 MiB/s.

You can buy more performance without having to increase disk space just to get IOPS.

The current gp3 limit has increased compared to the old slide; see AWS EBS gp3 during actual configuration.

Elastic Volumes allows increasing capacity or changing performance/type while the machine is running; may need to expand partition/filesystem in OS.

EBS charges based on the capacity allocated, not just the number of bytes in use.

5. Multi-Attach

io1/io2 supports mounting the same volume to up to 16 Nitro instances in the same AZ when the configuration is supported.

Machines can read/write, but the application must have locking and filesystem cluster-aware to avoid data corruption.

Multi-Attach does not turn EBS into a multi-AZ shared file system. Multiple Linux servers sharing the same files are often more suitable for EFS.

6. Use cases

Use cases: Boot disk/dev server: gp3. Database on EC2 needs consistent I/O: io2. Log or sequential big data: st1. Want to transfer AZ: snapshot and then create a new volume in the destination AZ.

EBS snapshots, AMI & encryption

Purpose: Backup disk, create a consistent machine, and protect EBS data with encryption.

1. Snapshot

A snapshot is a copy at a point in time.
The first snapshot of the block copy contains data; Next time save the changed block.
Deleting old snapshots does not eliminate the ability to restore from remaining snapshots.

It is not required to remove the volume for snapshots. If you want to backup consistently with the database, you need to flush/quiesce the appropriate application or backup process. Snapshots do not contain RAM.

Volume can be created in another AZ from snapshot.

Copying snapshot to another Region/account requires appropriate sharing and KMS permissions; snapshots using AWS managed keys are not shared cross-account like customer managed keys.

2. Backup features

FeaturesSolve the problem

Recycle BinRecover accidentally deleted snapshots/AMIs if retention rules are in place

EBS Snapshot Archive

EBS Snapshot Archive is a lower-cost storage class for snapshots that rarely need to be restored, such as long-term backups.

If you permanently delete or restore to Standard before 90 days, you will still have to pay the Archive fee for the remaining time. Because Archive saves full snapshots, the billed capacity may be larger than the incremental version; Need to consider both capacity and restore fee.

3. AMI

AMI: EC2 creation sample: OS, software, configuration and disk information.

With EBS-backed AMI, disk data resides in EBS snapshots.

Install and configure EC2 → create AMI → Launch Template → ASG create the same machine

AMI has a Region scope; Copy to another Region before using there. Update AMI and patches periodically, do not leave secrets in the image.

4. Amazon Data Lifecycle Manager (DLM)

Amazon DLM automatically create, retain and delete EBS snapshots / EBS-backed AMIs according to policy; No need to write your own Lambda or cron for a simple backup schedule.

EC2 + EBS volumes
↓ DLM policy: backup every day
EBS snapshots
↓ keep 7 days
Automatically delete expired snapshots
FunctionMeaning
ScheduleCreate scheduled snapshots or EBS-backed AMIs; Select resources by policy/tags
RetentionKeep by number of copies or time, depending on policy
DeleteDelete expired snapshots; deregister AMI and process related snapshots according to policy
CopyCopy snapshot to another Region according to support policy

DLM manages copies created by DLM itself; Do not self-manage snapshots/AMIs created in other ways and do not use Instance Store-backed AMIs. Choose AWS Backup when you need centralized policies for multiple services.

5. EBS encryption

KMS protects volumes, snapshots, and data transfers between EC2/EBS.
Snapshots from encrypted volumes are also encrypted; volume created from encrypted
snapshots hold encryption.

Do not turn on encryption directly on the old unencrypted volume: snapshot → copy encrypted snapshot → create a new encrypted volume → replace volume.

The role needs KMS permission to use the key.

6. Use cases

Use cases: Golden AMI for ASG; cross-Region snapshot/copy for DR; Recycle Bin prevents accidental deletion; Convert legacy disk to encrypted volume using snapshot.

EBS vs EFS vs Instance Store

Purpose: Distinguish between private disks, shared files and temporary disks to avoid choosing the wrong place to save data.

Three ways to save data:

EBS = block volume for EC2
EFS = shared file system
Instance Store = temporary disk on the host

1. Key comparison

CriteriaEBSEFSInstance Store
TypeBlock disk over the networkShared file system NFS/POSIXLocal block disk on the host
ShareUsually an EC2; Conditional Multi-AttachMultiple Linux clients mounted togetherAttach to instance/host
ScopeOne AZMulti-AZ Regional or One ZoneA host
After stop/host errorEBS retains data, except for configuration deletionIndependent of EC2All data may be lost
Used forBoot disk, databaseShared content, home directory, containersCache, buffer, scratch

2. How does EFS work?

Create a mount target in AZ, enable NFS 2049 via SG and then mount from the Linux client. EFS automatically increases/decreases capacity according to the file, without needing to allocate volume size first.

Regional EFS saves across multiple AZs for better fault tolerance.

One Zone is cheaper but doesn't want to lose the whole AZ.

Encrypt at rest using KMS; You can turn on encryption in transit and use access points to limit paths/permissions.

3. Performance and EFS costs

General Purpose is suitable for most latency-sensitive applications. Max I/O is the choice for some very large parallel workloads, with higher latency.

Elastic throughput adjusts itself according to load; Provisioned sets its own throughput level; Bursting ties throughput capacity to saved data and burst credits.

Lifecycle can transfer files to IA/Archive to reduce storage fees, in exchange for access fees and class conditions.

4. Instance Store

Very fast because the disk is near the compute.
Data may remain after reboot but is lost when stopped, hibernate, terminate or otherwise
hardware error.
Do not save single copies of important data; Use backup/replication or
other data sources.

5. Use cases

Use cases: WordPress or multiple ECS tasks need to see the same file: EFS. Private database on an EC2: EBS. Handles reproducible intermediate data: Instance Store. Windows SMB share: see FSx for Windows File Server.
