S3 encryption, HTTPS & CORS

Purpose: Protect content stored in S3, encrypt transmission and let the browser access the correct origin.

1. Encryption at rest

WayWho manages the key?Point to understand
SSE-S3S3/AWSAES-256 server-side encryption; default for new objects
SSE-KMSAWS KMSControl key policy, audit key usage, have KMS permission/quota/cost
SSE-CCustomersSend key per request over HTTPS; S3 does not save keys for future use
Client-sideApplication/clientEncrypt before upload; S3 only receives ciphertext

Encryption does not grant access on its own and does not change bucket policy. Changing the default encryption does not automatically re-encrypt any old objects with the new type/key.

2. SSE-KMS

Upload needs appropriate permissions like kms:GenerateDataKey; reading requires kms:Decrypt.
Cross-account access requires S3 permission and customer managed KMS key
permission from the other side.

KMS's request rate may become limited when S3 traffic is large.

S3 Bucket Keys help reduce KMS requests and SSE-KMS costs when appropriate; must still keep the correct key policy.

3. HTTPS

TLS/HTTPS protects transmission. Bucket policy can be explicit Deny if aws:SecureTransport=false to deny HTTP.

Client --HTTPS--> S3 --server-side encryption--> object is saved
S3 website endpoint does not support HTTPS directly; Use CloudFront for your website
HTTPS.
SSE-C requires HTTPS and must keep the key secure. If the key is lost, it cannot be decrypted.

4. CORS

Origin includes protocol, host and port. The web at https://app.example.com calling S3 at another origin needs CORS on the destination bucket with the appropriate origin/method/header.

CORS is a browser rule for reading responses, does not grant S3 permissions and does not prevent any clients outside the browser. Pre-signed URL/bucket policy must still allow action first.

5. Use cases

Use cases: Need control/audit key: SSE-KMS. Browser uploads directly to S3: pre-signed PUT + CORS. Data must be encrypted before reaching S3: client-side. Only for secure transmission: policy enforces HTTPS.

Quick review · SAA-C03

SSE-S3/SSE-KMS/SSE-C is server-side encryption; HTTPS protects in transit; CORS is a browser mechanism, not IAM permission.

S3 versioning, replication & immutable protection

Purpose: Recover an overwritten/wrongly deleted object that has a copy elsewhere and keep the data from being destroyed prematurely.

Three different mechanisms:

Versioning = keeping versions
Replication = copy to another bucket
Object Lock = version protection by retention

1. Versioning

Turn on in bucket to keep multiple versions of the same key. Overwrite creates new version; DELETE normally adds a delete marker, not immediately deleting old versions.

Restore by getting the old version or deleting the appropriate delete marker. Deleting with version ID can permanently delete that version. Suspend Versioning does not automatically delete existing versions.

2. CRR and SRR

CRR replicate to another Region; SRR replicates in the same Region.

Can cross-account, needs Versioning at source/destination with appropriate roles and policies; The SSE-KMS object also needs KMS configuration/permissions.

Asynchronous replication: does not promise data to appear immediately.
By default, the live replication rule applies new objects after enabling it; old object used
S3 Batch Replication.

3. Delete and replicate

Delete markers can be replicated if appropriate options and rules are enabled. Permanently deleting a version at the source does not automatically replicate that deletion to the destination.

There is no automatic chaining: object replicate A → B does not continue on its own to B → C
just because B has a rule to C.
If you want multiple destinations, configure appropriate replication from the source.

4. MFA Delete

MFA required when permanently deleting version or changing Versioning status. MFA is not required just to add a regular delete marker.

Bucket owner/root enables or disables MFA Delete via API/CLI with MFA, not via S3 Console. Versioning must be enabled.

5. Object Lock

WORM protects each version; Need Versioning.

Can be enabled for new or existing buckets according to the support process; Once enabled, do not turn off Object Lock/Versioning in the usual way.

MechanismMeaning
Governance retentionPeople with appropriate bypass permissions can bypass protection
Compliance retentionNo one, not even root, can remove/shorten the retention of the locked version
Legal holdHold until the person with the right to remove the hold; independent of retention date
Locking an existing version still allows writing a new version with the same key.
Legal hold does not expire; Expired retention may not be deleted if legal
hold is still on.

6. Use cases

Use cases: File is overwritten: Versioning. DR/compliance multiple Region: CRR. Anti-ransomware backups or records should remain intact: Object Lock, limited permissions and appropriate policy retention.

Quick review · SAA-C03

Versioning keeps multiple versions; Replication copies objects between buckets; Object Lock protects instances from deletion/editing according to retention.

S3 events & service integrations

Purpose: Automatically handle new or changed objects, instead of constantly checking the bucket.

1. Event stream

Upload object → S3 event → SQS / SNS / Lambda / EventBridge
                           └─ processor reads object from bucket

Event describes the bucket/key/version and operation, not the entire file content. Prefix/suffix can be filtered to only process uploads/ or .jpg.

2. Select destination

SQS serves as a buffer for workers; SNS fan-out; Lambda processing directly; EventBridge has rules/filters and many target types.

The direct SQS/SNS/Lambda destination must be in the same Region as the bucket according to the supported configuration.

S3 does not send directly to the SQS FIFO; Use EventBridge if you need a FIFO target. AWS notification destinations.

3. Where is Permission located?

Destination resource policy for s3.amazonaws.com permissions sqs:SendMessage, sns:Publish or lambda:InvokeFunction.

Limited by source bucket ARN and source account; The purpose of using KMS also requires appropriate key permission.

The consumer role is another layer: the worker/Lambda needs permission to read the object and decrypt it if necessary. Policy for S3 to broadcast events does not automatically grant file reading permissions to consumers.

4. Duplicate events and loops

Event can be delivered more than once and the global order is not guaranteed. The consumer must be idempotent: reprocessing the same object/version does not create unwanted duplicate effects.

Separate input/output prefix or bucket. Lambdas that write thumbnails to the same prefix that are triggering can call themselves indefinitely.

5. Use cases

Use cases: Upload photo → thumbnail. New file → SQS → worker processing with retry. Event by object type → EventBridge → Step Functions for multiple steps.

Quick review · SAA-C03

S3 Event Notifications and EventBridge/SNS/SQS/Lambda for asynchronous processing; Need to understand retry capabilities and how to handle duplicate events.

S3 performance, Requester Pays & Batch Operations

Purpose: Speed up file transfers, manipulate multiple objects, and choose which side pays the cost of reading data.

Tools according to your needs:

Multipart Upload = split file into multiple parts
Byte-range GET = read part of object
Transfer Acceleration = transfer acceleration across the edge
Batch Operations = process multiple objects
Requester Pays = requester pays request/data transfer fee

1. Request rate by prefix

S3 supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD per second per partitioned prefix.

Distributing workload across multiple prefixes helps increase total throughput; When scaling quickly, you may encounter 503 Slow Down and need to retry/backoff.

Prefix: the beginning of the object key, not the physical folder.

With SSE-KMS, the KMS request quota must also be considered.

2. Multipart Upload

Split object into parts to upload in parallel; If the part is defective, just send that part back.
Usually worth using from about 100 MB, required when exceeding the 5 GB single PUT limit.

The maximum object is now 50 TB via multipart, instead of 5 TB in the old document.

Configure lifecycle cleaning incomplete multipart upload to avoid unfinished part fees. AWS object upload limits.

3. Transfer Acceleration and byte-range GET

Transfer Acceleration receives data at the edge location and then uses the AWS network to reach the bucket, allowing uploading from remote locations via the Internet; must turn on the bucket and measure the benefits versus costs.

Multipart combinations are possible.

Byte-range GET takes part of an object or multiple ranges in parallel, reading header/file chunks and speeding up download; error just retry the corresponding part.

4. Batch Operations

A job includes a manifest object, action, and IAM role.

Used to copy, change tags, restore archive or invoke Lambda on many objects; service tracks and generates completion reports.

Use Inventory/Athena to select objects into the manifest when appropriate. Changing the old encryption object usually requires copy/rewrite, not just changing the default encryption in the bucket.

5. Requester Pays

Authenticated requesters pay request and download fees; The bucket owner still pays for storage. Requester must confirm payment; anonymous access is not supported.

This is a fee mechanism and does not grant permission to read the bucket. Still need policy to allow requests.

6. Use cases

Use cases: Large video: multipart. Upload from multiple continents: try Transfer Acceleration. Retag millions of objects: Batch Operations. Divide large dataset to another account: Requester Pays.

7. Parallel download using S3 Byte-Range Fetches

S3 Large Object
  ├─ HTTP Range: bytes=0-99MB → Worker 1
  ├─ HTTP Range: bytes=100-199MB → Worker 2
  └─ HTTP Range: bytes=200-299MB → Worker 3
  ↓ Merge order at client → Increase download throughput & retry only error parts
Quick review · SAA-C03

Increase S3 performance by designing appropriate requests/transfers; Batch Operations deal with batches of objects, not single direct API reads.

1. IAM policy, bucket policy and ACL

IAM policy grants permissions to users/roles; bucket policy grants permissions from the resource side, useful for cross-account or AWS services.

Explicit Deny still beats Allow; SSE-KMS adds a key permission layer.

Bucket ARN is used for bucket level actions like ListBucket; object ARN is used for
GetObject/PutObject.
Do not confuse arn:aws:s3:::bucket with arn:aws:s3:::bucket/*.

S3 ACL — permissions on bucket or object

S3 ACL (Access Control List) grant basic permissions to AWS accounts or supported groups on buckets or individual objects; Does not have the same level of detail/conditions as IAM and bucket policies.

TypeScope and examples
Bucket ACLPermissions at the bucket level: READ allows listing objects; Do not allow yourself to read the content of every object.
Object ACLPermissions on each object: READ to read file; READ_ACP/WRITE_ACP to read/edit ACLs.
READ = list bucket or read object, depending on ACL type
WRITE = create/delete object at bucket level; Does not apply to Object ACLs
READ_ACP = read ACL
WRITE_ACP = edit ACL
FULL_CONTROL = full ACL permissions applicable to that resource

2. Pre-signed URL

The backend signs the URL for an action/key for a limited time.

The person with the URL uses signer rights for that request, without needing to receive an access key; The URL is a bearer token so it must be kept private.

The URL does not override the signer's authority and may expire early when the temporary credential expires.

With SigV4 and IAM User credential, the maximum period is usually 7 days; Don't consider every URL to live 7 days.

Pre-signed URLs are not disposable by default. Upload browser needs proper CORS in addition to PutObject permission.

3. Access Points

Each Access Point has its own hostname and policy for the application/team, pointing to the same
a bucket.
Bucket policy and access point policy must coordinate; Access Points are not bypassed
bucket guardrail.

VPC-only Access Point limits access through the specified VPC, combining VPC Endpoint and endpoint policy.

Having a route to S3 still requires full IAM/bucket/access point/KMS permissions.

Multi-Region Access Point (MRAP)

MRAP provides a global endpoint for S3 buckets in many Regions. The request itself goes through the AWS network to the bucket with the lowest network latency among the available buckets active routing status; Integrated automatic MRAP AWS Global Accelerator.

MRAP does not select a bucket based on whether the object exists or not: GET can return 404 If the selected bucket does not have an object. For example, US and Singapore users use the same endpoint to read replicated data in two Regions. ·

From November 7, 2025, the feature is only available to existing customers and certain qualified partners.
