AWS Well-Architected Framework & Tool

Purpose: AWS Well-Architected Framework helps evaluate architecture according to best practices instead of just looking at individual services. AWS Well-Architected Tool turns that review process into trackable workloads, questions, risks, and improvement plans.

1. 6 pillars

The six pillars are not separate trade-offs; Good design often makes them support each other.

Operational Excellence
= operate, observe, automate and continuously improve

Security
= identity, data, system and access control protection

Reliability
= fault tolerance, recovery and response to changing needs

Performance Efficiency
= use resources of the right type, right size, at the right time

Cost Optimization
= achieve business goals at reasonable costs

Sustainability
= reduce environmental impact by using resources efficiently

Pillars = an architectural testing system, not a checklist to memorize line by line.

2. Workload review

Workload is a set of resources and code that delivers business value, for example a web app, backend process or data pipeline.

The tool does not edit the architecture itself and does not replace the architect review; it standardizes questions, saves decisions, and points out areas for improvement.

3. AWS Well-Architected Tool

Well-Architected Tool is a free service in AWS Console to review workloads according to 6 pillars and related lenses.

Common process: Select workload · Answer questions · Review results by pillar · Generate report · Track improvement status

Dashboard displays total workload and number of high/medium risk issues; Report helps share results with people who are not directly accessing the tool. AWS WA Tool

4. Access and scope

IAM controls who can create, view, edit, or share review workloads. Review answers are architectural information, so do not enter unnecessary secrets, passwords or sensitive data.

The tool mainly works on metadata and review responses; it does not install agents into your workload and does not grant data-plane permissions to your application.

Console/API access using TLS; The power to improve the actual architecture still lies with the target services such as IAM, VPC, RDS, S3 or CloudFormation.

5. Use cases

Use cases:

  • Review a workload before production launch to find high risk issues regarding security, reliability or cost.
  • Track architectural improvements each sprint using improvement plans and milestone/report.
  • Standardize reviews of multiple workloads within an organization, instead of each team using its own checklist.

AWS Trusted Advisor

Purpose: AWS Trusted Advisor audits accounts at a high level and provides recommendations to improve costs, security, performance, fault tolerance, service quotas, and operations.

1. Account assessment

Trusted Advisor does not need to install agents into EC2; It reads the configuration and resource status in the account to create recommendations.

AWS account
↓
Trusted Advisor checks
↓
Recommendations
↓
Review / remediate

For example, checks can detect public snapshots, IAM root access keys, service quotas near limits, or resources that can optimize costs.

Trusted Advisor is a recommendation tool, not a guardrail that blocks incorrect operations at deployment time.

2. Check categories

Common main categories: Cost Optimization · Performance · Security · Fault Tolerance · Service Quotas · Operational Excellence

CategoryArchitectural example
SecurityCheck for risky public or credential configurations.
Fault ToleranceRemind the design to be more fault tolerant, for example backup or Multi-AZ are suitable.
Service QuotasWarning about quota almost running out before scaling gets stuck.
Cost OptimizationFind idle resources or more economical options.

3. Support plan and API

In the console, the level of checks available depends on the support plan. Full check set and permission to use Trusted Advisor/Support API require appropriate support plan such as Business Support+, Enterprise Support or Unified Operations.

Programmatic access is useful when you want to get recommendations for multiple accounts or integrate with internal dashboards. Trusted Advisor API

4. Access and security

IAM controls who can see the Trusted Advisor and call the API. With multiple accounts, administrators often aggregate data through AWS Organizations and appropriate cross-account permissions.

Trusted Advisor recommendations may contain resource configuration information, so view permissions should only be granted to those who need to operate them. Console/API access using TLS; True remediation still requires permissions on the target service.

5. Use cases

Use cases:

  • Account review periodically to detect S3/EBS/RDS public exposure, quotas are about to be full or resources are costing money.
  • Security team gathers Trusted Advisor findings from multiple accounts to prioritize remediation.
  • Before scaling a workload, check service quotas and fault-tolerance recommendations to avoid errors when increasing load.
