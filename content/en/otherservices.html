AWS CloudFormation

Purpose: Write AWS infrastructure into code to create/update resources automatically, instead of manually configuring on Console.

YAML / JSON Template
↓
CloudFormation
↓
Stack
↓
AWS Resources

Templates and Stack

Template = YAML/JSON file describing the infrastructure to create.

For example:

VPC · EC2 · ALB · RDS

Stack = real resources created by CloudFormation from templates.

The same template can be used for: Dev · Test · Prod

Common parts:

  • Resources = resource to create

  • Parameters = input

  • Outputs = output, for example endpoint

  • Conditions = condition whether to create a resource or not

Change Set and Rollback

Change Set = CloudFormation preview will:

Add · Modify · Delete · Replace

any resource before updating.

Rollback = if update fails, CloudFormation tries to return the stack to the previous state.

Rollback is not a data backup.

DeletionPolicy

  • Retain = delete stack but keep resource

  • Snapshot = create a snapshot before deletion if the resource supports it

StackSets

= deploy the same CloudFormation template to:

Multiple AWS Accounts · + · Multiple Regions

Suitable for AWS Organizations / multi-account.

Drift Detection

Drift = The real resource is edited differently from the template.

For example:

Templates:
SG permit 443

Someone edit Console:
SG allow 22

→ Drift

Drift Detection help detect that difference.

Infrastructure Composer and Service Role

Infrastructure Composer = intuitive interface for designing CloudFormation templates.

Service Role = IAM Role that CloudFormation uses to:

Create · Update · Delete

AWS resources.

Remember quickly

  • CloudFormation = Infrastructure as Code
  • Template = YAML/JSON blueprint
  • Stack = resources are created from template
  • Change Set = preview changes
  • Rollback = update error → return to previous state
  • StackSets = deploy multiple accounts/Region
  • Drift Detection = detected that the resource was edited differently from the template

Memory sentence: Template → CloudFormation → Stack → AWS Resources

6. Automation

Automation Runbook is a multi-step automation script AWS Systems Manager Automation execute in a specified sequence/flow to manage AWS resources.

Instead of the admin manually manipulating each step, the runbook runs the entire process itself; can call AWS API, run script, wait or request approval.

For example:

Create AMI
↓
Stop EC2
↓
Update Config
↓
Start EC2
↓

Automation = automating a multi-step process.

7. State Manager

= hold on desired configuration.

For example, if you want every EC2 to always have a CloudWatch Agent:

Desired:
CloudWatch Agent must be installed

Actual:
EC2 does not have an Agent yet

↓
State Manager

→ return the device to the desired state

State Manager = ensures the machine's configuration is always as desired.

8. Operating conditions

Automation's Execution role must have permissions for each target service; Not every step requires SSM Agent on the device. Session Manager can logs to S3/CloudWatch Logs when configured, but SSH tunnel/port forwarding content is not logged this way.

Run Command supports concurrency limits/error thresholds; Patch Manager is not used to upgrade major OS versions.

9. Use cases

Use cases: Runbook creates AMI, updates configuration, and verifies EC2; Maintenance Window selects running hours; The State Manager keeps the CloudWatch Agent installed.

Quick review · SAA-C03

Systems Manager manages fleet operations: Run Command executes commands; Patch Manager patches the machine; Session Manager access without opening SSH.

↓

↓
