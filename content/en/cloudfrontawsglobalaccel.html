Amazon CloudFront: CDN & origins

Purpose: Deliver web/files via edge near users to reduce latency and backend load.

1. Cache at the edge

Viewer → edge location
          ├─ cache hit → return content
          └─ cache miss → origin → cache when policy allows → return content

Origin: where the original content is located.

Distribution has one or more origins; cache behavior determines origin and policy for each URL path.

CloudFront serves both static and dynamic HTTP(S), not just static files. Uncache requests can still use network and connection optimization.

CloudFront and origin do not need to be in the same AZ. CloudFront is a global service running in edge locations; origin can be in an AWS Region or on-premises. VPC origin must use supported Region and resources.

2. Origins

Origin / mechanismFunctionFor example
S3 OriginGet content from S3 bucketHTML, CSS, JS, images
Custom OriginGet content from HTTP/HTTPS serverPublic ALB, EC2, web server on-premises
VPC OriginPrivate connections to VPC resources are supportedInternal ALB, NLB, EC2
Origin GroupPrimary + secondary origins group for failoverPrimary ALB fails → Secondary S3 serves the backup site

Origin Group is a backup group, not a type of server. Failover according to configured connection error/status codes, GET/HEAD/OPTIONS only; OPTIONS must also be enabled in cached HTTP methods. Do not use this mechanism to failover POST yourself.

VPC origin helps origin to be private, but must still meet SG/network requirements and supported features.

Public custom origins need to limit users from bypassing CloudFront if edge protection is required.

3. Cache Behaviors select origin

Path patternOriginRequest example
/images/*S3/images/logo.png
/api/*ALB/api/orders
Default (*)On-premises server/home

CloudFront reviews behaviors in the configured order and use the first matching behavior; Do not choose the most specific pattern yourself. If individual behavior does not match, use Default Cache Behavior (*).

4. Private S3 and OAC

OAC signs request from CloudFront, bucket policy for distribution is read; No need to open a public bucket. Object SSE-KMS also needs a suitable KMS key policy.

S3 REST bucket origin is different from S3 website endpoint. The website endpoint is a custom HTTP origin, not using OAC in the way of a private bucket origin.

5. TLS and edge protection

Custom domains need a certificate with the correct name.

ACM certificate for viewer → CloudFront must be in us-east-1; certificate for origin is a separate leg. AWS CloudFront certificate requirements.

WAF filters application requests; Shield helps protect against DDoS; signed URL/cookie controls viewer access to private content.

OAC grants CloudFront permission to read S3, without authenticating each user.

6. Use cases

Use cases: Global website/photo/video: CloudFront + S3. Private app needs edge delivery: VPC origin is suitable. HTTP(S) API: behavior/cache policy according to content and security requirements.

7. CloudFront Video Streaming (VOD vs Live) & Custom Domain HTTPS

CloudFront caching, delivery controls & geo restriction

Purpose: Cache the right content, update it at the right time and limit who can receive the content.

Cache stream:

Viewer requests
↓ Cache keys
CloudFront edge
├─ hit → cached response
└─ miss → origin → response / cache according to policy

1. Cache key

Cache key determines which requests share the same response. Path is the main part; You can add query strings, headers/cookies as different content.

Putting too many variables in the key reduces cache hits.

Leaving out variables that actually change the content may return erroneous data; Individual responses according to users need safe or non-cache policies.

2. Cache policy and origin request policy

Cache policy determines key/TTL. Origin request policy transfers additional information to origin even though it is not in the key.

Forward header/cookie does not by itself guarantee a unique response. Check cache behavior with origin's Cache-Control, especially minimum TTL and sensitive data.

3. TTL, file version and invalidation

TTL regulates cache time.
Origin changes the file without automatically making every edge get a new version immediately.
Use a version name like app.abc123.js for assets that don't change; HTML can have short TTL
more.

Invalidation removes path from cache before TTL: /index.html, /images/* or /*.

Wildcard path helps delete many objects but invalidation still has quota/cost; It is not a mechanism to backup or repair the original file.

4. Signed URL and signed cookie

Signed URL matches a specific file; signed cookie merges multiple files such as videos
many segments.
Both control the duration/conditions of private content access via CloudFront.

Block direct access to the origin if you want every user to pass this check. S3 pre-signed URL is another mechanism, granting requests directly to S3 with signer permissions.

5. Geo restriction

Allowlist/blocklist by country in distribution based on Geo-IP.
VPN/proxy may affect location identification; do not change
authentication/authorization by user.

6. Price Class

Price Class Choose a group of edge locations serving distribution to balance costs and latency.

Price ClassScopeTarget
100America, Canada, Europe, IsraelLimited to lower cost areas
200Class 100 + many regions in Asia, Africa, Middle East; There is VietnamBalance cost and coverage
AllAll CloudFront edge locationsLargest global coverage

For example, customers in Vietnam: Class 100 does not include edge in Vietnam, so you may have to go further; Class 200 includes Vietnam so latency can be reduced; All opens the entire edge network. Actual costs depend on traffic and service area.

Price Class does not block users by location. People outside the range can still access it; If you want to restrict countries, use Geo Restriction/WAF.

7. Viewer Protocol Policy

PolicyMeaning
HTTP and HTTPSAllows both protocols
Redirect HTTP to HTTPSConvert HTTP viewer to HTTPS; HTTP/1.0 requests using write methods may be rejected
HTTPS OnlyOnly for HTTPS; HTTP returns 403

Policy applies to the leg viewer → CloudFront; The CloudFront → origin route has its own protocol policy.

8. Use cases

Use cases: JS/CSS versioned: Long TTL. Quickly changed HTML: invalidation. Paid content per file: signed URL; multiple video segments: signed cookie. The content varies by query: the cache key contains the necessary query.

9. Automatic Compression (Gzip/Brotli) & 4 Viewer/Origin Events hook points

Automatic Compression: when the browser sends Accept-Encoding: br, gzip, CloudFront automatically compresses eligible files using Brotli/Gzip at Edge, compressed and paid cache Content-Encoding.

Event HookRunning timeSupported by

AWS Global Accelerator

Purpose: Bring TCP/UDP traffic into the AWS network near the client, keep the IP stable and transfer it to a healthy endpoint.

1. Anycast and network line

Anycast
= multiple network points broadcast the same IP; The client goes to the appropriate edge and then traffic
follow the AWS backbone to the endpoint.
Client → static Anycast IP → AWS edge → AWS backbone → regional endpoint

Global Accelerator IPv4 typically provides two static IPv4; dual-stack adds IPv6. IP stays stable when changing backend, useful for firewall allowlist.

2. Endpoints and health

Endpoint group by Region contains ALB, NLB, EC2 or EIP according to the supported configuration.
Health controls where traffic is received; Endpoint weight and traffic dial adjustable
distribution.
Traffic dial changes the rate of traffic entering a Region; endpoint weight divided in
group. group.
When there is an error, the service changes network routing without having to wait for the client to run out of DNS cache
get a new IP.

3. No cache

Global Accelerator accelerates the network, does not cache HTTP objects.
New content is still coming to the app; TLS, authentication and request control remain
needed at the endpoint/application.

Do not confuse the Global Accelerator's static IP with the AZ static IP of an NLB: Accelerator sends global traffic to regional endpoints.

4. Use cases

Use cases: UDP game, VoIP, global TCP app; Multi-Region APIs need stable IP allowlists and quick transitions from faulty endpoints. Website needs to cache images/videos near the user: consider CloudFront.

5. Target Endpoint types supported by Global Accelerator

Global Accelerator routes to all Internet-facing ALB/NLB, Internal ALB/NLB, EC2 Instances and Elastic IP in one or more Regions without exposing the internal network structure.

Quick review · SAA-C03

Global Accelerator uses static anycast IP and the global AWS network to improve access to regional endpoints; Does not cache content like CloudFront.

CloudFront vs Global Accelerator vs S3 CRR

Purpose: Distinguish between content acceleration, network acceleration and persistent data replication.

Three mechanisms:

CloudFront = HTTP(S) delivery + cache
Global Accelerator = TCP/UDP acceleration, no cache
S3 CRR = copy object to another Region

1. Comparison table

MechanismWhat to do?When choosing
CloudFrontCDN for HTTP(S), caches at the edge and passes requests to the originWeb/API, photos, videos, signed content
Global AcceleratorTCP/UDP over AWS backbone with static Anycast IP, no cacheGlobal app, IP allowlist, network failover
S3 CRRReplicate object to bucket in another Region, asynchronouslyDR, compliance, data must have a regional copy

2. Cache is different from replica

CloudFront cache may evict or run out of TTL; origin is still the data source.

CRR creates a real object in the destination bucket, requires Versioning and permission; The app that wants to read the target version must access the correct bucket/endpoint.

Do not use CloudFront cache instead of backup/DR for S3. CRR does not automatically distribute HTTP to the edge or automatically move all clients to a backup bucket.

3. CloudFront is different from Accelerator

CloudFront understands HTTP and has cache behavior, signed URL/cookie, geo restriction.
Global Accelerator handles TCP/UDP and static IP routes; no key cache/TTL
like CDN.

HTTP app can also use Accelerator when a fixed IP/network failover is needed. Choose according to the main requirement, not just based on the word “global”.

4. Use cases

Use cases: Photo website: CloudFront. Multi-Region UDP Game: Global Accelerator. Object needs another Region copy: CRR. It's possible to have CRR for DR and CloudFront for delivery, but you still have to configure origin/failover accordingly.

Quick review · SAA-C03

CloudFront optimizes HTTP content caching; Global Accelerator optimizes network path/TCP-UDP; S3 CRR copies data between Regions.
